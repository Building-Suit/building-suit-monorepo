# SAS private invalidation transport

Child of the client correction #294. This implements server-generated invalidations for committed SAS configuration receipts, adapter command receipts, verified-manifest observations and ingested remote audit observations. The existing adapter verifier still owns signature/digest/nonce/response validation; notification triggers do not create receipts or grant target authority. Query receipts do not emit, avoiding a fetch/receipt/invalidation loop.

The server topic RPC returns `sas:<authority environment>:<operator user>:<Auth session>`. It requires an enabled database-provisioned owner, an active authority environment and a matching existing, unexpired `auth.sessions` record. Topics are received through an authorized no-store endpoint; browsers cannot choose another operator or target project. A read policy plus a restrictive namespace policy protects these topics even if another permissive policy exists. A restrictive INSERT policy prevents client sends to the namespace. No managed-schema RLS alteration or broad table grant is included.

The sanitized outbox stores only a source key, random event UUID, authority environment, optional internal binding, invalidation kinds and delivery timestamps. Recipients are selected at delivery time from enabled owners and active Auth sessions in that authority; bound events additionally require the active Suit/binding/target environment. Shared recipient locks serialize delivery against operator disable/session removal. Each private broadcast payload has only `id`, `authorityEnvironmentId`, and `kinds`. It contains no customer row, payment payload, actor identity, secret, provider response or target project connection detail.

Operator revocation attempts one final empty invalidation to its old session topics; the client rechecks authority, clears projections and closes the channel. Subsequent emits exclude revoked owners. Supported Auth logout removes the session and subsequent emits exclude it even if an old websocket permission/JWT is cached. Foreground/subscription/reconnect recovery rechecks the existing Auth-session record; no completed authority check is cached. Server flushes are bounded to 100 pending items, service-role-only, deduplicated by source key, and client event IDs suppress repeated reads. Provider acceptance is confirmed by a read of the matching private managed message because `realtime.send` catches errors as warnings. A failed publication leaves a pending outbox item without rolling back the business command. The delivery timestamp confirms database publication to currently eligible sessions, not socket acknowledgement; initial/reconnect/foreground authorized reads recover missed messages. No scheduler or credential is provisioned.

## Existing secure Shop path and explicit gap

A SAS-initiated Shop command traverses the existing signed target-owned bridge. Its verified SAS receipt commits into `adapter_attempt_results`; only command receipts then enqueue invalidation for that binding's authority. An explicit authenticated audit retrieval verifies and ingests remote observations, which also enqueue Activity invalidation. Neither path reads another project's private database or subscribes to its Realtime service.

A Shop-originated change made outside that bridge (including a provider webhook) does not currently push an unsolicited event into SAS. This PR does not claim that coverage. A future target-owned event outbox/forwarder needs a separately reviewed reverse event capability and provisioned binding/signing reference. SAS must verify canonical signed envelopes, audience, source/target binding, timestamp/nonce, event-ID/digest replay identity, payload allowlist and rate bounds; map the approved source binding to the authority server-side; then enqueue only kinds. Target secrets, project refs/endpoints and service-role keys must stay outside browsers. No unsigned generic webhook, client-selected topic, cross-project socket, target table grant, credential reuse, or background audit polling is a fallback.
