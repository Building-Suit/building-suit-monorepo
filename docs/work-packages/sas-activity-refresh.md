# Super Admin Activity refresh correction

The inspected saved screenshot (`libfile_425a5fbaaaf4819199aaf0a40a7b277d`) shows Activity. The previous index route refreshed the registry every 30 seconds. While that request was pending, `useAdminRegistry` projected an empty selection and `loading`; the Activity context watcher then reset its query, pagination and rows. The same-user Supabase auth notification and focus handler also cleared the session/registry before rechecking, creating another false context transition.

Keep the last authorized registry/session visible during a background request. Explicit sign-out, actual user/environment/binding changes and authorization denials still clear sensitive projections. Activity refresh keeps its query and existing rows until the authorized response arrives; payment queue refresh keeps its selected review and draft. New invalidations recheck authority rather than relying on a completed check cache. Same-user repeated `SIGNED_IN` notifications do not erase review state; initial session and token refresh still revalidate quietly.

There is no recurring registry data poll. A receive-only, same-project private Supabase Broadcast channel queues sanitized invalidations, coalesces bursts and duplicate IDs, checks environment scope, closes on identity change/disposal, and performs one recovery on subscription/reconnect, online, visibility or focus. Deferred updates wait while a review/configuration/offer dialog or command is active; authority is still checked before deferral. Notifications only request authorized HTTP projections; notification payloads never supply records, privileges or commands. Channel transport heartbeats/reconnects are separate from data polling.

## Hosted delivery remains a separate approval gate

This change prepares the receiver; it does not install a hosted emitter or Realtime authorization policy. Without that setup, foreground recovery and explicit user queries work, while uninterrupted cross-tab/server-change delivery is not established. A denied private channel must not fall back to a public channel or raw `postgres_changes` subscription.

A separately reviewed setup must authorize SELECT on the managed `realtime.messages` broadcast channel only for the current verified administrator's authority environment. Use the existing `public.super_admin_session()` authority result and an exact `sas:<authorityEnvironmentId>` topic, rather than user-editable metadata. No client send/INSERT grant or read grants to control-plane tables are needed. Do not change managed-schema RLS globally, subscribe to a Shop project, or send provider/customer/row payloads.

A sanitized server emission has only `{ id: <unique UUID>, authorityEnvironmentId: <verified environment>, kinds: <subset of registry/activity/billing/offers/configuration> }`, broadcast event `invalidate`, private topic `sas:<environment>`. Configuration revision/verified-manifest changes invalidate the registry; authorized activity and command receipts invalidate affected projections. Query/read receipts must not emit invalidations, which would create a feedback loop. Remote audit retrieval remains explicitly partial; this receiver does not turn every target Shop mutation into a local observation.

Before enabling delivery, test two independently authenticated administrator tabs in the same authorized environment, wrong-environment subscribe denial, signed-out denial, revoked-owner denial, command/query feedback-loop prevention, reconnect recovery, idle request counts and dirty review preservation. Hosted setup and these real delivery checks are unrun and require separate approval. No migration, security setting, provider credential, hosted data, or payment incident record was changed for this work.
