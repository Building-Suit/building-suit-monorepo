## Observed cause and resulting behavior

The live before-change inspection recorded ten `agents` invalidations in a ten-minute window. The existing Oracle worker calls its trusted presence RPC once a minute, and that RPC unconditionally emitted an application invalidation. A liveness heartbeat therefore caused a complete agents/office-observations GET even when no work changed. Separately, company subscribed to Brain changes although its operational snapshot is independent, and initial/reconnect refresh paths could overlap. The Chat composer treated the shared loading flag as a reason to disable input and Send during these background reads.

Background agent refresh now retains the last authorized transcript and uses a separate refreshing state. Typing and sending remain available; an explicit send takes priority over a replaceable background GET, with request epochs preventing the late aborted read from overwriting the write. Unknown write outcomes retain their exact idempotency key, and revoked/offline/account changes still clear sensitive state.

The shared SSE hub coalesces the initial/reconnect snapshot across subscribers, ignores repeated ready frames and sends subsequent category hints only to their own subscribers. A short-lived connection does not reset exponential recovery backoff; only a sustained connection earns a fresh retry budget. Visibility/online recovery awaits one access check before reopening. Protocol comments and heartbeats cause no application data reads. Consumer disposal removes listeners and pending retries.

Forward migration `20261105192548_hq_presence_without_snapshot_polling.sql` changes the existing worker-presence RPC to emit a small private observation containing its actual timestamp and optional current leased employee/task. The BFF checks fresh founder authorization before forwarding it. The browser updates only monotonic, bounded runtime/known-working-agent timestamps, without fetching a snapshot or inventing task activity. Missing observations expire honestly through a display-only timer. An ephemeral presence-delivery error cannot cancel a valid job lease or rerun inference.

Actual job state changes still push `agents`; lease/timestamp-only renewals do not. A genuinely changed roster pushes both `agents` and `company`, because company uses the roster for office membership. An identical roster sync emits neither. Company no longer refreshes merely because a Brain document changed. This is event-driven application delivery with transport/lease liveness, not recurring company, agents or Brain data polling. No worker module change or restart is required.
