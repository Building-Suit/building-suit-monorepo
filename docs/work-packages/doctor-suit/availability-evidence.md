## Review regression: timezone changes during an hours edit

Independent parent review identified that the first schedule-write API accepted only the schedule version. A deterministic two-transaction reproduction held a clinic-timezone update under the practice lock while an already-open hours editor waited. Against `f32cd2f3`, the editor incorrectly committed after that lock released (the regression failed because its command exit status was zero).

Schedule writes now require the location version captured with their configuration. After acquiring the same practice lock and rechecking current authority, the backend compares this version before validation, receipt lookup, schedule mutation or audit insertion. The idempotency material includes the location version. The client rejects an already-observed configuration/context mismatch before calling the adapter and sends the captured configuration version to the server; a response-time check remains additional protection. Missing location context is rejected.

The new transaction regression requires SQLSTATE `40001` / `DOCTOR_AVAILABILITY_CONFLICT`, byte-for-byte unchanged schedule rows, no new schedule audit and no successful command receipt. A freshly opened editor with the new location version succeeds and returns the new timezone. Existing availability, readonly clinic, revocation, and booking-timezone scenarios remain part of the full regression suites. Final exact-candidate receipts for this correction are recorded in PR358.
