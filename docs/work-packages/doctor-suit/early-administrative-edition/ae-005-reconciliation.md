## Implemented evidence and reporting

The database-owner-only `doctor_private.record_saas_synthetic_evidence` fixture interface records enumerated payment observations in an immutable ledger. It accepts only the `synthetic-fixture/` namespace, exact integer amount/currency/subscriber, intent, outcome, sequence and delivery ID. There is no public/provider endpoint, raw payload, redirect, arbitrary URL, credential, signing secret or new client grant. The function is security-invoker and its tables and execution are revoked from anonymous, authenticated and service roles. Both tables force RLS. The database-owner test harness is explicitly a fixture writer, never proof of authenticated provider or approved manual-review authority.

Every new event binds to one held intent. Exact amount, currency and subscriber comparisons classify matching versus mismatched evidence. Per-delivery and global event locks precede the subscriber lock. Same delivery/request returns its original receipt; a changed request for that delivery fails atomically. A new delivery of the same exact event is recorded as duplicate. A changed payload or reuse of one event across intents is retained as a conflict and puts both affected intents into discrepancy review. Event rows are never overwritten and conflicting transactions leave no orphan event. Unknown outcomes require review; pending observations arriving after a synthetic confirmation do not downgrade it. Contradictory confirmed/failed or same-sequence outcomes require discrepancy review rather than guessing provider ordering or refund semantics.

All evidence remains synthetic, including `confirmed_synthetic`. It never changes the held intent, subscription account, period, eligibility or paid/live access. The original payment route remains unconfigured. No event, URL, metadata, receipt or unknown/pending state can authorize settlement. A future real provider/manual route must implement independent verified evidence, exact target/merchant binding and approval/custody/review gates before it can be considered for actual settlement. This packet cannot grant those approvals.

`doctor_saas_financial_status` and the strict application adapter expose only the subscriber's SaaS held-intent population. Full-population totals are independent of page size and grouped by currency **and explicit exponent**. `quoted_minor` is an exact decimal string, even when aggregate values exceed JavaScript's safe-integer range; it is the sum of selected base quotes, not invoiced, collected, settled, refunded or patient revenue. `settled_minor` is null because settlement is unavailable, rather than a fabricated known zero. Each paginated row links its immutable quote, intent and synthetic event IDs. Foreign owners receive no rows/totals/source links; delegated practice access cannot read subscriber finances. Accepted raw provider payloads and other subscribers' reported identities are never returned.

Invoices, settlement, lifecycle and paid/live activation remain explicitly false. Independent financial review remains pending. There is no automatic charge/refund, guessed billing/effective date, renewal/cancel/reactivate execution or invoice/tax-compliance claim. Current trial/expiry/history access behavior remains owned by the already configured immutable terms. Requests for unavailable financial lifecycle actions must not be presented as completed actions.
