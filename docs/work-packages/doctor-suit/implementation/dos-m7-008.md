The existing M3 runner emits `test-results/doctor-m3-actual/provider-receipt.json` with exact head/base, clean source, execution outcome and all ten browser task results. The existing native candidate reader validates both API29/API36 shell/vault/policy populations, exact APK/test-APK/source and the synthetic-only authority restrictions. Neither proves production capacity, physical-device qualification or approved recovery. These readers already exist; they are reused rather than reimplemented.

`tests/helpers/operational-support-evidence.mjs` compares an explicit declaration with bounded supplied JSON bytes and their supplied SHA-256 hashes. It admits the actual M3 producer format and reuses `inspectNativeCandidate` for native receipts. It rejects a mismatched head/base, altered bytes, incomplete/duplicate/failed M3 population, wrong APK/native population, contradictory coverage declaration, missing surface exclusions and any inferred production capacity, provider upgrade or production load authorization. Explicitly absent receipts remain unavailable; an all-missing receipt population returns overall unavailable even when the declaration honestly says unavailable. A same-source successful receipt is not evidence for another candidate.

The output distinguishes verified **supplied receipt consistency** from unavailable evidence. It always preserves physical-device, iOS, patient-mobile, offline-clinical and clinical-production exclusions. Operating limits stay unavailable without approved workloads, verified provider quotas/costs and accountable support/runbooks. Rollback dependencies stay unavailable without approved recovery objectives/custody, complete database/object restore and an authorized scope. No new threshold, custody assignment, provider contract or operational profile is invented. No opaque evidence can switch those declarations to verified.

The helper has no network/filesystem/execution interface. It hashes actual supplied bytes; a matching caller-supplied hash establishes integrity consistency, not authenticity. `executionProvenanceVerified`, `fullTaskAccepted`, `clinicalApproval`, `productionCapacityClaim`, `providerUpgradeAuthorized` and `productionLoadTestAuthorized` are always false. A trusted independent runner must separately retrieve the real allowed artifacts and establish their run/job provenance. Pure unit fixtures cannot supply that proof. Failed or unavailable receipts are never silently promoted into readiness.

Local tests use synthetic representations of the existing producer formats. They cover missing/changed source, input digest mismatch, duplicate/failed population, inherited native rejection boundaries, contradictory declarations, removed exclusions, unauthorized readiness claims and bounded/private input. The tests exercise the actual comparison and reused reader; they are not SQL, browser, load, restore or hosted execution. No dummy SQL/browser placeholders are added. Canonical C03 still requires authentic independent exact-candidate receipts for all obligations, including the presently unavailable operational and rollback evidence.
