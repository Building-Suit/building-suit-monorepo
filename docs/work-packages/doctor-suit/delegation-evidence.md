# DOS-M1-009/010: independent secretary membership and administrative grants

Parent PR354 head `f4bbfb3ea5abd67099e155d344cd5051fac139b8` provides the location/context foundation. The immutable planning-v0.4 source remains PR345 head `4ca7110f4d6efa828e0b41213e5c059bf02ba9db`. This focused access-management change implements invitations before the dependent grant editor. It does not import/activate Automation, connect providers, migrate hosted data, deploy, merge staging/main or establish clinical/legal authority.

An invitation binds one stored practice, verified recipient email, a 32-byte browser-generated secret hash, expiry and exact approved administrative capability sets for each selected location. Owner-only creation, cancellation and membership status/grant commands use practice serialization, optimistic versions and actor-bound receipts. Acceptance also takes the recipient enrollment lock, validates the latest confirmed session/recipient/secret/expiry/scope and creates one independent membership. Matching email alone never grants access. A secretary identity may accept two doctors' independent invitations without gaining a doctor profile, owner association or subscription. Metadata cannot supply ownership or clinical authority.

The browser submits only a SHA-256 hash during creation. The raw secret appears only in the one-time local receipt and the recipient's private POST body; it never enters URLs, cookies, persistent client drafts, stored backend rows, receipts or telemetry. Uncertain creation retries preserve the same key/material while that form remains open, including equivalent recipient casing and capability-set ordering. Closing, leaving or changing account/context discards local material and invalidates pending results. A lost/closed uncertain receipt requires cancelling the pending invitation and issuing a new one. The preview sends no email or external message and makes no delivery claim. The user privately transfers the code to the intended synthetic recipient.

Every new membership-location row stores an exact capability set. Legacy NULL overrides retain the earlier explicit membership contract until replaced. Current authorization and context projections resolve per-location sets rather than inheriting the aggregate union. Owners may replace selected/all eleven approved administrative capabilities or remove every grant. Grant edits never reactivate suspended/revoked status. Clinical signing, prescribing, team delegation and owner promotion are absent from the administrative catalogue. Status and grant mutations preserve practice/actor/member attribution; grant audit details retain exact before/after location/capability sets. Historical rows and accepted audit events remain intact.

Shared UI owns the existing complete access and invitation templates, controlled permission fields, bounded pagination and confirmation dialogs. Apps own values, validation, typed RPC adapters, secret lifecycle and commands. Shared UX owns foreground/visible-page refresh. Existing consumers keep their optional defaults. All new routes are in the canonical registry, with no local Vue composition or CSS. English/Arabic mobile/desktop flows use the same presentation.

Protected context is rechecked on foreground/visibility return and every 30 seconds while visible. Refresh work coalesces; unchanged context preserves drafts. Changed/revoked grants clear protected rows, pending dialogs, local search/drafts and scope before subsequent data is accepted. Backend authorization applies on every request; foreground/interval request latency remains. No Realtime push or immediate remote browser invalidation is claimed. Hidden or suspended documents do not start refresh work, including queued foreground events after pagehide. Document/BFCache/auth cleanup retains its existing fail-closed policy. Team list data uses explicit request refresh; another browser's acceptance is seen after a reload.
