# DOS-M1-014 appointment and queue evidence

Parent: independently reviewed passing PR358 head `54f91a987a7ef9dba86290190b63e8775d315a5a`. Planning remains immutable PR345 head `4ca7110f4d6efa828e0b41213e5c059bf02ba9db`. This work implements synthetic administrative appointments; it does not import/activate Automation, publish a release, deploy a provider, merge staging or assert clinical/legal approval.

The server has six explicit states: booked, checked_in, in_progress, completed, cancelled and no_show. Only six source/target edges are allowed. Same-day check-in retains one appointment identity as the queue entry. A doctor-wide partial unique index prevents two in-progress visits, including across clinics. Cancellation after check-in requires both appointment-write and queue authority and retains its reason and prior check-in. An in-progress visit can only complete administratively; it cannot be cancelled or rescheduled. No clinical signing authority is granted.

Booking and rescheduling use the authoritative availability/conflict helper and doctor-wide range exclusion. Rescheduling requires fresh source/destination grants, current active patient, captured rule/location versions, original appointment version and an administrative reason. Exact retries retain one receipt/event. Changed rules, locations, grants or sessions are checked after the practice lock. Existing times, original clinic/timezone snapshots and immutable event history survive hours/location edits, rescheduling and archive. Active queue dependencies block archive even when the scheduled end is past. Historical rows remain retained by foreign keys.

Appointment reads require exact `appointments.read`. Patient names require a separate current `patients.read`; otherwise the projection is explicitly redacted. Writes and queue commands require their independent capabilities. Browser direct table reads/writes are denied. Histories are paged and require access to every clinic represented in the history. Every important write appends actor-attributed administrative events and audit.

The complete `BsPracticeAppointmentsPage` composes existing shared calendar, entity picker, data table, dialogs and pagination. Doctor adapters own queries and domain rules. Shared UX protects dirty forms, pending/confirmation state and late command settlement. Captured confirmations retain the original record/version. Uncertain replies keep the original idempotency material. A known denial immediately aborts all pending private work and invalidates late replies. Context, grant, clinic, auth SID and unmount changes clear forms, histories, patient options, slots and subscriptions. English/Arabic desktop dark/mobile light journeys cover these flows. External delivery remains explicitly disabled.

Realtime subscribes only to INSERT/UPDATE revision events; DELETE events are excluded because the documented provider behavior does not apply row policies to deleted records. The policy treats an invalid/revoked SID as a false row predicate; authoritative RPCs still reject that SID explicitly. Realtime publishes only practice ID, clinic ID and a revision counter, with no appointment/patient payload. A restrictive RLS guard retains fresh verified-session/current-clinic permission checks even if another permissive policy is added. The existing shared `createScopedRealtime` owns subscription teardown, obsolete-event rejection, coalescing and authoritative initial/reconnect refresh. Disconnects discard stale board/history/slots; explicit refresh and foreground revalidation remain available. Publication registration uses the [documented Supabase interface](https://supabase.com/docs/guides/realtime/postgres-changes). Provider-managed schemas are preserved.
