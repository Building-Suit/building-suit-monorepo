# DOS-M1-007: doctor-led synthetic practice setup

Parent PR352 provides verified Doctor sessions. This task implements the original planning-v0.4 onboarding acceptance without changing or reimporting those plans. The user-authorized GitHub workflow remains separate from inactive Automation. No hosted migration, deployment, operational registration or main promotion is performed.

The approved setup fields are doctor display name, practice name, initial location name and an explicitly selected IANA timezone. The backend stores these in a user-owned draft and uses a persisted command key and version to resume another verified session. Completion creates one profile, one practice owner association and one initial location atomically. The canonical owner association is `practices.owner_user_id`; the doctor needs no delegated secretary membership row. Exact command retries cannot duplicate ownership, locations or audit events. Stale draft/profile versions fail explicitly. Eligibility is rechecked under the actor transaction lock so a concurrently accepted delegated membership cannot race owner setup.

The current and compatibility onboarding entry points reject delegated-only accounts using stored memberships, independent of editable metadata. An existing practice owner remains an owner when also delegated elsewhere. This is synthetic administrative enrollment; it never establishes professional credentials, legal approval, clinical signing authority or a paid entitlement. Profile maintenance changes only the approved owner/practice names through an owner-only optimistic, audited, idempotent command. Location maintenance and selection remain DOS-M1-008.

All presentation remains in packages/ui. The existing shared signup template gains optional profile/timezone/contact-field controls and a semantic draft-save action. Existing consumers retain their default fields. The new complete practice overview and the shared shell show the authorized initial practice/location context on mobile and desktop. Doctor adapters own all queries, values, validation, navigation and error classification. Private state belongs to one Nuxt app, is cleared on auth/session changes and document exit, and cannot be restored by late requests. Existing shared UX hooks clear transient form data and revalidate BFCache restores.

Verification includes nine stateful unit tests for projection whitelists, incomplete drafts, duplicate-submit exclusion, uncertain-response request identity, separate-session resume, stale/aborted reads, delegated denial and profile conflicts. Actual migrated disposable PostgreSQL runs 92 assertions: 34 identity/RLS, 14 current-session and 44 setup/profile assertions. Four additional real concurrent-transaction scenarios verify enrollment denial after the actor lock releases and duplicate completion with one practice/location/audit event. The browser protocol fixture exercises draft resume in another browser context, doctor-alone completion, profile maintenance and delegated denial in English desktop and Arabic mobile. Its synthetic HTTP responses do not prove actual Supabase service behavior.

**Full Supabase Auth/Storage/Realtime service integration remains UNRUN** because the executor could not extract the provider PostgreSQL image within its disk capacity. SQL provider-contract scaffolding and the HTTP fixture do not replace that obligation. Connections are user-managed, clinical/legal/provider gates remain open, and no real patient data is used. Exact-head CI receipts and final command totals belong in the task PR.
