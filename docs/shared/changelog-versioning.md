# Shared versioned changelog

BS-CHANGELOG-VERSION-001 / BS-LAUNCH-R15. SemVer is per Suit (BS-VERSION-D01); New lasts exactly 48 hours from authoritative actual release publication (BS-CHANGELOG-NEW-D01). The owner correction of 2026-10-15T21:45:58Z defines the active release boundary: **one evolving upcoming release per Suit from the actual current main-to-stg tree difference**, not a release per PR/push. Several readable changes belong inside that one release. No historical task record or stored release is deleted or rewritten.

`packages/contracts/src/changelog.ts` validates bilingual Suit identities and entries. Released entries require strict SemVer `version` and `releasedAt`. Coming Soon uses `targetVersion` and forbids released-version/date fields. Every item has English/Arabic title, summary and plain-text details; no raw HTML, commit/task dumps, credentials or unknown metadata reaches the public projection. An upcoming revision's `publishedAt` is its trusted preview-update time and is displayed as Updated. It never starts New or implies production shipment. A frozen actual release keeps its first-publication time, version, contents and digest forever; retries and copy refreshes cannot extend the badge.

The environment-specific SAS catalog is authoritative. Apps query only its sanitized public RPC through the environment-bound Nuxt server adapter. SAS never reads/writes target Suit databases; browser roles cannot mutate candidate/history tables or publishing RPCs. Unknown registration, missing baselines/auth/configuration, mismatched environments/trees, failed deployments and malformed translations fail closed. Transport/configuration errors remain explicit rather than turning into successful empty feeds.

Agents curate `release-changes/items.json` with meaningful current-code evidence against actual current main and staging trees. Private task fragments remain review provenance and path/dependency classification, not public release boundaries. Deterministic CI removes fully reverted/already-on-main items, retains surviving partial/overlapping changes, includes divergence/removals and requires review coverage. The highest remaining public impact derives one target from the actual production version. A first official private origin of `0.0.0` is not invented history; current combined Shop capabilities target **one 0.1.0**, with no manufactured earlier 0.1.0/0.1.1 releases. Details, probes, preservation, production acknowledgment/retry and external activation are specified in [the runbook](release-publication-runbook.md).

Staging refreshes a retained immutable candidate revision and serves it as Coming Soon only after staging readiness. An authorized stg-to-main promotion freezes the exact ready candidate only after production readiness; it validates rather than bumps its saved version again. Internal-only/net-zero work produces no public version. Production receipts update the next candidate's baseline; failed acknowledgment resumes idempotently, preserving committed production history. Direct-main hotfixes/conflict-resolution edits without an exact staged candidate cannot be advertised. Original legacy anchor/manifests remain evidence but do not restrict current net-diff coverage.

`createChangelogClient` validates and filters by Suit/status/search; it owns no target database or publisher credential. `BsChangelogTimeline` and `BsChangelogCard` provide shared AR/EN, LTR/RTL, light/dark, responsive status controls and explicit loading/empty/error/retry states. The Shop landing teaser and full `/changelog` use keyboard-accessible Released (default) and Coming Soon tabs. The teaser limits the selected status to three entries, then links to full history using Premium Gold and a direction-aware arrow; full history is unlimited. Cards show real version and release date only for released entries. Upcoming target versions and timestamps remain integrity metadata and are omitted from presentation. Duplicate title/summary/detail text renders once. `selectChangelogOverview` and `selectChangelogReleases` remain available for consumers that explicitly need complete groups. See [the released-history evidence audit](changelog-history-audit.md) for the unversioned production baseline. Grouping never rewrites clocks. Language switching reads the same bilingual records.

New is true only for a released public entry with `0 <= serverNow - publishedAt < 48h`. UI time starts at the trusted server snapshot and advances by monotonic elapsed time, never browser wall-clock guesses; resume/navigation refreshes the snapshot. Upcoming entries never get New. No manual visual acceptance, merge, production promotion, provider activation or credential configuration is implied by this specification.
