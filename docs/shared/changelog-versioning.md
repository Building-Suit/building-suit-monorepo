# Shared versioned changelog

BS-CHANGELOG-VERSION-001 implements BS-LAUNCH-R15. Approved decisions from the task contract: BS-VERSION-D01 uses semantic MAJOR.MINOR.PATCH versions with explicit prerelease labels; BS-CHANGELOG-NEW-D01 uses exactly 48 hours from authoritative publication; BS-LAUNCH-D02 replaces the unexecuted Shop-only SS-WEB-CHANGELOG-001 scope. No historical implementation or task lifecycle record is rewritten here. Do not add a second Shop-only feed. Control-plane task supersession remains owned by that system.

`packages/contracts/src/changelog.ts` defines and validates the reusable feed. Suit identities are registered in `suits`, with bilingual names; entries must reference that registry. Shop, Ledger, Inventory, Automation and future registered Suits use the same schema. Versions use strict SemVer, including optional prerelease and build labels. Released entries require `version` and `releasedAt`; Coming Soon requires `targetVersion` (a SemVer target, optionally explicitly prereleased), and forbids released-version/release-time fields. A target is an intention rather than a release claim. Each entry requires English and Arabic title, summary and plain-text details, explicit visibility and UTC `publishedAt`. Links are optional; when provided they require bilingual labels and absolute HTTPS URLs without credentials.

A publishing service supplies immutable first-publication timestamps, release timestamps and `serverNow` from its trusted clock. Editing copy must not reset publication or extend New. Public services must authorize and remove internal entries before delivery, validate curated copy, and avoid publishing credentials, security details, raw commits or internal task IDs. The parser projects only approved fields; this cannot recognize sensitive text embedded in an otherwise valid title. Customer content needs agent curation and PR editorial review. The approved replacement for the manual publication bottleneck is task release fragments with deterministic CI, never raw commit/task conversion or an LLM in CI. Public filtering additionally excludes internal and future-publication entries and sorts newest publication first. Timestamp ties use stable Suit identity, release state and descending SemVer precedence within that Suit, then entry ID only after equal precedence. Numeric and prerelease identifiers follow SemVer without floating-point rounding; build metadata does not affect precedence. Versions from independent Suits are never compared as a shared sequence. Batch promotion can give several versions the same first-publication time, so opaque entry IDs must never decide which version is newest.

`createChangelogClient` in `packages/data-access` receives a product-owned authorized transport and validates each response before filtering by Suit, status or bilingual search. It forwards cancellation and owns no cache, tenant selection, credentials or product schema. Private adapters must keep environment/session/tenant scope in their own query keys and clear sensitive state on session changes. The environment-specific centralized SAS catalog and restricted publishing RPCs are defined by the new forward migration. Product Nuxt server read adapters consume only its sanitized public feed. [Automatic publication and activation](release-publication-runbook.md) describes the allocator, immutable manifests, dependency coverage, exact production promotion and external prerequisites. The implementation does not establish hosted activation.

`BsChangelogTimeline` owns timeline, card and native accessible Suit/status controls. Pass validated `feed`, `locale`, translated `copy`, optional fixed `suit` and `state` (`ready`, `loading`, `error`, `denied`). A fixed Suit removes the cross-Suit selector. Error retry emits `retry` for the owning adapter. `BsChangelogCard` displays identity, version or target version, explicit release state, publication/release dates, plain-text detail and optional links. Components do not fetch data or authorize access. The catalogue at `/components#changelog` uses synthetic examples, including a future registered Suit; they are not actual release announcements.

New applies only to released public timeline entries with `0 <= authoritativeNow - publishedAt < 48h`. The UI starts from `serverNow` and advances by monotonic elapsed time, never the browser wall clock. It resets this baseline when a new authoritative snapshot arrives and cleans up the timer on unmount. Feed owners should refresh authoritative snapshots after resume/navigation; publication corrections require a refreshed feed. Locale direction, version bidi isolation, responsive wrapping and semantic tokens preserve shared presentation.

## Shop landing discovery

The optional typed changelog projection on `BsLandingPage` renders shared `BsWhatsNewSection`, showing the newest three distinct deployed Shop releases, retaining every note in each selected Suit/version group and an EN/AR link to `/changelog`. `BsChangelogPage` displays the full public released Shop history. Both reuse `BsChangelogTimeline`/`BsChangelogCard` with the trusted clock and existing exact 48-hour badge. Public adapters exclude internal entries, future publication and Coming Soon; no fixture announcements appear in product pages. `selectChangelogReleases` selects complete released Suit/version groups after public filtering; the timeline’s `releaseLimit` counts those groups rather than truncating entries. Grouping and sorting never edit `publishedAt`, `releasedAt` or `serverNow`, so the New badge still expires exactly 48 hours after immutable first publication. Loading, empty, failure and retry remain explicit. This is an additive section after pricing, not a landing redesign.
