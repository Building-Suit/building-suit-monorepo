# Automatic task release publication

This is BS-CHANGELOG-VERSION-001 / BS-LAUNCH-R15. Agents choose the truthful change classification and curate copy during implementation; users do not select release numbers or release types. PR review approves the fragment. CI contains no LLM and never converts task or commit text into public announcements.

## Author and review

Add an append-only `release-fragments/<unique-id>.json` in each task PR. Required fields are `id`, internal `task`, registered `suits`, `classification`, `disposition`, `paths`, `reason` and, for public changes, `notes.title`, `notes.summary`, `notes.details`, each with English and Arabic plain text. `paths` are exact files or directory prefixes, without glob syntax. They cover every changed path except fragment files. Document genuinely internal changes with classification/disposition `internal` and omit notes. A task with public changes cannot hide them in an internal fragment.

Breaking compatibility is `major`; a backward-compatible capability is `minor`; a fix or improvement is `patch`. Internal maintenance produces no public version or entry. Per Suit, the highest public impact in one accepted merge wins. Multiple entries in that batch share the allocated version. New fragment IDs are mandatory for subsequent work on a task. Accepted fragments cannot be edited, deleted or reused. Corrections are separately reviewed fragments; they do not reset an existing publication timestamp.

`pnpm release:check` compares HEAD with origin/stg. In a stacked PR use `RELEASE_BASE_SHA=origin/<parent> pnpm release:check`. Required `review` runs the same validator against the PR head and base. It validates registration against repository Suit workspaces, path coverage, the transitive package dependency graph, duplicates, translations, public field boundaries and classification. SAS validates the authoritative active runtime registry again on acceptance. Shared changes expand only through affected dependencies; root tooling/policy changes require explicit classification for all consumers. Reviewers remain responsible for semantic truth, sensitive prose and accurate impact; regex checks cannot replace editorial review.

## Ownership and immutable state

The environment-specific Super Admin database owns the release catalog, registry and environment binding under ADR0004. It does not query or write target Suit databases. Automation `control.tasks` is unrelated. `release_version_heads` is the allocator high-water mark, initialized only from verified historical release evidence; missing baselines fail closed. Existing histories are not overwritten. Import historical public records and their original first-publication timestamps with a reviewed forward migration before activation if a prior real feed exists. Synthetic catalogue examples are not real releases or baselines.

`release_stage_accept` serializes on a transaction-scoped advisory lock and updates version heads, immutable manifests, consumed-fragment keys and the ordered cursor atomically. The unique source SHA and fragment keys are authoritative. Identical retries return saved outcomes; changed content under the same SHA fails. Versions are reserved before publication and never recycled. A failed transaction consumes nothing; a committed reservation with failed deployment remains pending. The immutable manifest includes source SHA/parent, repository, reviewed fragments, allocated versions, public copy and a PostgreSQL JSONB SHA-256 digest. Digest is over PostgreSQL's `jsonb::text` UTF-8 representation; production checks the same representation, rather than JS object order. Private provenance never enters the public projection.

`release_publish` is server-only and has no raw table grants. Anon and authenticated roles can only call the sanitized `release_public_feed`. The RPC projects an allowlist, excludes pending records and internal notes, and supplies trusted `serverNow`. Publication timestamps are assigned independently by each environment's database clock, once. Content/version/digest remain identical across promotion. Coming Soon remains a separate editorial contract; the release allocator does not create or promote targets.

## Reconciliation and deployment gates

`Publish accepted task releases` wakes on stg/main pushes, full CI completion, deployment-status events and hourly reconciliation. Events are wake-ups, never proof of deployment or a source of executable refs. It checks out protected branch tips only, verifies repository/environment/project refs, fetches actual protected refs and rejects stale runs. Concurrency reduces overlap, but database locking and keys enforce correctness. Artifacts are diagnostic only; durable progress is in SAS and append-only Git fragments.

Staging replays every unprocessed first-parent commit after the database cursor in branch order, validating each merge's delta and fragments. Cancelled/pending Actions runs cannot drop a merge. A rollback or divergent cursor fails closed. First deploy the fix through the normal branch process; never reset the release cursor, delete manifests or recycle versions. Old commits without fragments must be behind the explicitly verified activation anchor, not silently accepted or retroactively converted from raw commits.

The existing CI workflow also runs reconciliation after its full verify job on trusted branch pushes, with bounded readiness retries. This works when the feature first lands on stg, before the separate event-retry workflow reaches the default branch. GitHub schedule/workflow_run/deployment_status wake-ups require the workflow on the default branch; until that happens, later trusted pushes or rerunning the trusted CI job provide recovery. No default-branch merge is performed by this task.

After reservation, CI verifies the latest statuses/checks on the exact current deployment SHA, requiring full `verify` plus the explicitly configured provider contexts. Failed, missing, pending or unconfigured gates stop publication. It re-reads the live branch immediately before calling publication. A newer successful deployed descendant can make older pending manifests visible, because it contains their accepted changes. Verify provider contexts cover all affected deployed Suits and required migration readiness before activation. Rate-limit failures are failures, not a reason to bypass gates.

Production never allocates versions. It reads the accepted staging catalog using a server-only staging credential, selects manifests whose source commits are ancestors of main, verifies every post-anchor fragment matches its accepted staging copy, and requires staging publication. The production RPC imports in parent-cursor order, checks digests/unique versions and publishes the whole batch atomically after production readiness. Several staging releases can promote together. Missing staging manifests, changed copy, cherry-picked/non-ancestral sources, direct-main hotfixes and out-of-order imports fail explicitly. Hotfixes must merge to stg and deploy there first, then merge the corresponding stg ancestry to main. No guessing provenance from equivalent patch text or version recalculation.

## Verification and recovery

- `node --test tooling/releases/*.test.mjs packages/contracts/tests/bs-changelog-version-001-1.test.mjs`
- `node tooling/releases/catalog-disposable.mjs` creates and removes only its uniquely named local PostgreSQL test container. It tests a dedicated schema fixture plus this actual forward migration, concurrency/retries, duplicate/digest conflicts, wrong environment/ref, no-op internal changes, missing baselines, reordered delivery/imports, authorization denial, failed-transaction recovery, batch promotion and independent immutable timestamps.
- `pnpm check`, `pnpm test`, affected typecheck/lint/build checks and existing SAS disposable integration validate broader contracts. Generated public database types come from the local SAS migration chain, never manual type edits.

If deployment fails, leave reservations pending and fix/redeploy through the normal provider path. A subsequent trusted event/hourly reconciliation resumes with the same versions. If a single write fails, its transaction rolls back; retry the identical request. If the payload/digest differs under the same key, stop and inspect the accepted manifest and Git ancestry; never overwrite it. If main lacks accepted staging ancestry, correct the release branch through review instead of manufacturing provenance. No destructive cleanup or hosted reset is a recovery step.
