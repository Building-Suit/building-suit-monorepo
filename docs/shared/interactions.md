# Shared interaction policy

`packages/ux/src/index.ts` declares the record presentation policy. Add/edit records use `BsDialog`; product forms retain their validation and authorized commands. `useRecordAction` tracks create/edit mode, visibility, pending state, safe validation feedback and deterministic dirty snapshots, including Set/Map-based permission forms. Reset initial values before calling `create()`, `edit()` or the compatible `open(mode)` entry point. `run(command, describeError)` provides the standard guarded command lifecycle: it prevents duplicate submission, retains the modal with product-safe feedback on failure, and calls `complete()` after success. Existing product-owned command flows may set `pending` and call `complete()` directly.

`BsRecordActionDialog` composes `BsDialog`, `BsForm`, `BsFormActions` and `BsButton` into the canonical create/edit surface. It forwards the shared close callback to product fields, locks dismissal and submission while pending, links/focuses validation feedback through `BsForm`, and supplies localized cancel/save actions. Products provide fields, translated titles/errors and authorized commands; they do not create a second modal/action engine. Long editors can opt into `pinnedActions`: actions render in the non-scrolling shared dialog footer, while Save remains associated with the native form for validation. Custom action slots receive `formId` and must associate their submit controls with it. Pending state locks both the form and footer dismissal/submission. The default in-form action placement is unchanged.

`BsDataTable` is the entry point for ordinary record actions. Its typed capabilities decide whether shared create/edit/archive/delete/void affordances are present, and its events hand the selected record to the product adapter. Create/edit handlers initialize the product form and open `BsRecordActionDialog`; they do not render an editable record form at the authenticated page root. Destructive events use `useConfirmation` where the product semantics permit the action.

Table search, filter, sort and page changes flow through the optional product-owned `BsDataTableQueryAdapter`. `BsEntityPicker` follows the same boundary: it emits search and load-more intent while the product adapter owns asynchronous retrieval, authorization and cache scope. Neither component imports product data access.

`BsDialog` owns modal placement, focus trapping, focus return, Escape handling, scroll containment, pending-state close protection and dirty-close confirmation. Dirty-close Cancel receives focus immediately and remains PrimeVue's autofocus target if the opening transition finishes afterward. Product close/cancel buttons must use its scoped `close` callback. Direct state resets are reserved for successful completion, tenant/account changes and explicit workflow resets. Long forms may choose the shared size variants; they must not introduce a second overlay implementation.

`useConfirmation().ask(message, title?)` queues accessible confirmations through `BsConfirmHost`. The object form accepts translated `message`, `title`, `confirmLabel`, `cancelLabel` and a `default` or `danger` tone for consequential actions. Apps include one host at their root. Use it for archive, void, removal and similar actions; domain authorization and reversals remain server responsibilities. Cancel receives initial focus and queued requests resolve in order. Do not use native browser confirm dialogs.

`BsSignupWizard` and `useSignupWizard` own variable-length step presentation, shared back/submit controls, error/notice placement, navigation bounds and advance concurrency. Apps supply stable step descriptors, translated action labels, field slots, validation and provisioning calls. The shared `focusSignupStage` policy gives a newly entered step initial focus only when the user has not already focused a control inside it; animation completion must not interrupt ongoing input. `BsVerificationForm` owns the accessible OTP, countdown, resend, feedback and pending presentation, while `useVerificationTimer` owns its expiry/resend clock and safe restore/reset mechanics. The server remains authoritative for validity and rate limits. Never persist passwords or OTPs in draft storage.

Messages sent to `useToasts` are already translated. Display safe product/domain error messages; do not expose raw SQL, credentials or infrastructure errors. Loading, empty, denied, error and successful states are part of each page's contract.

`BsButton` composes PrimeVue Button with canonical default/primary/secondary/accent/danger variants plus chrome-free `text`, `link`, `icon`, `tab`, `chip`, and `tile` presentations. Semantic variants do not inherit `ls-btn`; their padding, wrapping, border, and active geometry are owned centrally. Its default type is `button`; form submissions explicitly set `submit`. `BsForm` retains native validation, provides a focusable linked error summary, announces pending saves and locks its fieldset while pending. Its class applies to the fieldset for grid/spacing composition. Products own error copy and submit handlers. `BsSelect` composes PrimeVue Select with translated filter/empty states and optional fixed-row virtualization; labels are required and native events/slots are forwarded. Product adapters own lazy queries. Native semantic controls may exist inside shared Bs component implementations, but Suit templates consume only Bs-prefixed renderable components under the zero-native boundary.

`BsField` and the field-group/section contracts own accessible label, description, help, error and required relationships. Checkbox, radio, switch, file and OTP semantics are implemented by their shared Bs controls; products do not recreate native labels or control styling. `BsSearchField`, `BsDateRangeFilter` and `BsFilterBar` are explicitly non-mutating controls for search, filters and report parameters. They do not open a record-action dialog and must not be used as an alternative mutation surface.

`BsQuantityStepper` uses the generic bounded/stepped quantity helpers; products supply their valid range. Zero is an emitted intent and the owning cart decides whether it means removal. Fractional manual input is retained, incomplete input restores its controlled value on blur, and touch buttons meet the shared target minimum. Product stock rules remain in Shop helpers and the server remains authoritative. `focusAfterRecordRemoval` restores a neighboring control or the collection heading after controlled removal.

`useViewportSpace` measures a local panel's available viewport space and disposes its observer/listeners on scope teardown; it has no shared SSR state. `usePointOfSaleSections` owns the small-screen catalog/cart selection and waits for rendering before focus restoration. The Shop cart confines scrolling to its line list at ordinary viewports; very short viewports use document flow to avoid clipping until the pending short-height reference is resolved.

`useNavigationChamber` owns the common app/settings chamber state using caller-supplied destinations. It normalizes query/hash suffixes, matches complete route segments and restores the route-appropriate chamber when the route or destinations change. State is instance-scoped and watchers follow the owning Vue scope. `useCollapsibleNavigation`, `useWorkspaceNavigation` and `useSideNavigation` continue to own collapse, route dismissal, Escape/Tab handling and focus return. All Suit workspaces use these controls through the canonical rail shell; the `shop` visual fork is removed, while catalogue filters remain opt-in. Account actions move with their existing labels/authorization projections, and workspace/scope/notification/trial commands remain on the page action row.
