# Building Suit design system

`packages/design-tokens/tokens.json` is the editable token source. It combines Building Suit's brand foundations with the latest Ledger Suit application palette, promoted to the shared system by [ADR 0003](../architecture/decisions/0003-ledger-neutral-palette.md). `pnpm tokens:generate` produces CSS variables, TypeScript and Tailwind color references. `pnpm tokens:check` detects drift. The preserved original token files in the documentation archive describe provenance and are not runtime imports.

All apps share Ledger's neutral surfaces: near-white/paper in light mode and ink/charcoal/graphite in dark mode. Building Navy and Premium Gold remain the brand/action colors; navy still appears in marketing and auth showcases. Hover, pressed, focus, text, border and overlay roles are canonical too, including the system-preference dark theme. These are shared tokens, not product CSS overrides. Semantic status colors, Manrope for Latin (the installed variable face is named `Manrope Variable`, which must lead the canonical font-family token), IBM Plex Sans Arabic for Arabic and Hugeicons Stroke Rounded remain the shared foundations. Logos and app icons are served from `packages/brand/assets`; Ledger Suit and Shop Suit each provide canonical mark and wordmark assets in light and dark variants.

The application language uses 10px controls, 14px content containers and 20px overlays. Ordinary cards receive only a hairline border and near-flat elevation; menus, dialogs and other temporary surfaces own the stronger shadows. Nested content uses `ls-card-flat` so page composition does not become stacks of floating cards. Marketing may be more expressive, but product screens retain the same semantic roles and restrained gold accents.

Use semantic `--bs-*` roles for application UI. Raw neutral and gray aliases support intentionally dark previews; navy/gold primitives support brand areas. Future apps inherit the same palette through the shared Nuxt layer.

Focus uses Building Navy in light mode and Highlight Gold in dark mode. These canonical roles exceed 3:1 against their control surfaces; light-mode Premium Gold did not. Always-dark brand panels retain the dark focus role in either theme. Feedback text uses the normal foreground when a semantic status color would have insufficient text contrast, while status borders/backgrounds and explicit wording preserve meaning.

The shared Nuxt layer registers fonts, tokens, styles, components, composables, theme behavior and public brand assets. Product apps register Supabase and supply their own locale messages, content, routes and business logic.

Atomic Design organizes `packages/ui/src`: atoms (icons, brand marks, status), molecules (fields, empty states, KPI presentation), organisms (tables, dialogs, wizard, settings and feedback), templates (complete page compositions, marketing/auth frames and authenticated shells). Product pages delegate to one canonical page template and own validation, currencies, roles, queries and commands. Atomic Design does not define database or business-service boundaries.

Canonical working surfaces are explicit contracts: `BsStatusBadge` accepts a written status plus an optional semantic tone; `BsCard` and `BsKpiCard` own ordinary card/KPI presentation; `BsPageHeader` receives product-built context items; and `BsTableDensity` receives translated labels and a compact/comfortable value. `BsPublicLegalPage` owns the shared legal-document layout while product adapters retain metadata, translated update labels and legal content. These components consume existing semantic tokens and do not create another editable visual system.

Suit structure and content use the semantic primitive layer rather than native tags or visual classes. `BsAppRoot` uses committed router context for default auth motion. Keyed session layouts own replacement and do not nest an implicit page transition; explicit product transitions remain supported. `BsAppRoot` owns Nuxt layout/page composition. The shared Nuxt-layer `BsRouteLayout` adapter wraps route-owned slot content in a named Nuxt layout when authorization selects that layout after session resolution; it does not own product authorization. `BsPage`, `BsPageBody`, `BsContainer`, `BsStack`, `BsInline` and `BsGrid` own responsive layout. `BsText`, `BsHeading`, `BsLink`, `BsIcon`, `BsImage`, `BsDivider`, list/description/disclosure/code primitives and `BsVisuallyHidden` own content semantics. `BsBox` is the deliberate escape valve for ordinary structural semantics: its `as` option is restricted to `div`, `main`, `section`, `article`, `header`, `footer`, `nav` and `aside`, while role, surface, padding, radius, scroll and sticky behavior remain typed. It does not expose a class/style customization contract.

`BsSurface`, `BsPanel`, `BsContentSection`, `BsActionTile` and `BsInteractiveCard` provide composed surfaces. Action tiles and interactive cards own link/button focus and interaction without inheriting ordinary button chrome. `BsAlert` and `BsStateSurface` cover information, success, warning, error, permission and read-only presentation. Product adapters provide content, routes, status values and authorization results; the primitives contain no product rules.

Data-heavy worklists use `BsDataTable` with typed Bs-owned column schemas and constrained domain-cell slots. `BsTableToolbar`, `BsTableSearch`, `BsTableFilters` and `BsTableActions` own its surrounding controls; consumers do not render vendor columns or provide presentation classes. `BsDescriptionList`, `BsHistoryList`/`BsTimeline`, `BsDetailSection`/`BsDetailDialog`, `BsTagEditor` and `BsEntityPicker` own recurring cross-product data presentation while product adapters retain queries, authorization and domain formatting.

The reusable composition inventory also includes `BsInput`, `BsTextarea`, `BsSelect`, `BsCheckbox`, `BsRadio`, `BsSwitch`, `BsFileInput` and `BsOtpInput` for native control semantics behind the Bs boundary. `BsField`, `BsFieldGroup`, `BsFormSection`, `BsChoiceGroup`, `BsForm` and `BsFormActions` own labels, descriptions, help, errors, required state, grouping, pending/disabled behavior and action placement. `BsSearchField`, `BsDateRangeFilter` and `BsFilterBar` cover non-mutating search, filter and report parameters without presenting them as CRUD forms. `BsTabs`, `BsToolbar`, `BsPagination` and `BsMenu` cover ordinary navigation and page tools; `BsSectionHeader`, `BsContentSection` and `BsStateSurface` cover responsive page structure and loading, empty, error, denied and success states. Products supply translated labels, values, permissions and handlers. They do not repeat the controls' border, radius, surface, spacing or state recipes.

Composition is downward-only: a shared layer may use its own layer or a lower layer, never a higher one. Every shared UI source is exported explicitly by `packages/ui`; wildcard exports are not permitted. The [shared UI ownership contract](ui-ownership.md) and its canonical manifest require zero local visual components, complete page-template mappings and zero migration debt.

The shared system supplies the layout composition for product applications: landing hero/features/workflow/pricing, login/signup split frame, shared navigation rail, collapsible chamber and content shell. `BsMarketingLayout` composes `BsLandingTopHeader` and `BsLandingFooter`; `BsLandingPage` composes the hero, product-preview frame, section rhythm, feature grid and workflow steps. `BsMarketingPricing` composes the Ledger-derived billing toggle, plan grid/cards, feature lists, resource limits, status banners and CTA placement. `BsContactPage`, `BsSupportRequestForm` and `BsContactInfoGrid` own public contact presentation, while legal route adapters consume `BsPublicLegalPage` directly. `BsAuthLayout` owns the responsive split geometry, `BsAuthForm` owns the canonical auth card/header/action shell, and `BsSignupWizard`, `BsVerificationForm` and `BsOtpInput` own signup and verification presentation. `BsAppShell` composes the canonical `BsSideMenu` rail/chamber for every Suit, without a standalone top header; context controls remain in the page action row. The legacy `shop` flag enables only catalogue navigation filters, not a separate visual shell. `BsTopHeader` remains an exported compatibility component but is not mounted by workspace shells; `BsUserMenu` owns account identity, product-supplied route actions, the shared language/theme settings, and sign-out ordering/behavior. `BsContextSwitcher`, `BsScopeSwitcher`, `BsNotificationMenu`, `BsTrialCountdown`, `BsReadOnlyBanner` and `BsAccessGate` own the common authenticated chrome states. App adapters provide navigation, content, assets, identity values, typed plan/context/notification data and action handlers. Change shared layout code to change all consumers.

Landing motion is progressive enhancement owned by `packages/ux/src/composables/useLandingMotion.ts`. It dynamically loads GSAP and ScrollTrigger on the client, scopes selectors to the mounted landing root and reverts the context on unmount. The optional `BsShopLandingJourney` organism in `BsLandingPage` presents a single fictional transaction through one persistent POS screen, device/counter staging, actual checkout confirmation, user-initiated browser printing and operational records. All business copy, product samples, amounts and stock values are typed app projections; the scene executes no business commands. Its reversible scrubbed timeline uses logical cursor coordinates and a separate mobile camera composition. Reduced-motion preferences, short landscape viewports, unavailable JavaScript and chunk-load failures retain the complete illustrated narrative. Only a successfully installed timeline enables the attribute that visually hides this transcript; it remains in the accessibility tree. Marketing navigation, pricing and account links remain outside the demonstration's inert UI. The Shop stage fills the available viewport below the measured marketing toolbar without a height cap; its laptop stays visible beside the closing caption. The Shop logo loader is rendered in the initial server HTML, with critical styles and a high-priority logo preload in the head. It hides page content from first paint and remains in place through hydration, waiting for window load, fonts, decoded page images (including lazy logo variants) and the GSAP chunk before enabling the journey. A head-level noscript style removes the loader and restores readable content when JavaScript is disabled. It restores scroll/focus state on completion or navigation; its explicit continue action opens the readable static presentation if an asset stalls. No-script pages never render a blocking loader.

The `/components` route in the documentation app is the live catalogue. Check English/Arabic, LTR/RTL, light/dark, narrow screens, keyboard navigation and focus whenever changing shared components.

The remaining workflow families are documented in [workflow presentation](workflow-presentation.md): exact money, usage meters, setup, imports, teams, reviews, metric charts, hierarchy/flow, repeating rows and printable documents. Their typed inputs preserve product ownership of policy, calculations and commands.

`BsAdministrationShell` is the shared two-chamber administration template (BS-SA-UI-R001). Its explicit `@building-suit/ux` types describe Suit rail entries, grouped context navigation and translated labels. Apps provide icons/logos, optional context routes and controlled `selectedSuit`/`selectedContext` values; selection emits updates and typed intent events without querying registries, choosing tenants or granting authority. Stable IDs must be unique within each collection. Logos are decorative alongside accessible labels. The administration template delegates its frame, responsive drawer, collapse control and theme/language controls to the same `BsAppShell` as every workspace. Active Suit buttons expose `aria-pressed`; context actions expose `aria-pressed`, and routed links expose `aria-current=page`. Registry data, disabled state and selection commands remain caller-owned.

Desktop rails and navigation chambers retain their working-space geometry when expanded or collapsed. Below 64rem, every workspace uses the shared off-canvas navigation, scrim, Escape/Tab handling and focus return. Shell IDs come from SSR-safe `useId`, so an embedded catalogue example does not duplicate its outer shell IDs. Context activation closes the drawer. Optional context tools, working content, rail entries and overlays remain shared-template slots; Suit routes supply no slot composition. The catalogue provides normal, loading, empty and long/overflow examples. These changes require rendered verification in EN/AR, both themes and desktop/mobile; no visual acceptance is implied by source implementation.

Future Suit administration extensions use the [typed registration contract](future-suit-administration.md). `administrationShellRegistration` maps identity and capability-gated context data to the existing shell inputs; descriptors and product adapters register support without changing shared shell conditionals.

Workspace panels use the canonical card surface, border, radius, elevation and padding scale. `BsAccessTabs` delegates to `BsTabs`, including counts and keyboard navigation, so access-management tabs use the same horizontal presentation as other workspaces. Product adapters explicitly provide home destinations when their dashboard differs from `/dashboard`.

`BsCard` supports the same responsive `span` contract as shared layout primitives. Dashboard charts and onboarding cards use it to occupy their intended grid tracks; the span resets on narrow screens.

`BsDashboardMetric` renders product-formatted KPI values with consistent title/value/hint structure and preserves source navigation as semantic events. Its 144px minimum height and 20px padding are canonical component tokens, matching the approved Shop dashboard specimen. Values use the existing h2 type scale; cards grow for translated or longer content. The complete financial notice remains product-owned and visible beside the metric grid.

Shop public/auth frames explicitly opt into `presentation: flat` through product configuration. The shared `BsAuthLayout`/`BsProductAuthFrame`/`BsSignInPage` default remains unchanged for other Suits. Flat form surfaces use canonical background/border/card-radius, no elevation, and h2 heading tokens; showcase titles use the display tokens. `BsPublicLegalPage` supports the same optional flat presentation for canonical display/h2 headings and a flat content surface. Content, account/session behavior and legal policy remain product-owned. The component catalogue describes this opt-in; native variant and missing-reference comparisons remain separate acceptance work.


### Account lifecycle page templates

`BsAccountActivationPage`, `BsAccountProvisioningPage` and `BsOwnerInvitationPage`
are explicitly exported complete page templates. Their finite content maps and
named typed view models contain only projected labels, state and capabilities.
Controlled field models and semantic events return changes to the owning app;
the templates do not call Auth, select tenants or calculate plan entitlements.
The activation page shows original trial history and actual grant/audit dates.
Provisioning distinguishes active access, invitation acceptance and owner email
verification; a separate resend requires acknowledgment. The owner template
shows password fields only after the app verifies target ownership.
The documentation `/components` page includes their contracts and an inert
unavailable-invitation preview.

Shop pricing cards share the canonical 352px maximum track in marketing and billing, shrinking to the available width on narrow screens. Only a product-designated promoted plan receives marketing emphasis; current/selected subscription state does not move it. Current paid plans expose a disabled Selected action. Capacity restrictions remain product-owned and appear in checkout rather than on each billing card.

`BsHostedCheckoutDialog` composes the shared record-action dialog with pinned payment/cancel actions, provider branding, a typed quote, consequences, restrictions, status/recovery and policy links. It performs no payment arithmetic or provider calls. `BsBillingPage` exposes controlled `checkoutVisible`; products open it on an explicit plan choice, while interval preview changes preserve the current interaction. The catalogue provides an unavailable checkout example.

Shared workspace chrome (`SHARED-WORKSPACE-CHROME-20261019`) is now the default for Ledger, Shop, Inventory, Automation, Doctor default/practice and Shop platform-administration layouts through `BsWorkspaceShell`. Super Admin retains its database-driven registry through `BsControlPlaneShell` → `BsAdministrationShell` → `BsAppShell`. Account/sign-out stays in the rail; supplied account/settings routes stay reachable in the settings chamber. Workspace selection/creation, scope switches, trial countdowns and notifications remain controlled product projections in the inline page tools. Empty/limited products do not receive invented navigation or capabilities. Public marketing/auth shells are unaffected. Local source review only: rendered states and local checks were not run at the owner's instruction.
