## Reproduce and preserve ownership

Prerequisites: pinned Node/pnpm dependencies, local Docker socket, Python 3 for safe tar inspection, and the pinned native image cache described in [native verification](../../native-financial-verification.md). The new image helper additionally pins Kong 2.8.1, Mailpit 1.30.2 and official PostgREST 16.1. No provider filesystem or SQL schema shim is introduced.

Prepare each `source`/`target` profile with `scripts/prepare-native-recovery-project.mjs`. Source copies the complete current migrations; target intentionally initializes only pristine provider schemas, with no application migrations before restoration. Both disable development seeds. `native-recovery-runtime.mjs <source|target> <start|stop>` requires `LEDGER_RECOVERY_DISPOSABLE_TEST=1`, checks fixed local IDs/ports/workdirs and guards retained volumes against adoption from an older task. Stop preserves volumes/backups. Runtime signing keys and fixture passwords are generated in ignored private files, never passed in command arguments or published.

For this managed environment, run `prepare-native-recovery-network.mjs` to add only the exact owned local service DNS names to Docker's proxy exclusions, preserving external proxies and all credential/config entries. Alpine `wget` still sends localhost health checks through the proxy. The runtime therefore checks all three real gateway endpoints for HTTP 200 after CLI startup; CLI exit alone is never readiness evidence. The actual Auth/Storage workflows independently verify operation.

Execute the stages in order, once in fresh owned projects:

1. Start source. `seed-native-recovery-source.mjs` performs real email verification and commits the checked financial/configuration/import/reversal/file fixture. For a fresh source it invokes the existing native Storage admission regression with private environment bindings to add the second tenant's three verified files. An existing complete fixture is verified without creating another tenant; incomplete/unexpected fixtures stop for inspection. No raw key belongs in shell history or logs.
2. `capture-native-recovery-source.mjs` captures actual API exports, private files, read-only SQL evidence, source object inventory and application-owned Auth/Storage customizations. New captures use distinct paths; prior exports are not overwritten.
3. `backup-native-recovery-source.mjs` freezes only owned gateway/Auth/REST/Storage/SMTP services. The database remains online for the official CLI roles/schema/data and explicit migration-history schema/data dumps. A separate Docker file-backend archive preserves the complete owned Storage volume. All artifacts are private and hashed.
4. Stop source with preservation, then start fresh target. `restore-native-recovery-target.mjs` refuses an existing application schema/users/objects, restores SQL in one transaction, copies the separate Storage archive and verifies exact object metadata/files before restarting providers. It uses the existing native `supabase_admin` operator only for the provider grants present in `roles.sql`; no application role is elevated. App-owned Storage policies use a pinned namespace context, and Auth triggers are recreated explicitly. Provider-managed schemas and provider migration histories remain initialized by their actual services.
5. `audit-native-recovery-copy.mjs` checks the complete restored application/Auth/Storage COPY values **before post-restore user traffic**. `verify-native-recovery-target.mjs` then verifies actual sign-in, exports/files, the six-artifact comparison, cross-project/tenant denials, corruption rejection and rolled-back posting/numbering continuity.

The native file backend and its tenant/path configuration are checked explicitly. This is a local Docker volume recovery procedure, not a claim of hosted S3 restoration. Keep source/target volumes and private backup material until reviewed; rerunning restore over the recovered target is rejected. The rejected SQL attempts exposed two distinct issues and rolled back safely: a provider parameter grant required the existing native administrator, and a deparsed Storage policy needed its explicit namespace binding. The corrected run preserved every required record without dropping or skipping controls.
