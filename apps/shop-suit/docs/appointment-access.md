# Appointment access foundation

SS-WEB-APPT-ACCESS-001 adds credential issuance and narrowly scoped sessions. It does not implement CUSTOMER-PORTAL, public booking, delivery integration, customer Auth accounts or subscription policy. No existing appointment receives a credential automatically. No customer is messaged.

## Staff commands and identity

The existing `appointments.manage` capability plus access to the appointment's actual location authorizes `appointment_access_status`, `appointment_access_issue` and `appointment_access_revoke`. Writes lock the shop and recheck authority; issuance also locks the appointment and a saved customer's phone source. There is no new billing or subscription gate. Staff use the optional controlled access dialog inside the registered shared appointments template. Issuance/rotation shows a code once; closing, leaving, changing tenant/location/account, or losing capability clears it. It never enters Nuxt shared state, storage, URLs, toasts, analytics or audit snapshots. Delivery remains manual through an already agreed channel.

Twelve independent unbiased Crockford-alphabet symbols provide 60 bits of cryptographic entropy. Display groups are four characters, separated with hyphens. Codes are random, never derived from appointment IDs or counters. Global unique hashes prevent lifetime reuse; issuance retries collisions at most five times, with atomic rollback preserving the old credential if generation fails. Issuance always replaces prior access and revokes its sessions. Plain codes are not recoverable later; staff explicitly rotate lost codes.

Phone normalization removes accepted display punctuation, accepts Arabic/Persian digits and treats an international `00` prefix like `+`. It requires 7–15 digits and does not infer a country or equate a national number with an unspecified country code. Verification must match the phone actually saved on the linked active customer, or the walk-in appointment. Unusable/missing phones cannot enable access. Phone or customer-identity changes permanently revoke affected credentials/sessions; restoring a former phone does not resurrect access. Ordinary name/notes/schedule edits do not rotate credentials.

## Public verification and sessions

All public operations use POST JSON under `/api/website/appointment-access/{verify,validate,rotate,logout}` on a currently published tenant host. Trusted Host selects the shop. Neither body shop IDs nor forwarded host/tenant headers select scope. Same-origin requests are required; JSON is bounded to 2048 bytes. Verification accepts only `code` and `phone`; the other commands accept an empty object. Credentials never go in URL parameters. The anonymous backend client forwards no product session or incoming JWT.

`appointment_access_verify` returns an identical `{ok:false}` for mismatch, missing/malformed factors, unknown/unpublished shop, revoked identity, quota failure and internal failure. It requires both normalized code and phone; neither factor alone exposes any customer/appointment data. Database quotas remain authoritative for direct RPC callers: 100 attempts/shop, five/code and ten/normalized phone per ten-minute window. Failed attempts commit counters rather than raising exceptions that roll back throttling. Unknown shops create no rate rows, known-shop bucket cardinality is bounded by its quota, and expired counters are pruned. The HTTP adapter adds a bounded per-process limit of twenty attempts per socket/shop per ten minutes; it does not trust forwarded IP headers. Logout remains available after that client limit.

Successful verification creates an independent random 256-bit token with an absolute ten-minute expiry. Only its hash is stored. The HTTP adapter places it in a Secure, HttpOnly, SameSite=Strict, host-only cookie scoped to `/api/website`. JSON responses return only success and expiry. Public pages strip all cookies; the four access APIs capture only this exact capability before discarding incoming private cookies/JWTs. Response cookie filtering permits only this API's own capability cookie. Responses remain private/no-store/noindex.

Each session refers to exactly one credential generation. A saved-customer credential grants an internal scope of one shop plus one saved customer; a walk-in credential grants one shop plus one appointment. The non-exposed `shop_private.appointment_access_scope` boundary rechecks shop publication, active identity/phone, credential revocation and absolute session expiry on every use. Future CUSTOMER-PORTAL RPCs must use it within their own explicit allowlisted projection. The current public validation endpoint returns only validity and expiry, with no customer identifiers, appointment history, financials, contact records or private notes.

Session rotation changes the bearer token atomically, invalidates the old token and retains the original expiry. It cannot extend the session lifetime. Logout revokes the matching token even when its shop is unpublished or it has expired; misses return generic success. Staff revocation invalidates all generations/sessions for that appointment. Database errors return generic failure without secret-bearing exception messages.

## Storage, audit and verification

Credential, session, quota and audit tables have RLS and no direct grants to anon, authenticated or service roles. Security-definer public entry points have explicit grants and empty search paths; private helpers are not exposed. Credentials never become columns on appointments, preserving the original audit snapshot contract. Audit records contain action, actor/record identifiers and time, never raw code, token, phone or payload/error dumps. No new logger is introduced.

The disposable runner `tooling/database/test-shop-appointment-access-local.mjs` first runs the complete existing appointment SQL regression, then the exact task obligation SQL. Synthetic fixtures cover 10,000 actual generated codes, forced collision retry/failure rollback, both identity scopes, permission/cross-shop denial, quota durability and expiry, rotation/revocation, permanent phone-change revocation, unpublish and secret-free audit. All fixtures roll back. Three exact obligation unit files cover syntax, theoretical entropy, normalization, strict adapters and the socket limiter. Built-server tests verify Host selection, transport/cookie scope, uniform failures and no response/log secret leakage. EN/AR browser cases verify one-time display, rotation/revocation, missing-phone gating, view-only denial and absence of storage/Nuxt-state caching. The GitHub disposable provider workflow applies the full forward migration chain and runs the SQL/API/browser regressions. Hosted schema changes remain CI-only.
