# Public Shop profile — SS-WEB-PROFILE-001

The existing business settings page includes a separate public-profile draft. Saving a website address first establishes its canonical URL; the SLUG task owns permanent aliases and host isolation. No existing Shop is opted in, backfilled or published by this migration.

Public name, description, phone, WhatsApp, email, opening hours and search title/description are independent from operational/account/receipt data. Location identifiers select only this Shop's active locations; visibility starts false and public names/addresses must be entered explicitly. No operational values are copied. Draft save tolerates incomplete profiles; publishing requires a logo, public name, description, one public contact and one explicitly visible active location with public name/address.

Publishing also requires an explicit current owner confirmation and at least one published product/service. The product-owned `PublishedItemReadiness` contract maps to `shop_private.website_catalog_readiness(uuid)`. Its implementation is intentionally `{ integration: 'pending', publishedItemCount: 0 }` until CATALOG supplies an authorized persisted publication model. Client-supplied counts/unknown profile keys are rejected. Operational catalog rows do not count. No catalog feature or customer publication is implemented here; wildcard hosts keep the SLUG task's fail-closed 404 boundary.

Draft configuration, a published snapshot and private logo assets have separate storage. The publish command copies an explicit snapshot; later draft edits/logo replacements cannot change it. The uncached `shop_website_public_profile` projection exposes only explicit published fields, hides operational identifiers/invisible locations, and rechecks live Shop/location/catalog readiness. The canonical slug always comes from the existing URL authority. This projection is a contract for the later public rendering integration, not a new private-route bypass.

Unpublish clears the public snapshot/opt-in and returns to draft immediately, retaining draft configuration, logo and permanent URL claims. It uses settings authorization without the paid-write gate so subscription expiry cannot trap an owner in publication. Suspension cannot be undone by unpublishing or publishing.

Logo files accept raster PNG/JPEG/WebP up to 128 KiB and 2048 pixels per dimension. The shared UX picker verifies MIME/signature, decodes and re-encodes to PNG to discard metadata and trailing content. The authorized database command independently checks bounded bytes, format headers/end markers and dimensions, rejecting SVG and MIME spoofing. Logos are stored inline in a dedicated private RLS table because these small bounded assets need no public/signed Storage URL. Read/replacement/removal always resolve the Shop through permission-checked RPCs, accept no foreign asset ID and serialize on the Shop row. A published snapshot contains its own immutable logo value. No public bucket, URL-fetching upload, service key or provider setting is introduced.

All profile/asset/publication writes record actor, Shop, action and time in a private audit table. Browser roles have no direct table access; RPC writes use the existing tenant, membership, subscription and permission checks. Private reads require `settings.manage`; only owners may opt into publishing. UI pending/dirty/focus behavior uses the existing shared record-action controller. Environment/portal/user/Shop cache keys and task-scope guards prevent late results crossing account/tenant/location changes.

Migrations are forward-only and deploy through CI. No hosted writes, manual deployments or actual publication are part of this task. CATALOG and eventual public rendering must preserve the readiness and snapshot contracts and add their own integration tests before enabling publication.
