# Invoice-linked partial returns

Building Suit chooses to reduce the original invoice’s outstanding debt before creating refund obligations: debt reduction = min(return value, current due), refund due = max(return value − current due, 0), new due = max(current due − return value, 0). A 100 sale with 40 paid and 60 due, returned value 80, leaves zero due and a 20 refund obligation. This is our product choice, not a universal market policy.

Only issued, original-invoice-linked line/quantity returns are supported. Manager identity (owner or system manager), `sales.issue`, `payments.refund`, subscription/write access, tenant and location authorization are checked on the server. New internal tables have RLS, no direct browser/service table grants and append-only history. Existing invoice, receipt, payment and commission snapshots are preserved. Original payment adjustments cannot overlap an invoice with partial returns; full corrections cannot run after partial returns.

Returns use original tax snapshots and their immutable line price, discount allocation and tax components. Each return is the difference between cumulative original-snapshot amounts, conserving every original minor unit on a full return. Forward issuance now freezes explicit disabled-calculation evidence in `sale_return_sources` without changing tax/ETA behavior. Historical records without sufficient original tax evidence are unavailable; absence is never interpreted as a zero rate. No historical backfill or catalog repricing occurs. Quantities must be representable at 0.01; unsupported historical precision is rejected.

Financial and physical changes commit together. Resellable products restore the original FIFO batch and unit cost; damaged returns consume their original returnable FIFO allocation without adding sellable stock. Both dispositions reduce remaining returnable quantity. Service refunds never restore consumed materials. Unperformed returned service quantities cannot subsequently be fulfilled or linked to already performed work. Original earned pre-tax commissions receive cumulative reversals; full cancellation cannot generate earnings or leave a duplicate reversal. Remaining fulfilled work may earn only its retained original basis. Commission events remain separate from wages and exports.

Refund obligations reserve original receipt allocation capacity immediately. Pending, failed and completed reservations all count, alongside previous payment adjustments. The deterministic proposed allocation visits original payments in `paid_at`, payment ID, allocation ID order, taking up to each allocation’s remaining capacity. The user reviews that complete plan; the command locks the invoice/allocations and revalidates the exact plan. Concurrent quantity/capacity changes require a fresh preview. Original tender and currency are fixed; no wallet credits, exchanges, goodwill, no-receipt returns, fees, cross-currency changes, unlinked payouts or over-refunds are introduced.

Creating a return does not move money. `external_record` records evidence that a refund was completed outside this application and requires a reference. It never calls a payment provider, including XPay SaaS billing. `cash_handover` records actual handover from the current open main cash shift; its lock prevents a concurrent shift closure from omitting the outflow. Noncash refunds cannot be converted to cash. `failed` appends a failed attempt and retains the obligation; retry completes the same reservation. Completed reservations cannot complete again. Events use the current correction/handover time and open period; old cash days are never rewritten. There is no external effect requiring an outbox in this slice because no external transfer is performed.

The shared `BsDocumentReturns` organism is embedded by `BsCommerceDocumentPage`. Shared `useReviewedCommand` invalidates stale previews and retains the exact request/payload after an uncertain response. Shop supplies authorized adapters and translated Arabic/English content. Return/refund writes require connection. They are not added to an offline queue or reported as successful locally; existing offline counter replay/reconciliation remains unchanged. An uncertain request is retried with the same identity and reconciled through authoritative history. On a fresh page load, history must load before a new review. Failed/pending refund obligations remain visible. Original documents remain available unchanged.

Both return read APIs require `sales.view`, `payments.view` (the existing `payment_access.can_view` boundary), and access to the requested location before returning any document or context. A member with sales visibility but no payment visibility can still read the ordinary sale with its existing payment redaction; return history and refund identifiers, tender amounts and references are denied. Manager capabilities do not bypass location scope.

## Stable API / ETA handoff

- `sale_return_context(shop, location, invoice, offset=0)` returns capability, supported-original status, due, original lines and remaining quantities, and 50 return records per history page with `totalCount`.
- `preview_sale_return(shop, location, invoice, lines)` returns version 1, original currency, frozen line deltas, cumulative quantities, total/net/tax, dueBefore, debtReduction, refundDue, dueAfter and original-payment allocations.
- `create_sale_return(request, shop, location, invoice, lines, reason, expectedPlan)` returns a stable UUID. `lines` is `[{lineId, quantity, disposition:'resellable'|'damaged'|'service'}]`. Same request and payload replay returns the original UUID; a conflicting payload is rejected. The full reviewed plan is required, never a client-computed amount.
- `get_sale_return(shop, location, returnId)` returns version 1, immutable header and original-document reference, frozen line components (`original_snapshot`), physical FIFO allocations, reserved refunds and append-only events. `original_document` contains `invoiceId`, `invoiceNumber`, `issuedAt`, `receiptId` (the receipt table’s invoice primary key, nullable for unpaid originals) and `etaSourceAvailable`. Original tax classifications/rates and discount allocations remain in each line’s `original_snapshot`. `created_at` dates the correction, not the original sale.
- `record_sale_return_refund(request, shop, location, refundId, operation, reference, reason)` accepts `external_record`, `cash_handover` or `failed`. Its request identity and immutable completion event are separate from the return identity. Same request/payload replay returns the original event UUID. Completed state means completion evidence recorded; it is not a provider execution acknowledgement.

Operational record state is append-only: pending reservation → failed attempt(s) → completion recorded. Failed attempts do not release money owed or original-payment capacity. Refund audit state is independent of stock disposition and ETA submission. The ETA owner may use the immutable return UUID and original invoice reference to build a return document; this feature neither queues nor submits tax documents. Existing provider/GitHub integration owns migration deployment. Parent owns staging merge. Manual testing follows staging and is not a pre-merge gate here.

Primary context reviewed 2026-10-15: [Square refund API](https://developer.squareup.com/reference/square/refunds-api/refund-payment) describes partial linked refunds, idempotency and original-payment capacity; [Shopify refund guidance](https://help.shopify.com/en/manual/fulfillment/managing-orders/refunding-orders) describes partial quantities, independent restocking and original tenders. Debt-first settlement, reservation retention and FIFO disposition policies above are Building Suit choices.
