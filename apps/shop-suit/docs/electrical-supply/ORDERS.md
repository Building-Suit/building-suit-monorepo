# Customer orders and fulfillment

Accepted quotations convert once into location-scoped customer orders. The order stores the exact accepted quotation/version, names, measurements, prices, discounts, tax rules and rounded money. Later catalog or tax-policy changes never reprice the agreement. The source quotation remains immutable history and cannot be cancelled/revised independently after conversion. Independent repeated conversion requests return the existing order, including after a lost response; actor-bound identical-request retries return the original result.

An offer accepted within its validity becomes an agreement: its earlier offer deadline does not silently revoke acceptance. Currency or product stock-unit/revision changes block initial conversion and require a fresh reviewed agreement. Creation requires existing sales-management authority, an active write subscription and location access. Customer/product/service tenant ownership is checked on the server. Direct client table writes and unbounded table reads are denied; directory/history queries are bounded and location-authorized.

Creating an order creates no invoice, payment, debt, batch, movement or stock reservation. Reservation commands explicitly create separate stock holds. Deposits use existing payment receipts and allocations; collection commands issue normal sales invoices. Existing financial and FIFO ledgers remain their implementation authority; no competing payment ledger is permitted.

Commercial money read projections use exact decimal strings and the maintained shared money formatter. Current and historical quotation snapshots and order headers retain large cents that JavaScript numbers cannot carry; stored historical JSONB is preserved. The forward migration checks the exact prior quotation-reader body before replacing its read projection. Line unit prices retain all12 decimal places. Open quotation editors retain the revision they opened with; background refreshes cannot silently advance their write token.

Local conversion qualification:111 actual migrations replay, quotation/order public-command cases, both merchant journeys and both real-session stock races pass in the owned PostgreSQL fixture with explicit provider stand-ins. Cases cover frozen price/name/tax/quantity, accepted-only conversion, same/different-request deduplication, post-conversion quote protection, dimension/currency changes, outsider/direct-table denial and exact large cents through history. Both English/light desktop and Arabic/dark mobile conversion/lost-response browser journeys pass. Shop typecheck/build and strict ownership (118 templates) pass at the conversion checkpoint; later combined source, native Supabase, reservation races and merchant/device acceptance remain separate gates.

## Stock reservations

Authorized staff reserve exact canonical quantities against an open order, at its original location. Replacement is atomic across all supplied lines and releases prior holds only if the replacement succeeds. Repeated SKU lines share available capacity within the same command. Services have no inventory reservation. Measured product revisions and whole-package boundaries remain authoritative; physical allocations preserve the accepted continuous/split requirements and explicit cutting-loss budget. Holds reference actual FIFO batches and physical reels, retain expiry/actor/reason history and do not move stock or funds.

POS catalog and reel pickers expose free capacity, with separate on-hand and held values. Deferred capacity checks reject stock counts, supplier returns, scrap or other writes that invalidate a hold. Release/reduce a hold before removing its source stock. Expiry frees availability by server time even before an explicit history-cleanup command. Cancellation releases all remaining holds. Each mutation advances the order revision and invalidates inventory/POS scope through the existing realtime versions.

The editor captures its original revision. Uncertain command results retain frozen inputs and request identity; dismissal stays blocked while the same request can be retried. Shop/location/account changes clear private UI state. Server authorization remains independent of UI controls. The schema uses private helpers and bounded authorized readers; no raw reservation table is published to Realtime.


## Deposits and partial collections

Record advances before collection with the existing receipt authority. Receipts retain their original identity, method, reference, actor and effective date. Unapplied amounts can be refunded after an order is cancelled; corrections record mistaken receipts without claiming money was returned. Applied funds are adjusted through their original invoice allocation. The customer statement shows an advance once, with a link to its order. Applying it later transfers the allocation to the delivery invoice and never records a second cash receipt.

New advance capacity accounts for pending agreed goods, actual outstanding delivery invoices, ordinary payments, returns and unapplied advances. Refunding an applied invoice allocation does not replenish the original advance. Each command checks the location, actor, subscription, open accounting period, captured order revision and request identity. The receipt and history readers return exact decimal strings with bounded pagination and a searched outstanding-invoice picker.

Collect reserved goods in one or more visits. Staff enter canonical stock quantities and a reason; packaged agreements require whole packages. Collection creates an ordinary issued invoice at the accepted name, price, discount and tax rules. Cumulative rounding preserves the accepted two-decimal totals and five-decimal tax components across visits. Current catalogue prices and tax changes never reprice an existing agreement. Goods require live reservations; services require no stock hold. Collection consumes the original FIFO batches once. Pending quantities remain reserved on the original sources until their original deadline. Continuous/split constraints and the remaining cutting-loss budget still apply. Uncertain results keep the request and fields frozen for an identical retry.

Sales issuance and payment authority remain separate. A cashier with issuance authority can collect held goods without applying advances. Deposit application additionally requires the existing receipt permission; private payment information requires payment-view permission. Existing invoice returns retain original tax, measurement, FIFO cost and cut-return approval. A returned physical cable piece becomes its own source and is never spliced into the original reel. Returns do not silently reopen the fulfilled order; any replacement requires a separately reviewed agreement.

The common Shop write gate takes the existing Shop lock before business locks and rechecks authorization after waiting. This aligns the earlier currency/tax guards with reservation, invoice and receipt writes and avoids a product/Shop lock inversion. Real-session cases cover competing holds, reservation-first and cashier-first sales, and two distinct collection requests. This serializes writes within one shop; representative busy-store performance remains part of final E6 qualification.

The shared order page composes `BsOrderFundingPanel` and `BsOrderDeliveryPanel`; Shop supplies typed state and semantic commands. Localized decimal text is normalized without floating-point parsing. Missing or malformed reader payloads produce recoverable panel errors. No browser operation directly constructs an invoice, receipt or stock movement. Native Supabase, hosted deployment, real merchant, hardware and native-speaker acceptance remain separately evidenced gates.
