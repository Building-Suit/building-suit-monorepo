# Building Suit — Deployment & Operations Runbook

## 1. Purpose & scope

Define how Building Suit is deployed, monitored, maintained, recovered, and operated after launch. This is the operational counterpart to the Implementation Plan `08.*` (what is built) and the Testing Strategy `09.*` (how it is validated): it converts the architecture's deployment and reliability direction (ARCH §13, §15, §16.3, §17) and the PRD operability requirements (NFR-OPS-01..07, release gates §6.9) into environments, pipelines, deployment steps, rollback, monitoring, backups, incident handling, and maintenance procedures.

**Status:** DRAFT — not approved. Only the human owner approves.

**Normative sources:** PRD `01.*` (§6.5 NFR-OPS, §6.9 release gates), System Architecture `04.*` (§13 reliability/recovery, §15 logging/monitoring, §16.3 security baseline, §17 deployment), Database Design `05.*` (migrations, backup considerations), API Contract `06.*`, Security Matrix `07.*`, Implementation Plan `08.*`, Testing Strategy `09.*`. Arabic `_AR` files are translation references only.

**In scope:** environments, CI/CD pipelines, environment variables/secrets, deployment steps, rollback, monitoring, logging, backups/recovery, scheduled-job operations, incident response, postmortems, and production maintenance.

**Activation-gated:** live Paymob payment operations are the top engineering/business priority but start from zero: no merchant account, contract, or integration exists. Activation requires merchant onboarding, KYC, contracting, legal/compliance validation, technical integration, callback verification, reconciliation testing, operational support procedures, and deployment/runbook readiness. The first Paymob release must include both resident-to-building payment collection and Building Suit SaaS subscription billing. Multi-portal deployment remains Future/Post-MVP.

> **Operating principle.** This runbook does not invent operational policy where a source defers it. PDPL/privacy/consent is the top legal sequencing priority and must be resolved before refund/dispute, support, and cancellation procedures are finalized. RPO/RTO/retention (ARCH-OPEN-03), provider selection (ARCH-OPEN-05), SLOs (ARCH-OPEN-06), and alert thresholds (ARCH §15.4) are **GATED**: the procedure is defined here, the approved numbers are filled in when recorded.

## 5. CI/CD pipeline (ARCH §17.3, §19.2)

Every change pipeline runs, in order:

1. Install pinned dependencies.
2. Formatting/linting, type checks, contract validation.
3. Unit and integration tests (authored test-first; CI enforces pass — ARCH §17.7).
4. Validate migrations against a disposable database.
5. Security and secret scans.
6. Build affected deployable applications/functions.
7. Deploy to staging.
8. Smoke and critical-path tests on staging.
9. Require explicit approval for production.
10. Record release version and migration state.

| ID | Rule | Source |
|---|---|---|
| OPS-010 | Merge is blocked on any red gate in steps 2–5. | ARCH §17.3 |
| OPS-011 | Each portal/app builds and deploys independently; one surface's pipeline does not couple another's release. | NFR-PERF-01; NFR-OPS-01; ARCH §17.5 |
| OPS-012 | Generated API clients (TS/Dart) are validated against the OpenAPI source; drift fails the build. | ADR-014 |
| OPS-013 | Production deploy requires human approval and records release version + migration state. | ARCH §17.3 steps 9–10 |

## 6. Deployment steps by surface

### 6.1 Database migrations (ARCH §17.4; NFR-OPS-02)
1. Author forward migration; version-controlled and reviewed.
2. Destructive changes use **expand-and-contract** (add new → backfill → switch reads → remove old in a later, explicit removal milestone).
3. CI validates on a disposable DB and rejects new authoritative objects in `public` or unapproved cross-portal dependencies.
4. Apply forward to ENV-STG; verify active clients/functions remain compatible.
5. Apply to ENV-PROD during the deployment window; data backfills are observable, restartable, and bounded.

### 6.2 Edge Functions / API (ARCH §8, §17.3)
1. Deploy functions after the migrations they depend on are live (expand phase first).
2. Maintain backward compatibility for installed Flutter versions during staged rollout.
3. Smoke-test authenticated command/query paths post-deploy.

### 6.3 Web portals (ARCH §17.5)
1. Build the specific portal only.
2. Deploy to its own hostnames/runtime; no other portal's protected routes included.
3. SSR state instantiated per request; verify no protected-state leakage into public caches.

### 6.4 Flutter app (ARCH §17.6)
1. Build the correct flavor; config points only to the target environment.
2. Ensure backward-compatible APIs (installed versions cannot upgrade instantly).
3. Apply minimum-supported-version / feature-flag controls before public release.
4. Release builds contain no mock services, test credentials, debug routes, or simulated privileged actions.

## 8. Monitoring (ARCH §15.3; NFR-OPS-05)

Production monitoring MUST cover:

- Authentication/verification failures.
- Authorization denials and suspicious tenant-boundary attempts.
- Edge Function/API error rate and latency.
- DB errors, slow queries, connection pressure, failed migrations.
- Ledger imbalance / reconciliation failures.
- Duplicate / idempotency conflicts.
- Subscription-transition failures.
- Vote-close job failures.
- Ordinary vote-request overdue/reminder job failures.
- Notification/outbox backlog and delivery failures.
- Realtime connection health.
- Storage upload/access failures.
- **GATED:** Paymob callback / mismatch / replay / reconciliation failures for resident payments, SaaS subscription payments, and withdrawals (E4).

### Alerts (ARCH §15.4) — thresholds GATED (ARCH-OPEN-06)
Alerts must exist for: any ledger-invariant breach; repeated cross-tenant authorization failures; failed/delayed critical scheduled jobs; sustained elevated API error rate; DB capacity/availability risk; backup/restore validation failure; (GATED) payment callback verification/reconciliation failure.

## 12. Incident response

> **PROPOSAL** — ownership/escalation roster is solo-CTO initially (ARCH §20 risk: solo-CTO overload → managed services + clear alerts + runbooks).

1. **Detect** — alert fires (§8) or report received.
2. **Triage & classify** — severity by blast radius: ledger-invariant breach and cross-tenant exposure are top severity (ARCH §16.4, §20).
3. **Contain** — for suspected cross-tenant/privilege issues, restrict the affected path (feature flag / disable function) before deep diagnosis.
4. **Diagnose** — follow the correlation ID (§9) across the chain.
5. **Recover** — apply forward fix + app rollback (§7); restore from backup only if data integrity is compromised (§10).
6. **Verify** — re-run relevant CHK checks (`09.*` CHK-02/03) on staging/prod smoke.
7. **Record** — open a postmortem (§13).

Special cases:
- **Ledger invariant breach:** never destructively edit history; correct via compensating entries (ADR-008); reconcile.
- **Paymob fee or settlement mismatch:** disable the affected payment/payout method if final fee or settlement availability cannot be verified before user confirmation; reconcile before re-enabling.
- **Refund/reversal/chargeback request:** route through Platform Support / Operations with Paymob evidence; do not expose or simulate a Building Admin or Resident refund action in MVP.
- **Webhook forgery/replay (GATED):** rely on HMAC + idempotency; reject and log; never settle on unverified callbacks.
- **Withdrawal Requires Review (GATED):** do not release funds or daily-limit reservation merely because Paymob is delayed. Record `Confirmed`, `Failed`, or `Reversed` as final primary status changes only with Paymob reference or documented reconciliation evidence through the restricted Platform Operator / Super-Admin path. Record `Still Pending` only as a review outcome that leaves primary status `Requires Review`, keeps reservations held, and posts no final outflow.
- **Cancellation with positive wallet balance:** do not proceed; instruct the Building Admin to withdraw the full positive wallet balance before cancellation. During cancellation retention, building data remains readable and writes remain disabled until reactivation or approved retention/deletion policy applies.
- **Secret exposure:** rotate affected secret (§14), invalidate sessions if tokens involved, audit access.

### 15.4 Checkpoint-08 operational gates

**Release verification — automatic completion.** Prove in a release environment that a replacement cycle finalizes with `completion_reason:"deadline_reached"` when the scheduled deadline passes with incomplete participation, and with `completion_reason:"complete_participation"` when every eligible Unit holds an effective vote before the deadline. Prove API-100 returns `403 automation_only` for Building Admin, incumbent, challenger, resident, company Super Admin, and Platform Operator sessions, and that no deployed client route, permission code, admin tool, or operator console exposes a close, approve-result, finalize, extend, or cancel-result action. Prove `409 voting_active` when neither completion condition holds. Prove replacement-cycle creation persists no title and rejects `title`/`is_retry`-style fields, and that retry metadata is server-derived from prior terminal-cycle history.

**Invariant checks — one effective vote per Unit.** Run a scheduled reconciliation query proving that for every replacement cycle no `(replacement_cycle_id, unit_id)` pair has more than one row with `superseded_at IS NULL`, that every superseded row has a complete and consistent supersession triple, that no superseding reference points outside its own cycle and Unit, and that no result row has been deleted. Any violation is a P1: freeze finalization for the affected Building, preserve all rows, and escalate before any corrective write.

**Monitoring — stuck cycles.** Alert when a cycle remains nonterminal while complete eligible-Unit participation has held for longer than the agreed evaluation window, and when a cycle remains nonterminal past `voting_end_at` plus the deadline-worker grace period. Both indicate a failed or skipped completion evaluation, not a business outcome. Numeric thresholds follow the ARCH-OPEN-06 alert/SLO decision and are not invented here.

**Monitoring — duplicate terminal events.** Alert on any cycle with more than one terminal transition, more than one recorded result, more than one Admin-transfer audit entry, or duplicate terminal outbox events. Exactly-once is an invariant, so any occurrence is an incident rather than a tunable.

**Audit reconciliation — superseded votes.** Periodically rebuild each cycle's exact internal tally from append-only history/supersession links and compare it to the stored result. Reconciliation output remains restricted. Verify the open member projection contains participation/progress only and no candidate totals, while finalized totals reconcile. DEC-16/ARCH-OPEN-13/SEC-ADR-09 are closed by this publication rule.

**Rollback and recovery.** Recovery never deletes, rewrites, or un-supersedes a vote row. A bad deployment is rolled back by restoring code and re-running the idempotent completion evaluator, which is a no-op against already-terminal cycles. Restores must preserve every historical and superseded row, supersession metadata, completion-evaluation records, terminal results, audit, and outbox. If a restore lands a Building mid-cycle, do not manually finalize, extend, or reopen: let the evaluator and deadline worker converge, and escalate if a stuck-cycle alert persists.

**Operational wording.** Runbooks, alert text, dashboards, and support scripts must not state that a replacement ballot "always remains open exactly three days." The correct operational statement is that it runs to the earlier of the scheduled three-day deadline or confirmed complete eligible-Unit participation, and that finalization is system-driven with no human close step. Support must never offer to close, extend, approve, or reopen an election, and must not confirm or deny whether a specific Unit voted.
