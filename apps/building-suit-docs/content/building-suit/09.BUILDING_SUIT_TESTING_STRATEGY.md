# Building Suit — Testing Strategy

## 1. Purpose & scope

Define how Building Suit validates correctness, stability, security, and regression safety before and after release. The strategy exists because the current automated tests are "scaffold-level and do not provide sufficient coverage for the implemented financial, governance, authorization, and realtime logic" (PRD §6.8).

In scope: manual/exploratory, unit, integration, end-to-end, regression, performance, and security testing; test data; environments; coverage policy; and release-validation checklists.

Out of MVP scope (specified, deferred): live Paymob payment test suite (E4) and multi-portal isolation-at-scale suite (E8) — authored when those epics activate.

## 3. Testing principles

1. **Test-first (ARCH §17.7).** A failing test precedes the implementation of any domain rule (validation, authorization, balances/ledger, subscription gating, governance activation, vote results, idempotency).
2. **Isolation-first negatives.** Tenant- and portal-isolation tests (ARCH §18.1) are written as failing negative tests before the guarded path exists.
3. **No invented behavior.** If a test needs a rule the sources do not define, raise a decision in the originating document — do not guess (ARCH §17.7, §19.4).
4. **Determinism.** Tests control time, randomness, IDs, and money; no reliance on wall-clock or network flakiness.
5. **Financial truth is sacred.** Ledger tests assert immutability and compensating-entry correction only — never destructive edits (ADR-008).
6. **Server is the authority.** Realtime/cache tests must never substitute for asserting the authoritative read (ADR-010).
7. **Bilingual + RTL.** Critical journeys assert EN/AR content and RTL layout (ARCH §19.4).

## 9. Coverage policy & quality gates

- **Risk-weighted coverage (TEST-DL-04):** finance, authorization, governance, isolation, and idempotency paths require meaningful coverage (PRD §6.9). Trivial presentation markup is exempt.
- **CI merge gate:** lint, type, contract-gen validation, unit, integration, migration validation, security/secret scan all green (ARCH §17.3).
- **Pre-production gate:** critical-path E2E + ARCH §18.1 matrix green; ARCH §18.2 "before pilot production data" list satisfied.
- **No silent invention gate:** a failing/undefined behavior raises a source decision, not an invented assertion (ARCH §19.4).

## 10. Release-validation checklists

Derived verbatim-in-intent from ARCH §18.2 and PRD §6.9.

### CHK-01 — Per change (pre-merge)
- [ ] New/changed domain logic was built test-first.
- [ ] Unit + integration suites green; contract regenerated and validated.
- [ ] Migrations validated on a disposable DB; expand-and-contract preserved.
- [ ] No secrets in code/logs/bundle; error responses safe.

### CHK-02 — Pre-staging / pre-production
- [ ] Critical-path E2E (TS-030..037) green on staging.
- [ ] ARCH §18.1 required-test matrix (§5) all green.
- [ ] EN/AR + RTL validated on changed journeys.

### CHK-03 — Before pilot production data (ARCH §18.2)
- [ ] Critical financial commands use atomic DB operations.
- [ ] RLS and authorization isolation tests pass.
- [ ] Activation, subscription gating, withdrawal reservation/review controls, monthly dues, Special Assessment/equalization, old owner-obligation review, directed payment buckets, content retention, resident-created-permission rules implemented and tested.
- [ ] Production error responses and CORS hardened; sensitive media private.
- [ ] Required audit events durable.
- [ ] Backup and restore configured and tested.
- [ ] Monitoring covers critical APIs, jobs, authorization, and ledger health.

### CHK-04 — Before online payment activation (ARCH §18.2; PRD §6.9) — GATED
- [ ] Full Paymob integration + operations spec approved, including final payout/wallet/custody/settlement/licensing model validation (ARCH-OPEN-09).
- [ ] Callback/webhook verification, idempotency, settlement availability, fee display/validation, reconciliation, withdrawal `Requires Review`, refunds/reversals/chargebacks, alerts tested (NFR-QA-04).
- [ ] Financial/legal compliance boundaries approved.

### CHK-05 — Before another portal launches (ARCH §18.2; PRD §6.9) — GATED
- [ ] Portal has its own approved BRD/PRD/UX/architecture/security/deployment.
- [ ] Trusted portal resolution generalized and tested.
- [ ] Cross-portal access and consent contracts explicit; deny-by-default proven.
