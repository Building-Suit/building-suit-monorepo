# Building Suit UI-Agnostic Motion Specification

**Specification status:** Independent motion system
**Compatible with:** Any visual language, component library, layout, framework, theme, or viewport
**Behavior source:** `03. BUILDING_SUIT_UX_SPEC.md`

## 1. Purpose and Use

This document defines how interface state changes move, not how the interface looks. It can be used with `03A.BUILDING_SUIT_UI_SPEC.md`, a generated interface, or a completely custom design.

Motion must never create product behavior, hide required information, change permissions, or become the only way a state is communicated. Components may look different across implementations while sharing the same semantic motion recipe.

To apply this system, map each interface event to a recipe by purpose: menu, navigation, contextual task, expand/collapse, feedback, collection change, drag, or scroll response. Do not select animation by component name or visual style.

## 2. Motion Principles

1. **Continuity:** Movement explains where content came from, where it went, or which state changed.
2. **Directness:** User-driven movement responds immediately. Decorative delay never blocks a task.
3. **Hierarchy:** The most important state change receives the clearest movement; supporting elements stay quieter.
4. **Restraint:** One dominant motion idea is used per event. Avoid simultaneous scale, rotation, blur, parallax, and stagger unless each carries meaning.
5. **Reversibility:** Reversible interactions can reverse from their current progress without jumping to an endpoint first.
6. **Interruptibility:** New input can safely finish, reverse, or replace an in-progress transition.
7. **Adaptability:** Recipes use relative distance and semantic layers instead of depending on a particular card, color, radius, or navigation layout.
8. **Accessibility:** Motion preference, focus, reading order, and input method remain respected in every recipe.

## 3. Shared Tokens

### 3.1 Duration

| Token | Default | Use |
|---|---:|---|
| `instant` | 0 ms | State that must update synchronously |
| `micro` | 120 ms | Press, hover, focus, tiny acknowledgment |
| `quick` | 180 ms | Exit, dismiss, small state replacement |
| `standard` | 240 ms | Most entrances and local transitions |
| `emphasized` | 320 ms | Menu, contextual task, meaningful rearrangement |
| `extended` | 420 ms max | Rare large spatial transition |

Duration may shorten by up to 20% on small travel distances and lengthen by up to 20% on large viewports. Avoid transitions longer than 420 ms unless the user directly controls their progress.

### 3.2 Easing

| Token | Curve | Use |
|---|---|---|
| `enter` | `cubic-bezier(0.16, 1, 0.3, 1)` | Elements arriving and settling |
| `exit` | `cubic-bezier(0.4, 0, 1, 1)` | Elements leaving quickly |
| `standard` | `cubic-bezier(0.2, 0, 0, 1)` | State-to-state movement |
| `linear` | linear | Progress directly bound to scroll or drag |

Use a spring only for a user-released drag or an element that must settle after overshoot. Target damping ratio `0.8–1.0`; allow no more than one subtle overshoot, never for destructive, financial, authentication, or error feedback.

### 3.3 Distance and scale

- Micro travel: `4–8 px` or the platform-equivalent unit.
- Local travel: `8–24 px`.
- Structural travel: derive from source and destination geometry; never invent a fixed off-screen distance when the actual boundary is known.
- Routine scale should remain between `0.96` and `1.04`.
- Larger scale changes are reserved for an explicitly selected UI adapter and must not reduce readability or make background actions appear available.

### 3.4 Stagger

- Use stagger only when it helps reveal order in a newly introduced group.
- Default offset: `16–24 ms` per item.
- Maximum accumulated delay: `80 ms`.
- Do not stagger validation errors, time-sensitive alerts, menu actions needed immediately, or long collections.

## 4. Menu Motion

The menu recipe works for a side panel, top panel, bottom sheet, command surface, popover, or full-screen navigation.

### 4.1 Open

1. The menu responds on activation without intentional delay.
2. The navigation layer enters from its real spatial origin using `emphasized + enter`.
3. Recommended starting state is `8–24 px` or `2–4%` toward the opening edge with `opacity 0–0.4`; the resting state is full opacity and zero offset.
4. If the current content must move, it moves once as a coherent plane using `emphasized + standard`. Scaling or softening the content is optional and belongs to the chosen UI, not this recipe.
5. A backdrop, when used, fades with `standard`. It must not finish substantially later than the navigation layer.
6. Focus moves into modal navigation after it is available. Background actions become non-interactive at the start of opening, not after the animation ends.

### 4.2 Close

1. Close uses `quick + exit` and may be slightly faster than open.
2. The menu exits toward its spatial origin while current content returns from its present interpolated state.
3. Focus returns to the invoker when it still exists; otherwise it moves to the closest logical destination.
4. Choosing a destination may combine close and navigation only when destination state is ready. It must not reveal unrelated stale content between them.

### 4.3 Gestures and interruption

1. A drag-enabled menu binds position directly to gesture progress with linear interpolation.
2. On release, settle toward the nearest valid state using distance and velocity. A fast intentional fling may override the halfway threshold.
3. Reversing direction reverses current progress; no restart flash is allowed.
4. Escape, system Back, backdrop selection, and destination selection follow the same close state machine.
5. Opening direction mirrors in RTL when the menu is tied to reading direction. Physical-edge menus retain their declared physical edge.

## 5. Scroll Motion

Scroll-linked movement is optional. Ordinary scrolling is always a valid implementation. When used, it must preserve content access, position, and direct manipulation.

### 5.1 Contextual collapse

Use when an expanded context region should become a compact persistent identity while content gains space.

```text
progress = clamp(scrollOffset / collapseDistance, 0, 1)
value = interpolate(expandedValue, compactValue, progress)
```

1. Bind movement directly to scroll using `linear`; do not animate toward delayed scroll positions.
2. Keep at least one stable identity cue through the full range.
3. Supporting content may reduce emphasis earlier than primary identity, but required actions and status must not disappear without an equivalent reachable location.
4. Reverse through the same states when the user scrolls back.
5. Prefer transforms and opacity. Avoid repeatedly measuring or reflowing layout on every frame.

### 5.2 Outer-to-inner handoff

Use only when a contextual region and a nested content region genuinely require separate scroll ownership.

1. The outer region owns upward movement until its compact stop.
2. The inner region receives movement only after that stop.
3. While inner offset is above zero, the inner region keeps the gesture.
4. At inner offset zero, downward movement may transfer to the outer region and restore context.
5. Momentum crosses the boundary once without double velocity, dead zones, or both regions moving together.
6. Keyboard, wheel, touch, and assistive input must reach the same content even if their handoff mechanics differ.

### 5.3 Viewport reveal

1. Use only for newly encountered, non-critical content.
2. Start no farther than `8–16 px` from rest with partial opacity and settle using `standard + enter`.
3. Trigger once per content identity, not every time the user scrolls past the threshold.
4. Items already visible at initial render may appear together; do not make the user wait through a cascade.
5. Critical messages, errors, focused controls, and primary actions appear immediately.

### 5.4 Parallax and depth

1. Parallax is decorative and optional.
2. Restrict travel to roughly `2–6%` of the containing viewport over the full scroll range.
3. Never apply parallax to body text, form controls, essential status, or anything the user must track precisely.
4. Disable parallax under Reduced Motion.

### 5.5 Scroll restoration and live updates

1. Returning from a secondary task restores the prior logical item and offset without an entrance animation.
2. Prepending or appending realtime content preserves the user's visual anchor.
3. New unseen content may use a non-moving indicator. Do not force-scroll unless the user explicitly requested follow mode.
4. Filter changes may crossfade result content using `quick`, but retained controls and scroll owner remain stable.

## 6. Navigation and Contextual Task Motion

### 6.1 Primary destination change

- Default to no transition or a `quick` opacity transition.
- When direction is meaningful, incoming content may travel `8–16 px` from the navigation direction while outgoing content fades.
- Persistent navigation and global context remain stationary.
- Never slide through intermediate protected or stale destinations.

### 6.2 Contextual task open and close

- Open from the invoking region when geometry is known; otherwise use `standard + enter` with `8–24 px` travel.
- The source context remains stable behind or adjacent to the task according to the chosen UI.
- Close reverses toward the source using `quick + exit`.
- After successful mutations, content may update before close completes so the restored context is already correct.

### 6.3 Shared-element continuity

- Shared-element transitions are optional and reserved for a single clear identity such as a selected building, unit, provider, or announcement.
- Text must remain legible throughout. Do not morph multiple dense regions simultaneously.
- If source or destination geometry is unavailable, fall back to a normal contextual-task transition without delay.

## 7. State and Feedback Motion

### 7.1 Press, focus, and selection

- Press acknowledgment uses `micro`; scale is optional and no smaller than `0.98` for text-bearing controls.
- Focus indication appears immediately and does not pulse continuously.
- Selection changes move an indicator or crossfade state using `quick + standard`.

### 7.2 Expand and collapse

- Use `standard + standard` and animate between measured endpoints.
- Content fades only if clipping would otherwise make it unreadable.
- User input can reverse the transition from current progress.

### 7.3 Success, warning, and error

- Feedback appears using `quick + enter` with `4–8 px` maximum travel.
- Error motion never shakes an entire page. A single subtle horizontal offset cycle may be used for a local invalid control only when paired with explicit error content.
- Financial, authentication, and destructive results do not bounce, celebrate excessively, or disappear before they can be understood.

### 7.4 Collection changes

- Insert: make space and fade/translate the new item using `standard`.
- Remove: first communicate removal state, then collapse space using `quick`.
- Reorder: animate retained items from previous to new geometry using `standard`.
- For large updates, animate the collection as one region rather than every item.

### 7.5 Loading

- Progress that begins within 120 ms needs no animated placeholder.
- Indeterminate indicators use calm, continuous motion with no flashing.
- Skeleton shimmer is optional; use a slow pass of at least 1,200 ms and disable it under Reduced Motion.
- Loaded content may crossfade over `quick`; it must not shift unexpectedly because placeholder geometry was inaccurate.

## 8. Reduced Motion

Honor the platform's reduced-motion preference from first render. Do not wait for settings to load before suppressing non-essential movement.

| Motion type | Reduced Motion behavior |
|---|---|
| Menu or contextual task | Replace structural travel/scale with a `0–120 ms` fade; preserve focus and interaction timing |
| Primary navigation | No transition or brief crossfade |
| Contextual collapse | Use normal document flow or a discrete expanded/compact state without interpolation |
| Viewport reveal | Content appears immediately |
| Parallax | Disabled |
| Shared element | Replace with crossfade |
| Loading shimmer | Static placeholder or low-motion opacity change |
| Drag | Keep direct tracking required for control, remove overshoot and animated settle where practical |

Reduced Motion must not remove content, state feedback, progress, focus behavior, or the ability to complete a gesture-driven task through another input.

## 9. Performance and Implementation Contract

1. Target the platform's native refresh rate; at minimum, maintain 60 frames per second on supported devices during routine motion.
2. Prefer compositor-friendly transform and opacity changes.
3. Avoid animating large blur regions, box shadows, filters, and layout properties on every scroll frame.
4. Measure geometry before a transition begins and reuse it until the transition ends unless the viewport changes materially.
5. Cancel observers, animation frames, and gesture listeners when their context is removed.
6. A route change, language change, active-building change, or permission update may cancel motion and commit the authoritative state immediately.
7. Automated tests must not depend on wall-clock animation completion. Expose settled state or await an animation-finished signal.

## 10. Motion State Model

Every interactive recipe supports these states:

```text
closed/resting -> opening -> open/settled -> closing -> closed/resting
                         ^        |
                         |        v
                      reversing/interrupted
```

Rules:

1. Only one state is authoritative at a time.
2. Reversal starts from current computed progress.
3. Interrupted transitions clean up temporary styles and interaction locks.
4. The final state, not elapsed time, determines focus, input availability, and route completion.
5. Repeated activation while an action is processing does not create duplicate mutations.

## 11. Platform-Agnostic Token Contract

Implementations may expose these names through CSS variables, theme tokens, native constants, or design-tool variables:

```text
motion.duration.micro = 120ms
motion.duration.quick = 180ms
motion.duration.standard = 240ms
motion.duration.emphasized = 320ms
motion.duration.extended = 420ms

motion.easing.enter = cubic-bezier(0.16, 1, 0.3, 1)
motion.easing.exit = cubic-bezier(0.4, 0, 1, 1)
motion.easing.standard = cubic-bezier(0.2, 0, 0, 1)
motion.easing.linear = linear

motion.distance.micro = 4–8px
motion.distance.local = 8–24px
motion.stagger.step = 16–24ms
motion.stagger.maximum = 80ms
```

An interface may tune these values as a set for platform conventions, but it must preserve the relative relationship: exit faster than structural entry, local movement shorter than structural movement, and user-controlled motion directly bound to input.

## 12. Motion Review Checklist

- Every animation maps to a semantic recipe and has a reason.
- Menu open, close, selection, Back/Escape, drag, RTL, and interruption use one state model.
- Scroll effects are reversible and do not compete for gesture ownership.
- Returning to a prior context restores its logical position.
- Required content and actions never wait behind decorative motion.
- Reduced Motion has been tested from first render.
- Keyboard, touch, pointer, wheel, and system navigation can reach equivalent states.
- No transition leaks protected or stale context.
- Loading and realtime updates do not cause unexpected jumps.
- Open Admin-replacement updates animate participation/progress only; no candidate-total bar, number, or supersession delta is rendered or animated before finalization. Finalized totals may enter only with the terminal result state.
- Money Vote tolerance/maximum recalculation and authorization consumed/remaining updates use restrained numeric replacement with no celebratory or approval-implying motion; a successful Vote alone never animates a financial posting.
- Routine motion stays within the shared duration, easing, distance, and performance limits.
