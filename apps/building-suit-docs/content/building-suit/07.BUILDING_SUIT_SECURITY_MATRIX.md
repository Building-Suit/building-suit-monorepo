# Building Suit — Security & Permissions Matrix

## 1. Security model overview & trust boundaries

The platform is hub-and-spoke: one global **Account** with one **Profile per Portal** (ADR-001). Building Suit treats the **Building** as the primary tenant and subscription boundary (ADR-002).

### 1.1 Trust boundaries (ARCH §4.3)

> ARCH §4.3 defines **seven** boundaries (device, portal, building, privileged backend, database, external integration, operations). This matrix lists the five most relevant to access control; the integration and operations boundaries are covered under §14.

| # | Boundary | Rule | Citation |
|---|---|---|---|
| TB-1 | Client ↔ API | Nothing from the client is trusted for authorization. All identifiers are public UUIDs; all authz is re-evaluated server-side. | NFR-SEC-02; DL-10 |
| TB-2 | Session → Portal | A valid global session must be resolved into the trusted current Portal and its Profile before any domain access. | ARCH §4.3, §10.3 |
| TB-3 | Profile → Building | Every building-scoped operation must validate Membership, status, role, permission, and resource ownership. | ARCH §4.3 |
| TB-4 | Backend secrets | `service_role`, Paymob credentials, and signing secrets exist only in backend runtimes and are never exposed to clients. | NFR-SEC-04 |
| TB-5 | Privileged backend | Any `service_role` operation must explicitly authorize the caller before access (RLS is bypassed under `service_role`). | ARCH §4.3; DB §10.1 |

### 1.2 Identity layering (ARCH §10.1)

```text
auth.users (Supabase Auth)
  → platform.users            (global account bridge)
  → platform.profiles         (one per Account per Portal — trusted portal only)
  → building_memberships      (Profile ↔ Building, with role + status)
  → role / permissions        (capabilities)
  → unit_occupancies          (owner/tenant occupancy + operation eligibility)
```

| Term | Definition | Citation |
|---|---|---|
| **Account** | Global authenticated identity. Alone grants **no** building/portal-domain access. | PRD §3.1, §4.1 |
| **Profile** | Account identity within one Portal. One Profile per Account per Portal. Portal roles are never stored on the global user. | PRD §3.1 |
| **Membership** | Profile participation in one Building, carrying a role and a status. | ARCH §10.1 |
| **Occupancy** | Owner or tenant relationship of a Profile to a Unit (history-preserving). | PRD §3.3; DB §7.2.5 |
| **Permission** | A capability granted through a role (or a future explicit grant). | PRD §3.4.1 |

## 2. Roles

| Role code | Name | Scope | Notes | Citation |
|---|---|---|---|---|
| `admin` | Administrator | Building | Holds all Building Suit permission codes. Primary subscription buyer. | PRD §3.4.1, §4.1 |
| `resident` | Resident | Building / Unit | Limited permission set (see §3). Baseline for approved members. | PRD §3.4.1 |
| `owner` | Owner (occupancy) | Unit | Uses `resident` permission mapping unless separately approved. Votes only when no tenant is assigned to the same unit. | PRD §3.3, §3.7.3 |
| `tenant` | Tenant (occupancy) | Unit | Uses `resident` permission mapping unless separately approved. Holds voting priority for the unit. | PRD §3.3, §3.7.3 |
| *(status, not a role)* | Blocked member | Building | Read-only where explicitly supported; all writes/votes/finance forbidden. | PRD §3.3; ARCH §10.4 |
| *(future/post-MVP)* | Service provider | Portal-wide | Not an active MVP actor. Provider profile, directory, discovery/contact, permissions, APIs, and moderation are reserved for Future/Post-MVP. | PRD §3.9 |
| *(platform)* | Platform operator / Super-Admin | Separate portal | Full Super-Admin Portal is required after Building Suit MVP completion and before pilot launch. It is never substituted by a Building role and covers onboarding requests, internal reporting, user management, subscription management, support operations, platform-controlled configuration, trial policy configuration, pricing policy configuration, withdrawal-risk configuration, withdrawal-limit policy configuration, and withdrawal operational review. A mini internal queue/reporting UI may exist only temporarily during development. | ARCH §10.7 |
| *(baseline)* | Global authenticated user | Portal entry | No building/domain access until a Profile → Membership is resolved. | PRD §4.1 |

> **Occupancy vs role.** `owner`/`tenant` describe occupancy of a Unit, not a distinct permission tier. Authorization for them maps to `resident` unless an explicit grant says otherwise (PRD §3.4.1).

## 5. Canonical authorization chain

Every building-scoped operation must satisfy **all** of the following, evaluated server-side, in the command transaction (ARCH §10.4, §8.3):

```text
authenticated Account
AND active current Portal Profile            (trusted portal, server-resolved)
AND resource belongs to requested Building   (tenancy check on building_id)
AND active Membership for writes             (status gate)
AND role has required permission             (PERM code)
AND operation-specific policy passes         (eligibility, final-admin, occupancy, snapshot…)
AND subscription/billing state passes         (where applicable — all building writes)
```

Role permission alone is **insufficient** for (ARCH §10.5):

| Operation | Additional policy | Citation |
|---|---|---|
| Casting a vote | Eligible Unit + tenant priority resolved under lock against **current** occupancy; ordinary Admin/author exclusion; replacement incumbent/challenger allowed through valid Units; a voter can never change or withdraw their own choice, and the only permitted replacement is a newly eligible resident superseding that Unit's previous effective vote; API-100 normal-result finalization is automation-only while API-101 withdrawal and trusted-ineligibility termination are preserved | ARCH §10.5, §25; PRD §3.7, §6.8D |
| Ordinary vote-request read/edit/decision | Pending/overdue/rejected content is creator/current-Admin only. After pre-decision withdrawal, product-facing content/history is creator-only; Admin/other residents are denied and privileged audit is separate. Rejected resubmission gets a full new review window; withdrawn resubmission has no deadline while the original membership remains active and eligible, and a successful withdrawn resubmission gets the same full new window (§15G). | PRD §3.7.2A/§6.8I; API-104..110, API-129 |
| Viewing past-resident finance | Limited to the occupancy period | ARCH §10.5; DB §10.3 |
| Future provider exact-location disclosure | Reserved Future/Post-MVP; requires explicit consent if provider scope is reintroduced | ARCH §10.5; DB-INV-024 |
| Building writes under subscription control | Permitted subscription state; finance configuration writes additionally require billing readiness | ARCH §10.5; PRD §3.6 |
| Final-administrator removal | Requires a valid replacement | ARCH §10.5; DB-INV-008 |
| Admin-replacement outcome | API-100 normal-result path: 50% quorum against the fixed Unit denominator, automatic finalization at the earlier of the scheduled deadline or confirmed complete eligible-Unit participation, majority, tie/no-quorum continuity, and atomic role transfer. No human role — Admin, incumbent, challenger, resident, company Super Admin, or Platform Operator — may invoke, approve, delay, or cancel it; the call is restricted to a trusted internal execution path. Cancellation/invalidation may still terminate a nonterminal cycle without result or transfer | ARCH §10.5, §25; PRD §3.7, §6.8D |

## 8. Row-Level Security model & known gaps

RLS is enabled on tenant-sensitive and exposed tables (DB §10.1). Target rules:

- Exposed views use `security_invoker = true` (DB §11.1).
- Direct writes to critical tables are denied to `anon`/`authenticated`; approved commands run via RPC / Edge Functions under `service_role`, which must authorize the caller (SDL-04).
- Building-scoped read policies require an **active** membership of the caller in the row's `building_id`.

**Target building-read predicate** (per the documented access model, DB §10.1–10.2):
```sql
building_id IN (
  SELECT m.building_id FROM memberships m
  JOIN profiles p ON p.id = m.profile_id
  WHERE p.user_id = auth.uid() AND m.status = 'active'
)
```

**Own-record predicate** (notifications, announcement_reads, files):
```sql
profile_id IN (SELECT p.id FROM profiles p WHERE p.user_id = auth.uid())
```

## 13. Subscription / billing gating

Building **writes** require a write-eligible subscription state (PRD §3.4, §3.6). Reads remain available regardless. Manual payment recording remains permanently available in write-eligible states after Paymob goes live and is never delegated to regular residents as an authoritative write.

| State | Building writes | Reads | Notes |
|---|---|---|---|
| `trial` | ✓ | ✓ | Zero subscription charge; duration assigned from the effective versioned trial policy at building creation; Building Admin sees remaining days and first billing date. |
| `active` | ✓ | ✓ | Paid. |
| `past_due` | ✓ (grace only) | ✓ | 14-day grace. |
| `locked` | ✗ | ✓ | After grace lapses unpaid → read-only; all writes rejected with `403 subscription_locked`. |
| `cancelled` | ✗ | ✓ | Read-only for 3-month retention; reactivation during retention restores write eligibility without data loss. |

Subscription status set: `trial`, `active`, `past_due`, `locked`, `cancelled` (PRD §3.6; BRD §7.4). The subscription check is part of the canonical chain (§5) for every building write, including finance writes, membership changes, issues, comments, announcements, votes, governance actions, building configuration, and subscription-affecting building operations.

Cancellation is blocked while the building wallet has a positive balance; the Admin must withdraw the full wallet balance first. Existing negative balance responsibility transfers to a successor admin; if no successor exists, resolution goes through the Platform Operator / Super-Admin process once defined.

Trial policy changes are versioned and apply only to buildings created after the new policy effective date. Pricing-policy changes may apply to existing buildings only after audited creation, effective date, notice period, applicability rule, audit actor, and delivery evidence are recorded for both in-app notices and the company-configured external notice channel(s) to every affected active Building Suit profile.

## 15I. Checkpoint-15 moderated community-content security controls

SEC-086: A resident-created Discussion/Issue revision that is pending or rejected is readable only by the immutable author and the live current Building Admin; it never enters ordinary feeds, counters, search, realtime topics, notifications, exports, analytics, previews, caches, or resident-visible deep links, and unknown/cross-tenant/unauthorized public IDs are concealed. Approval alone publishes, and only the approved current revision.

SEC-087: All Checkpoint-15 commands derive actor, role, time, author identity, Building scope, lifecycle version, and presentation server-side inside the transaction. Client-supplied author/identity fields, moderation/approval/progress states, another actor's presentation, type reclassification, recipients, and timestamps are rejected; `content_type` and each revision's/comment's presentation are immutable after submission/creation. API-140/142 accept only deterministic closed patches and materialize complete immutable snapshots; API-143 accepts no content/presentation field and publishes only the stored candidate.

SEC-088: Mandatory reasons (Discussion/Issue rejection, author reopen reason, Admin reopen acceptance and rejection) reject blank/placeholder text server-side after canonical normalization; optional texts (resolution summary, comment-hide reason) truly accept omission and are normalized, bounded, and sanitized when supplied. The two classes are never confused in contract, UI, or tests.

SEC-089: Only the live current Building Admin, reauthorized at commit, executes approve, reject, Issue progress, reopen decision, and comment hide; a former/replaced Admin, stale session, cached screen, queued or in-flight command, or late response cannot commit and loses identity-bearing anonymous-content access immediately across live requests, caches, realtime, exports, and late responses. The Admin cannot edit resident-authored content, type, anonymity choice, reopen reason, or comments.

SEC-090: Comment creation requires the caller-authorized current version plus live active same-Building membership and approved/published-parent visibility inside the transaction; former members, pending applicants, cross-Building, company, and unauthorized accounts can neither comment nor discover concealed content. Optional canonical comment media remains active only after same-Building uploader/attachment, completion, safety, and private-access revalidation. Published comments and their links are immutable; hide retains the original as a moderation event, conceals its media from ordinary residents, and no hard-delete, edit, restore, appeal, or mass-moderation path exists.

SEC-091: Anonymous-author identity is never resolvable or correlatable by ordinary residents through author labels, avatars, Unit labels, public/profile IDs, notifications, realtime, search, exports, analytics, logs, cursors, cache keys, moderation placeholders, filenames/paths/URLs, media descriptors, signed-access issuance, telemetry, download behavior, error payloads, timing/count side channels, or a stable cross-post pseudonym. The current Admin sees the real identity only within live authorized Building moderation/review surfaces, always accompanied by the explicit author-selected-anonymous indicator, and has no contract to reveal or change the author's presentation choice.

SEC-092: Resubmission requires the immutable author's current active eligible membership and a genuine server-detected change of normalized content and/or the new revision's presentation; unchanged replay cannot fabricate a new review, forged novelty claims fail, and no numeric cap, cooldown, or deadline is introduced. Append-only revisions, decisions, progress events, reopen rows, comments, and moderation events cannot be rewritten with stale or forged commands.

SEC-093: The one-per-aggregate reopen request is database-backed: a second request fails as exhausted, idempotent replay consumes nothing, and concurrent request/decision/progress/Admin-replacement commands serialize first-valid-atomic-commit-wins with no partial state, event, notification, realtime, search, or cache artifact from a loser.

SEC-094: Checkpoint-15 telemetry/logs/metrics/audit carry safe public/correlation IDs, content type, and state/version codes only; they exclude resident text, hidden comment bodies, real anonymous-author identity, contact data, raw attachment data, internal IDs, and secrets, and enumeration timing/cursors remain bounded and purpose-bound.

SEC-095: This workflow adds no company/Super Admin content-review queue, company adjudication/escalation, employee moderation permission, public/global or cross-Building surface, new subscription/finance/Paymob/withdrawal/Vote/election/Unit/membership behavior, or Q226+ contract; API-110/113/121/129, API-130..138, and all Checkpoint-12/13/14 controls remain unchanged.
