## 1. API Conventions

### 1.1 Base URL & versioning
- **Logical base:** `https://api.buildingsuit.app/v1` *(PROPOSAL — exact host unspecified by sources)*.
- **Current carrier:** Supabase Edge Functions at `POST /functions/v1/<function-name>`. Each logical route below lists its current function name.
- **Versioning:** breaking changes increment the major version (`/v2`). Additive, backward-compatible changes do not. Clients MUST tolerate unknown additive response fields.

### 1.2 Authentication model
- All protected endpoints require `Authorization: Bearer <supabase_jwt>` (ARCH §10.2; NFR-SEC-01).
- The server verifies the JWT, resolves the **trusted portal** from server configuration (never from client input — ARCH §10.3), then resolves the caller's **Profile** for that portal.
- Building-scoped endpoints additionally evaluate the full chain: active Profile → resource∈Building → active Membership (for writes) → role permission → operation-specific policy → subscription/billing state (ARCH §10.4; PRD §3.4). The only Checkpoint-13 exception is the original author's own retained withdrawn-record personal-history read in API-108 and presentation-only Hide/Restore in API-129 after the original membership ends: the path Building remains a tenant/resource-scope and anti-enumeration check, but API-129 changes only account-owned presentation state and is not a Building-domain write. It grants no current Building read, content edit/resubmit, or other Building action. `locked` and `cancelled` buildings are read-only: historical reads remain available, but every Building-domain write is rejected.
- `blocked` membership may satisfy only explicitly read-only endpoints (PRD §3.3).
- Public webhook endpoints are unauthenticated by JWT and instead use signature verification (§5).

### 1.3 Public identifiers
- All resources are addressed by **UUID public identifiers** at the boundary. Internal numeric IDs are never exposed and clients MUST NOT depend on them (ARCH §9.4; NFR-SEC-07).
- Path/body identifier fields use the `*_public_id` naming (e.g., `building_public_id`).

### 1.4 Content types & headers
| Header | Direction | Rule |
|---|---|---|
| `Authorization: Bearer <jwt>` | request | Required on protected endpoints. |
| `Content-Type: application/json` | request | Required for bodies. |
| `Idempotency-Key: <opaque-string>` | request | Required on retry-sensitive commands (marked **Idempotency: required**). Max 200 chars. |
| `Accept-Language: ar | en` | request | Optional; affects localized `message` resolution where applicable (NFR-I18N). |
| `X-Correlation-Id: <uuid>` | request/response | Optional inbound; always echoed/generated in response for tracing (NFR-OPS-06). |
| `Cache-Control: private, no-store` | response | Set on all protected responses (ARCH §8.4). |
| `Content-Type: application/json; charset=utf-8` | response | All responses. |

### 1.5 Success envelope (fixed — ARCH §8.5)
```json
{ "success": true, "data": {} }
```
- A command result MAY carry a user-facing confirmation as a stable chained key, never a server-rendered sentence:
```json
{ "success": true, "data": {}, "message_key": "success.payment.recorded", "params": {} }
```
- List responses place items and paging inside `data`:
```json
{ "success": true, "data": { "items": [], "page": { "next_cursor": "…|null", "has_more": false } } }
```

### 1.6 Error envelope (fixed — ARCH §8.5)
```json
{ "success": false, "error": { "code": "stable_error_code", "message_key": "error.stable_error_code", "params": {}, "message": "Safe English fallback summary", "details": {} } }
```
- `code` is a stable machine string (§1.9 catalog).
- `message_key` is a stable, chained i18n key (default `error.<code>`) that the **client** resolves to the active language via its i18n catalog. `params` carries safe interpolation values (counts, names, public identifiers) — never pre-rendered localized text. This is the convention for all user-facing text (DB §6.7; ARCH §7.8): the backend ships keys, the frontend renders language.
- `message` is an **optional safe English fallback** for logs and unconfigured clients; clients MUST prefer `message_key` and MUST NOT parse `message` for logic.
- `details` carries safe, field-level context only.
- Production errors never contain SQL, stack traces, or internal exception text (ARCH §8.3, §16.3; NFR-SEC-08).

### 1.7 HTTP status mapping (fixed — PRD NFR-VAL-03/04; ARCH §13.3)
| Status | Meaning |
|---|---|
| `200` | Successful query or idempotent-replay command. |
| `201` | Resource created. |
| `202` | Accepted for async processing (e.g., export job, queued callback). |
| `400` | Validation error (`code: validation_error`). |
| `401` | Missing/invalid authentication. |
| `403` | Authenticated but not permitted (role/policy/subscription/consent). |
| `404` | Resource unknown or not visible in caller's authorized scope. |
| `409` | Safe, user-resolvable state conflict (incl. idempotency-key fingerprint mismatch). |
| `413` | Upload exceeds allowed size. |
| `415` | Unsupported media type. |
| `429` | Rate limit exceeded. |
| `500` | Unexpected internal error (generic body only). |
| `503` | Dependency unavailable (e.g., gateway) — domain state unchanged. |

### 1.8 Field conventions
| Field | Type | Rule |
|---|---|---|
| `*_public_id` | string (uuid) | Public resource identifier. Internal numeric `id` is never exposed (§1.3; DB §6.4). |
| `amount`, option `amount`, `monthly_fee`, `reserved_amount`, authorization amounts | string decimal | Scale 2, e.g. `"150.00"` (DL-04). Legacy `money_amount` is compatibility-only and not the Checkpoint-09 target contract. |
| `currency_code` | string | ISO 4217; MVP `EGP`. |

| `status`, `role`, `type`, `*_scope`, `method` | enum (stable string name) | Each value is a member of a backend-defined enumeration stored internally as an integer code (DB §6.6) and shared with clients as a typed contract (ARCH §8.9). The wire uses the stable string **name**; clients map it through the shared type, never by hardcoded literal. Values enumerated per endpoint. |
| phone | string | Egyptian, canonical `+20` (PRD §3.1). |

### 1.10 Pagination, filtering, sorting (DB §19; ARCH §8.4)
- **Pagination:** keyset/cursor. Query params `?limit=<1..100, default 25>&cursor=<opaque>`. Response `page.next_cursor` is `null` when exhausted. Default sort is `created_at desc, id desc` unless an endpoint states otherwise.
- **Filtering:** documented per endpoint via explicit query params only (e.g., `status`, `type`, `unit_public_id`, `category`, `from`/`to`). Arbitrary field filtering is not supported.
- **Sorting:** fixed per endpoint; urgent announcements are pinned first (PRD §3.8.2).
- **Exports** that may exceed limits return `202` + a job handle and complete asynchronously (DB §19).

### 1.11 Idempotency semantics (ARCH §13.2; DB §7.8, §13.3)
1. Client sends `Idempotency-Key` on retry-sensitive commands.
2. Server computes a canonical request fingerprint and claims `ops.idempotency_keys` on `(scope_type, scope_id, command_name, idempotency_key)`.
3. **Same key + same fingerprint, completed** → returns the stored authoritative result with the original status (a replay, `200`).
4. **Same key + different fingerprint** → `409 idempotency_conflict`.
5. **In-progress duplicate** → does not execute concurrently; returns `409 state_conflict` (`reason: in_progress`) and the client retries.
6. Financial/webhook keys are retained for the full replay window.

### 1.12 Concurrency (ARCH §13.3)
Safe, user-resolvable conflicts return `409` with a specific code (`state_conflict`, `duplicate_request`, `occupancy_conflict`, `final_admin_protection`, `replay_detected`). The client refreshes authoritative state and may retry.

### 1.13 Rate limits (ARCH §16.1; NFR-PERF-07)
Rate limits apply to auth, verification, invitations, joins, uploads, and sensitive commands. Exceeding returns `429 rate_limited` with `details.retry_after_seconds` and a `Retry-After` header. *Proposed defaults (PROPOSAL):* auth/verify 10/min/IP+account; invitations/joins 30/hour/account; uploads 60/hour/account; financial commands 120/min/building.

### 1.14 Caching (ARCH §8.4; NFR-PERF-02)
All protected responses set `Cache-Control: private, no-store`. Protected data is never placed in shared/public caches.

### 1.15 Deprecation & compatibility policy
- Removing/renaming a field or changing its meaning, removing an endpoint, tightening validation, or changing an enum's existing values is **breaking** → new major version.
- Deprecated-but-present elements are marked with a `Deprecation` response header and `Sunset` date; they remain for at least one minor cycle.
- Error `code` strings and permission codes are contracts; changes require coordinated PRD/security-matrix/seed/test updates (PRD §3.4.1).

## 3. Endpoint specifications

### 3.1 Identity / Portal / Auth

#### API-001 — Register account · C
- **Route:** `POST /v1/auth/register` (custom; wraps GoTrue sign-up) · **Idem:** required.
- **Auth:** none. **Purpose:** create a global account with required Egyptian phone, optional email, and password; trigger required verification(s) (PRD §3.1; UX §1.2).
- **Request:**
  | field | type | rules |
  |---|---|---|
  | `email` | string? | optional; valid and unique when supplied |
  | `phone` | string | required Egyptian phone, normalized `+20`, unique |
  | `password` | string | policy-compliant |
  | `accepted_terms` | bool | MUST be `true` |
- **Success `201`:** `{ "account_public_id", "verification_required": ["phone"] }`; phone verification is the only registration verification gate.
- **Errors:** `400 validation_error`; `409 duplicate_request` (account exists); `429 rate_limited`.

#### API-002 — Verify optional profile email · C
- **Route:** `POST /v1/me/email/verify` · **Idem:** required. **Auth:** bearer.
- **Purpose:** verify an optional email after the user adds or updates it in Profile / Account Settings. Email verification is required only before email-based notifications/messages are sent; missing or unverified email never blocks app access, first login, Home, building access, or core product usage.
- **Request:** `{ "email", "otp" }` (six-digit).
- **Success `200`:** `{ "email_verified": true }`. **Errors:** `400 validation_error`; `409 state_conflict` (expired/used); `429 rate_limited`.

#### API-003 — Verify phone WhatsApp OTP · C
- **Route:** `POST /v1/auth/verify-phone` · **Idem:** required. **Auth:** none.
- **Request:** `{ "phone", "otp" }` (six-digit WhatsApp OTP). **Provider unresolved → GAP-002.**
- **Success `200`:** `{ "phone_verified": true }`. **Errors:** as API-002; `503 dependency_unavailable` (OTP provider down).

#### API-004 — Login · C
- **Route:** `POST /v1/auth/login` (GoTrue-backed) · **Auth:** none.
- **Request:** `{ "identifier" (+20 phone), "password" }` (PRD §3.1). Email login is not part of this checkpoint and requires a future explicit decision.
- **Success `200`:** `{ "access_token", "refresh_token", "expires_at", "account_public_id" }`.
- **Errors:** `401 unauthenticated`; `403 phone_not_verified`; `403 profile_required`; `429 rate_limited`.

#### API-005 — Refresh session · C
- **Route:** `POST /v1/auth/refresh` (GoTrue-backed). **Request:** `{ "refresh_token" }`. **Success `200`:** new token set. **Errors:** `401 unauthenticated`.

#### API-006 — Request password reset · C
- **Route:** `POST /v1/auth/password/reset-request` · **Idem:** required. **Request:** `{ "identifier" }` (canonical +20 phone). MVP password recovery uses the verified phone path; email recovery is not part of this checkpoint and requires a future explicit decision. **Success `200`** (neutral, no account enumeration). **Errors:** `429 rate_limited`. (UX §1.3)

#### API-007 — Confirm/change password · C
- **Route:** `POST /v1/auth/password/change` · **Idem:** required.
- **Auth:** reset token OR bearer (recent-auth may be required, ARCH §10.2). **Request:** `{ "token"?, "new_password" }`. **Success `200`.** **Errors:** `400`, `401`, `429`.

#### API-008 — Complete Google One Last Step · C
- **Route:** `POST /v1/auth/google/one-last-step` · **Idem:** required. **Auth:** bearer (Google session).
- **Purpose:** complete the Google-only One Last Step screen after every successful Google callback, including required phone verification, outstanding Profile fields, and terms acceptance before normal navigation (PRD §3.1; UX §2.3).
- **Request:** `{ "phone"?, "otp"?, "accepted_terms": true, "required_profile_fields"?: {...} }`; phone and OTP are required only while verified phone is outstanding. **Success `200`:** `{ "phone_verified": true, "profile_ready": true }`. **Errors:** `400`, `403 phone_not_verified`.

Fingerprint sign-in has no public biometric endpoint. #### API-036 — Record expense · C
- **Route:** `POST /v1/buildings/{building_public_id}/expenses` · **Idem:** required. **Auth:** permission `finance.expense` + finance-eligible subscription.
- **Purpose:** record a general expense, a `Unit Settlement Expense`, or an `Equalization Payout` / `Special Assessment Settlement`. A general expense posts an expense debit + manual credit and may exceed manual balance only after explicit confirmation. Unit settlement records a real outside-app payout against the old occupancy period without changing the current resident opening balance. Equalization payout records physical settlement of an entitled Equalization Credit and reduces building balance (PRD §3.5.4; DB §7.3).
- **Request:** `{ title, amount, expense_type?, spending_purpose_public_id?, create_spending_purpose?:{ title, category?, vendor_or_payee?, invoice_order_contract_reference? }, authorizing_money_vote_public_id?, authorization_commitment_public_id?, ...existing settlement/equalization fields, description?, confirm_over_balance? }`. Ordinary general Expense requires one stable same-Building spending purpose, selected or atomically created. When Money Vote authorization is required/used, `authorizing_money_vote_public_id` is mandatory at initial posting; it cannot be attached later.
- **Type rules:**
  - `general` uses the normal expense posting rule. `unit_settlement` requires `unit_public_id` and the ended `unit_occupancy_public_id` whose historical credit is being settled.
  - Outside Emergency Expense, the server locks the purpose, effective Building limit/provenance, related effective operations, optional authorization, and ledger accounts. Without authorization, cumulative same-purpose amount must remain within the effective no-vote limit. With authorization, the server validates same Building, successful Vote and spend winner, purpose relationship, tolerance ceiling, validity or qualifying documented pre-expiry commitment, cumulative consumption, idempotency, and concurrency. Vote ID is never decorative metadata.
  - One authorization may link multiple same-purpose Expenses/installments. `proposed_effective_amount + cumulative_effective_linked_amount` may equal but never exceed `maximum_authorized_amount`. Concurrent postings serialize; an overrun leaves no partial Expense/ledger/audit/outbox state. `Started` alone is never valid commitment evidence. Emergency Expense remains API-089.
  - `equalization_payout` and `special_assessment_settlement` are two wire labels for the same Admin-only Equalization Payout invariant. They require `equalization_credit_public_id`, `special_assessment_public_id`, `entitled_profile_public_id`, `unit_public_id`, `role`, and `payout_method`; an applicable ownership/occupancy period is retained from the credit and may be asserted by the corresponding request field. `cash|instapay|other` reduces the manual-balance component; `wallet` reduces the wallet-balance component; every method reduces `total_building_balance` by `amount`.
  - The server locks the Equalization Credit and verifies that it is `available`, has no prior or reserved `future_discount` consumption, the full `amount` matches its remaining unsettled amount, and the supplied person, role, Unit, period, and original Special Assessment match the stored entitlement. Client-supplied linkage cannot redirect a payout.
  - Equalization Payout atomically creates the expense and balance-reducing ledger operation, writes audit/outbox records, and sets the Equalization Credit wire status to `paid_out` with `settled_at`. Both `paid_out` and the separately retained terminal `settled` status are unavailable states; a new direct payout uses `paid_out`, while `settled` is reserved for an approved reconciliation/normalization that must retain `settlement_outcome`. The same credit cannot later be applied as a future discount or paid out again through API-035, API-036, API-076, or API-080.
- **Success `201`:** `{ operation_public_id, expense_public_id, expense_type, status:"posted", spending_purpose_public_id?, authorization?:{ money_vote_public_id, winning_option_public_id, base_amount, tolerance_percent, maximum_authorized_amount, consumed_amount, remaining_amount, validity_status, commitment_status }, no_vote_policy?:{ effective_limit, provenance, cumulative_purpose_amount }, building_balance_after, equalization_credit? }`.
- **Errors:** `400 validation_error`; `400 credit_scope_not_allowed`; `400 payout_amount_mismatch`; `403 forbidden`; `403 subscription_locked`; `404 not_found`; `409 idempotency_conflict`; `409 state_conflict` (`reason: over_manual_balance|credit_state_changed|credit_reserved`); `409 credit_already_settled`. **Trace:** PRD §3.5.4; BRD BR-FIN-24; UX §1.13; DB §7.3.

#### API-037 — Request wallet withdrawal · C

#### API-045 — Cast vote · C
- **Route:** `POST /v1/buildings/{building_public_id}/votes/{vote_public_id}/cast` · **Idem:** required. **Auth:** permission `vote.cast` + eligibility.
- **Purpose:** cast across all eligible Units atomically. Ordinary votes use `option_public_id`; dedicated Admin-replacement ballots use the cycle-bound incumbent/challenger option. The incumbent and challenger are not excluded from replacement voting and may cast only through Units they validly represent.
- **Request:** `{ option_public_id, expected_cycle_version? }`; replacement option IDs are supplied only by API-098/API-099 safe views and remain cycle-bound. `expected_cycle_version` is optional for ordinary votes and recommended for replacement ballots so a stale client is detected instead of writing against a changed cycle.
- **Eligibility is evaluated against current occupancy.** For a replacement ballot the server resolves, under lock, which Profile currently holds casting priority for each Unit. A resident who became the eligible occupant of an existing Unit while the cycle is open may cast for that Unit. A caller who has lost priority is rejected and the Unit's existing effective vote is untouched. Casting never creates a Unit and never changes the fixed Unit denominator.
- **Replacement supersession.** If the Unit already holds an effective vote and the caller is now its eligible voter, a successful cast supersedes it atomically; failure leaves the previous vote/effective internal tally unchanged. At most one effective vote exists per Unit. The response never reveals prior vote existence/content and matches a first cast. API-098 publishes participation/progress only while open, so no per-candidate −1/+1 delta is exposed; internal aggregate recomputation remains exact/immediate.
- **Success `200`:** `{ recorded_units:n, vote_status, cycle_status?, finalized? }`. A committed choice is final for its voter; existing ordinary auto-close and replacement automatic completion/withdrawal/ineligibility behavior remains. API-098 provides the open participation-only projection derived from effective votes, without candidate totals or Unit/person disclosure.
- **Errors:** `403 not_eligible_to_vote` (`reason`, including `unit_priority_lost`); `409 duplicate_request` (`conflict_on: vote_unit` — the same voter double-casting, F-23); `409 state_conflict` (vote not open); `409 cycle_terminal` when the replacement cycle finalized, was withdrawn, or was invalidated before commit — no mutation occurs and the previous effective vote stands; `409 stale_cycle_version` when `expected_cycle_version` no longer matches, requiring the client to re-read API-098 rather than retry blindly. Error bodies must not disclose the existence, author, timing, or content of any prior Unit vote. **Trace:** worked example §6.3.

#### API-046 — Close vote · C/J
- **Route:** `POST /v1/buildings/{building_public_id}/votes/{vote_public_id}/close` · **Idem:** required. **Auth:** permission `vote.approve` (manual) or scheduler (API-J02).
- **Purpose:** atomic, idempotent close of ordinary normal/money votes using creation-time snapshots. Replacement close/transfer is API-100; generic close never changes Admin roles.
- **Local limit-change state owner:** for `no_vote_limit_change`, API-046 is the only trusted local application boundary. It locks the Building policy, active scheduled change, Vote, and snapshotted policy versions in the shared order; revalidates immutable topic/proposal, valid result and approve winner, same-Building scope, and maximum; then closes and applies exactly once. An approval win updates the effective limit/provenance/protection and atomically marks any active platform schedule `superseded_by_local_vote`, before or after its due time. A non-success before the platform due time leaves `scheduled` unchanged; after due while `suspended_open_vote`, it invokes the trusted scheduled application in the same serialized continuation and applies the platform value immediately. If Super Admin already cancelled the schedule, the Vote is independent: approval applies locally and non-success leaves current value. Every outcome creates no financial authorization, Expense, payable, reservation, Special Assessment, balance, or ledger mutation.
- **Linked Special Assessment state owner:** its linked Vote is a `spending_authorization` under the existing Special Assessment purpose/link rules. When it is current for an unchanged draft, the same locked close transaction owns the non-financial draft transition: a valid successful 70% result sets `pending_vote -> approved`; failed or no-quorum sets `pending_vote -> vote_failed`; expiry sets `pending_vote -> vote_expired`; a cancelled draft remains `cancelled`, and a cancelled linked Vote leaves or moves the draft to non-postable `cancelled`. Every such close transition creates zero obligations, debt, Equalization Credit, ledger entries, or balance movement. A material revision invalidates the old link, so closing that stale Vote cannot approve the revised draft.
- **Success `200`:** `{ status: "closed", result_valid, winner?, limit_change_application?:{ applied, previous_value, effective_value, previous_provenance, provenance, protected_from_exceptional_propagation, source_vote_public_id, financial_effects_created:false }, linked_resource_transition?: { special_assessment_draft_public_id, from_status:"pending_vote", to_status:"approved"|"vote_failed"|"vote_expired"|"cancelled", financial_effects_created:false } }`.
- **Errors:** `409 state_conflict` (already closed → idempotent return of stored result). **Trace:** worked example §6.3.

## 5. Webhook contracts

#### API-070 — Paymob resident-payment / subscription-payment / withdrawal callback · W  *(activation-gated)*
- **Route:** `POST /v1/webhooks/paymob` · public (no JWT). **Status:** Paymob starts from zero: no current merchant account, contract, or integration. Activation requires merchant onboarding, KYC, contracting, legal/compliance validation, technical integration, callback/webhook verification, settlement-availability handling, payout-flow validation, fee quote/display validation, reconciliation testing, operational support procedures, and deployment/runbook readiness. The first Paymob release must include both resident-to-building payment collection and Building Suit SaaS subscription billing. The final Paymob subaccount/wallet model and any provider-side destination-saving capability remain capability-gated.
- **Verification (MUST):**
  1. Verify HMAC/signature; failure → `401 signature_invalid` (ARCH §11.3; NFR-SEC-05).
  2. Replay protection via unique `callback_event_id` / `gateway_reference`; duplicate → `200` with no state change (idempotent) or `409 replay_detected` if fingerprint differs.
  3. Reconcile amount, fee, total charged, currency, order/gateway reference, building, unit/profile/subscription invoice, selected due bucket, occupancy/ownership period, and status against trusted internal records (PRD §3.11).
  4. On confirmed resident payment: reduce the selected bucket/scope debt or create the approved `Occupancy Credit` / `Owner Obligation Credit` **exactly once**, transition the payment attempt to `trusted_confirmed` / `collected_not_available`, and keep the amount outside available-for-withdrawal balance until Paymob confirms settlement availability. Resident payment fee remains receipt/reconciliation data and is not building funds.
  5. On confirmed SaaS subscription payment: settle the subscription invoice/attempt and update subscription state exactly once.
  6. On Paymob settlement availability: move the collected amount into available balance exactly once according to the validated funds-separation model.
  7. On refund, reversal, or chargeback: preserve the original payment and post a compensating operation exactly once.
  8. On confirmed withdrawal: transition withdrawal to `Confirmed`, consume its amount-plus-fee balance/daily-limit reservation, and post the approved settlement effect once. On failed or reversed withdrawal: transition to `Failed` or `Reversed` and release balance/daily-limit reservations once for the original `withdrawal_limit_day`.
  9. Browser redirects are never proof of payment (PRD §3.11; ARCH §11.3).
- **Request (provider-shaped, validated before use):** `{ event_id, type: resident_payment|subscription_payment|withdrawal|settlement_availability, gateway_reference, amount, fee?, total_charged?, currency, order_reference, status, hmac/signature }`.
- **Success `200`:** `{ acknowledged: true }`. **Errors:** `401 signature_invalid`; `409 replay_detected`; `400 validation_error` (reconciliation mismatch → recorded, not applied); `503 dependency_unavailable`.
- **Atomicity & exactly-once:** confirmation, ledger posting, audit, and outbox occur in one idempotent transaction (DB §13.1; F-22).

## 8A. Checkpoint-05 command contracts (API-085..API-105)

All commands below require authenticated Building membership or the stated service authority, a request `Idempotency-Key`, server-derived Building scope, stable `message_key` errors, and one transaction for domain mutation + audit + outbox. Mutations of an existing aggregate require optimistic `expected_version`; create commands do not. A create command instead locks and revalidates its current Building-scoped prerequisites, enforces the stated uniqueness key, and returns either the same result for the same idempotency key/payload or an exact conflict for a changed key payload, lost eligibility, stale prerequisite, or concurrent winner. Reuse of a key with a different payload returns `409 idempotency_conflict`; a stale existing aggregate or prerequisite/deadline/state race returns `409 state_conflict` with the endpoint-specific reason. Reads and notifications expose only Building-authorized, resident-safe profile and financial data; cross-Building existence is concealed as `404`. Unless narrowed below, `400 validation_error`, `401 unauthenticated`, `403 forbidden`, concealed `404 not_found`, and `409 state_conflict` apply.

#### API-085 — Preview Special Assessment distribution · Q
- **Routes/method/auth:** `POST /v1/buildings/{building_public_id}/special-assessment-drafts/preview` and `GET /v1/buildings/{building_public_id}/special-assessment-draft-previews/{assessment_preview_public_id}/distribution?assessment_preview_version=&cursor=&limit=`; authenticated Admin with `finance.record`; side-effect-free, so no idempotency key.

No financial rows are touched; preview consumption, version, Vote/approval invalidation, audit, and outbox are atomic; row lock rejects stale races.

- **Route/method/auth/idempotency:** `POST /v1/buildings/{building_public_id}/special-assessment-drafts/{special_assessment_draft_public_id}/activate`; Admin `finance.record`; key required.

Audit records safe public IDs/versions/authority/correlation, never content text.

**Common query contract.** Amended API-047/049 and the Admin queue use purpose/actor/tenant-bound signed keyset cursors, canonical bounded `limit`, deterministic `activity_at DESC, public_id DESC` ordering, and server-derived `allowed_actions` per item from state/version, immutable authorship, live membership, current Admin authority, reopen usage, and content visibility.

#### API-139 — Reject pending Discussion/Issue revision · C

- **Route/auth/request:** `POST /v1/buildings/{building_public_id}/issues/{issue_public_id}/reject`; live current Building Admin (same predicate as API-050). Body `{ expected_version, rejection_reason }`; `rejection_reason` is mandatory, normalized, nonblank, and non-placeholder (Q212); no content/type/presentation field is accepted.
- **Success/behavior:** `200 { issue_public_id, status:"rejected_revision", rejected_revision_number, lifecycle_version, allowed_actions:[] }`. Appends the immutable decision (revision, reason, acting Admin, authority context, server time, correlation, version); deletes/overwrites nothing; the safe reason becomes visible to the immutable author, who independently derives `revise_and_resubmit`. Approve-first or resubmit-first races conflict per the common contract.

#### API-140 — Revise and resubmit rejected Discussion/Issue · C

- **Route/auth/request:** `POST /v1/buildings/{building_public_id}/issues/{issue_public_id}/resubmit`; immutable original author with current active eligible same-Building membership (Q214). Body `{ expected_version, category?, title?, location_scope?, description?, is_anonymous?, file_public_ids?[] }` is a closed deterministic patch over the latest caller-authorized eligible immutable revision loaded inside the locked transaction; `content_type` is immutable and unsupported (Q215). Omitted content/presentation fields inherit the exact canonical prior value; supplied fields replace only themselves after full canonical validation. Thus required `category`, `title`, and `location_scope` can never resolve null, blank, missing, or unsupported. `description` omitted inherits, non-null normalizes/validates and replaces, and explicit `null` clears only where canonical create/data rules allow it. `file_public_ids` omitted inherits the exact prior authorized set; a supplied array replaces the whole set, empty clears only where canonical content permits content without media, and duplicate/unauthorized/incomplete/cross-Building/unsafe IDs fail atomically. `is_anonymous` omitted inherits; explicit boolean selects presentation only for this new revision. No author/identity, Admin projection, approval/moderation/progress state, Building scope, actor, recipient, timestamp, or unknown field is accepted.
- **Success/behavior:** `201 { issue_public_id, status:"pending", revision_number, lifecycle_version, allowed_actions:[] }`. The server stores a complete immutable normalized snapshot, never a sparse revision and never mutating an earlier snapshot, then returns it to current Admin review (Q213/Q225). It compares that fully materialized snapshot (content, attachment set, and presentation) to the latest immutable revision: identical material returns `409 no_change_detected` and appends nothing; otherwise it is a genuine change. No fixed attempt limit, cooldown, or deadline exists; ended/ineligible membership fails concealed or with safe state. Same-key/same-fingerprint replays; changed payload under the key conflicts; stale/concurrent losers leave no revision, file link, event, notification, realtime, search, cache, or audit-success artifact.

#### API-141 — Admin Issue progress transition · C

- **Route/auth/request:** `POST /v1/buildings/{building_public_id}/issues/{issue_public_id}/progress`; live current Building Admin, reauthorized inside the transaction (Q217). Body `{ expected_version, next_state:"in_progress"|"resolved", resolution_summary? }`. Allowed only for a published `content_type:"issue"` and only for the exact forward step `open -> in_progress` or `in_progress -> resolved` (Q216); `resolution_summary` is accepted only with `next_state:"resolved"`, is optional, and when supplied is normalized, bounded, and sanitized (Q218). No body-edit, priority, assignee, due-date, or `closed` field exists.
- **Success/behavior:** `200 { issue_public_id, progress_state, lifecycle_version, resolution_summary_safe?, allowed_actions }`. Appends the immutable transition event (acting Admin, authority context, prior/next state, server time, version, correlation). Residents cannot call this; a former/replaced Admin or stale version fails without partial effects. Omitted summary blocks nothing.

#### API-142 — Author Issue reopening/relisting request · C

- **Route/auth/request:** `POST /v1/buildings/{building_public_id}/issues/{issue_public_id}/reopen-request`; immutable original author with current active eligible membership. Body `{ expected_version, reason, category?, title?, location_scope?, description?, is_anonymous?, file_public_ids?[] }`; `reason` is mandatory, normalized, nonblank, non-placeholder, and stored separately and immutably from the publication revision (Q219). The optional revision fields use the same closed deterministic patch semantics as API-140: load the latest caller-authorized eligible immutable revision in the lock; omissions inherit; supplied values replace after canonical validation; required fields cannot resolve invalid; `description` has omitted/non-null/null semantics; `file_public_ids` has omitted/inherit versus supplied/full replacement (including allowed empty clear) semantics with atomic file authorization; and `is_anonymous` omitted inherits while an explicit boolean applies only to this candidate. `content_type` remains immutable/unsupported, and unknown/identity/Admin-state/scope/actor/recipient/timestamp fields are rejected.
- **Success/behavior:** `201 { issue_public_id, status:"reopen_requested", revision_number, lifecycle_version, reopen:{ used:true }, allowed_actions:[] }`. A reason-only request is valid: it stores a complete immutable candidate snapshot identical in content/presentation to the last published revision plus the separate reopening reason. API-140's `no_change_detected` rule does not apply. Allowed only from `resolved` with the one-per-aggregate request unused; the Issue remains `resolved` and its prior published revision current while review awaits. Prior progress history, optional resolution summary, comments, and identity-presentation history are retained. A second request returns `409 reopen_exhausted`; idempotent replay consumes nothing; stale/concurrent losers leave no revision, file link, event, notification, realtime, search, cache, or audit-success artifact.

#### API-143 — Admin decide reopening request · C

- **Route/auth/request:** `POST /v1/buildings/{building_public_id}/issues/{issue_public_id}/reopen-decision`; live current Building Admin. Body `{ expected_version, decision:"accept"|"reject", decision_reason }`; `decision_reason` is mandatory, normalized, nonblank, and non-placeholder for both outcomes (Q220); no content/presentation edit field exists.
- **Success/behavior:** accept → `200 { issue_public_id, progress_state:"open", published_revision_number, lifecycle_version, decision_safe, allowed_actions }`: atomically records the explained acceptance, reopens the same aggregate to `open`, and publishes exactly the already-stored candidate snapshot with its selected presentation; it never reconstructs, merges, or accepts content/presentation fields at decision time. Reject → `200 { issue_public_id, progress_state:"resolved", lifecycle_version, decision_safe, allowed_actions:[] }`: the Issue stays resolved with its previously published revision unchanged and the candidate plus reason retained only in authorized history. The safe reason is visible to the author either way. Competing accept/reject/progress/Admin-replacement commands resolve first-valid-atomic-commit-wins with no losing partial event/notification/cache artifact.

#### API-144 — Hide published comment · C

- **Route/auth/request:** `POST /v1/buildings/{building_public_id}/issues/{issue_public_id}/comments/{comment_public_id}/hide`; live current Building Admin, reauthorized at commit (Q222). Body `{ expected_version, hide_reason? }`; `hide_reason` is optional — absence never blocks — and when supplied is normalized, bounded, and sanitized.
- **Success/behavior:** `200 { comment_public_id, hidden:true, lifecycle_version }`. Appends the immutable retained moderation event; never deletes, overwrites, anonymizes, or detaches the comment, its author attribution, anonymity selection, or history. Ordinary resident projections thereafter render the neutral non-identifying hidden placeholder without the optional reason. Concurrent hide/retry is idempotent (already-hidden replays the stored result); no restore, appeal, self-delete, auto-hide, or mass-moderation contract exists.
