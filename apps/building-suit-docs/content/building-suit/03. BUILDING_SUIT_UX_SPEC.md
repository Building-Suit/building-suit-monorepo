# Building Suit User Experience Specification

**Specification status:** Step 2 UX behavior specification under Strict Validation Mode
**Source basis:** `01.BUILDING_SUIT_PRD.md` and `02.BUILDING_SUIT_BRD.md`
**Primary active portal:** Building Suit
**Planned isolated portals:** Shop Suit, Business Suit, City Suit, and Super-Admin

This specification is self-contained for product behavior. It defines user goals, information requirements, task flows, validation, system feedback, permissions, recovery, and where each action leads. It intentionally does not prescribe visual composition, component type, placement, dimensions, color, typography, imagery, or animation.

Use this document alone when the implementing AI or design team should choose the user interface. To apply the optional approved interface direction, also load `03A.BUILDING_SUIT_UI_SPEC.md`. Motion is independently defined in `03B.BUILDING_SUIT_MOTION_SPEC.md` and may be combined with any interface direction. When documents conflict, this UX specification controls product behavior; the UI and motion specifications control only presentation and movement.

The term **Account** refers only to the global authenticated user identity. An Account is connected to one Profile per Portal. Building administrator, owner, tenant, resident, provider, and other labels are roles or participation states, not Accounts.

## 1. Core User Journeys

### 1.1 Authenticate and Enter the Building Suit Portal

1. **Entry Point**
   - The user opens the Building Suit portal directly or follows a Building Suit link.
   - The portal checks for a valid Building Suit session before showing protected content.
2. **User Actions and Immediate System Responses**
   1. If no valid session exists, the system presents Login.
   2. The user either enters a valid Egyptian phone number with a password, chooses Google, or uses Fingerprint Sign-In when it is available. Email login is not part of this checkpoint.
   3. If the user chooses Google, every successful OAuth callback routes to One Last Step before any Profile or Building resolution. One Last Step is exclusive to Google authentication and completes any outstanding required phone verification, Profile fields, and terms acceptance.
   4. Fingerprint Sign-In is shown only when the user previously enabled it on this device after a successful password or Google login. It is never shown as an available action on the first login.
   5. On password submit or fingerprint confirmation, the primary action enters a processing state and prevents duplicate submission.
   6. A successful operating-system fingerprint confirmation unlocks the locally protected session credential; it does not replace server session validation or authorization.
   7. If the credentials and session are valid, the system loads the Account's Building Suit Profile and its active or blocked building memberships.
   8. If the Account's phone number is not yet verified via WhatsApp OTP, the system redirects to phone verification.
   9. Missing or unverified email does not block app access, first login, Home access, building access, or core product usage.
   10. If an active building context was previously selected and remains accessible, the system restores it.
   11. If no previous context is available but at least one accessible building exists, the system selects the first accessible building.
   12. If no accessible building exists, the system presents the Empty State / Welcome screen first.
3. **Final Resolution**
   - The user arrives at the Building Suit Home dashboard with the correct active building context, or at the Empty State / Welcome screen when no building is available.
4. **Failure and Recovery**
   - Invalid credentials remain on Login with an actionable error.
   - An unconfirmed phone moves the user to WhatsApp OTP verification and permits a controlled resend.
   - An unverified email only disables email-dependent actions until the user verifies it from Profile or Account Settings.
   - Failed, cancelled, unavailable, or invalidated fingerprint authentication keeps the user on Login and exposes normal password and Google fallback actions.
   - A failed session refresh clears local authenticated state and returns the user to Login.
   - A network failure keeps the user on the current authentication screen and permits retry.

### 1.2 Register and Verify a New Account

1. **Entry Point**
   - The user selects Register from Login.
2. **User Actions and Immediate System Responses**
   1. Registration always requests Phone and Email together. There is no Email / Phone / Both method-selection step.
   2. Phone is required and must be a valid unique Egyptian phone number. Email is visibly labeled **Optional** beside the Email field and, when provided, must be a valid unique email address.
   3. The user enters full name, required phone, optional email, password, matching password confirmation, and accepts the terms.
   4. The system validates the form before submission and identifies invalid fields.
   5. On successful registration, the system sends a six-digit OTP to the required phone number via WhatsApp.
   6. Phone verification is always required. Registration does not send or require an email verification code.
   7. The user enters the six-digit phone code.
   8. The user may request another code on the same channel only after the resend cooldown expires.
   9. After phone verification succeeds, the system loads the Building Suit Profile.
3. **Final Resolution**
   - The user enters Home when a building membership exists, or the Empty State / Welcome screen when none exists.
4. **Failure and Recovery**
   - Duplicate email and duplicate phone errors are attached to the relevant field.
   - Invalid or expired verification codes remain on the relevant verification screen and permit retry or resend.
   - A failed WhatsApp delivery does not block the resend flow; resend becomes available after the cooldown regardless of delivery status.
   - One Last Step is not used in password registration; it is reserved exclusively for the Google authentication callback.
   - If the user exits phone verification before completing it, the Account exists but phone verification remains pending; the system routes back to phone verification on next login.

### 1.3 Recover or Change a Password

1. **Entry Point**
   - The user selects Forgot Password from Login, or Security from Profile while authenticated.
2. **User Actions and Immediate System Responses**
   1. In recovery, the user enters the verified Egyptian phone number linked to the Account and requests a reset. Email recovery is not part of this checkpoint unless a later explicit decision reintroduces it.
   2. The system confirms the request without exposing whether an Account exists beyond approved error handling and starts a resend cooldown.
   3. The user supplies the valid reset code from the verified WhatsApp phone channel or follows the valid recovery handoff, then enters and confirms a new password.
   4. In authenticated Security settings, the user enters the current password, a new password, and matching confirmation.
3. **Final Resolution**
   - Recovery returns the user to Login after a successful password update.
   - Authenticated password change completes the Security task and displays success feedback.
4. **Failure and Recovery**
   - Invalid or expired recovery credentials remain on the recovery flow.
   - Incorrect current password, weak new password, or mismatch is surfaced without clearing all fields unnecessarily.

### 1.4 Create a Building

1. **Entry Point**
   - An authenticated user selects Create Building from Empty State / Welcome or an approved global entry point.
2. **User Actions and Immediate System Responses**
   1. **Location first:** The user selects or confirms a real location before naming or completing the building. The user may use location detection, a map point, or manual correction where available.
   2. The system immediately returns any buildings already created within the approved approximate five-mile threshold as a discovery list (name, distance, and available administrator contact information where permitted).
   3. The user chooses one of three paths from the discovery result:
      - **Request to Join** a listed building, handing off to Request to Join a Building (UX §1.6).
      - **Create It Myself**, continuing to Step 2 below.
      - **Request Building Suit to Set It Up**, handing off to Request Company-Assisted Onboarding (UX §1.4A) and ending this journey.
   4. The system auto-fills address from the selected location. The address remains editable, and the user may add an optional landmark or distinguishing note, such as "next to a mosque", "in front of a school", or "beside a market".
   5. The system generates the initial building name from the location-derived address. The building name remains editable.
   6. The user enters total number of units and may edit the generated building name.
   7. The system validates that the name is between 2 and 100 characters and that total units is a positive integer no greater than 1,000.
   8. The user states whether they live in the building. If yes, the user selects owner or tenant and supplies a unit number.
   9. On final submit, the system re-checks for nearby buildings within the approved approximate five-mile threshold, since the location may have been refined since the first check.
   10. If no relevant nearby conflict exists, the system creates the building, units, administrator membership, zero-charge trial, and optional creator unit membership.
   11. If nearby candidates exist that were not resolved in the initial discovery, the system presents a blocking conflict modal with candidate identity, distance, and available administrator contact information.
   12. The user either returns to correct the location, contacts or joins an existing building, or explicitly confirms creation despite the warning.
3. **Final Resolution**
   - The building is operationally active immediately after creation.
   - The creator becomes the building administrator.
   - The new building becomes the active context and the system presents completion or Home.
   - A visible setup notice directs the administrator to create billing configuration before configuration-dependent finance operations can proceed. Join requests remain available.
   - Subscription billing begins only after the assigned zero-charge trial ends. After trial it uses the canonical active-unit snapshot with the EGP 200 minimum (UX §1.4A; PRD §3.6).
4. **Failure and Recovery**
   - Step validation prevents forward navigation when required data is missing or invalid.
   - A create conflict does not silently create a duplicate.
   - A failed final submission keeps all wizard data available for correction and retry.

### 1.4A Request Company-Assisted Building Onboarding

1. **Entry Point**
   - The user selects Request Building Suit to Set It Up from the Create a Building location-discovery step (UX §1.4).
2. **User Actions and Immediate System Responses**
   1. The user confirms or adjusts contact details and the captured location, and may supply a known building name, an estimated unit count, and notes for the onboarding team.
   2. On submit, the system creates a pending onboarding request and confirms the published SLA: claimed within 1 business day and fulfilled within 5 business days where the requester provides complete information.
   3. During pilot, the founder personally handles assisted onboarding through the full Super-Admin portal. Temporary internal tooling may support development only and is not the pilot operating surface.
   4. The operator completes the self-service building-detail and optional creator-occupancy information on the requester's behalf after location/discovery/path selection, using information gathered directly from the requester (for example, an owner/resident roster), and records first activation for the units that roster supports.
   5. The operator marks the request fulfilled.
3. **Final Resolution**
   - The requester receives administrator access to the newly created building and an in-product notification that onboarding is complete.
   - The Building is operationally active from creation and receives the same zero-charge trial and post-trial active-unit billing formula as a self-service Building (PRD §3.6).
   - First activation reflects verified occupancy the operator recorded; it does not change the active-unit definition used for governance (PRD §3.2 Activation distinction).
4. **Failure and Recovery**
   - The requester may cancel a pending request at any time before fulfillment and switch to self-service creation (UX §1.4) instead.
   - A Platform Operator may reject a request with a required reason; rejection does not block the requester from creating the building themselves afterward.
   - Concurrent claims by two operators are prevented; only one operator holds an active claim at a time.

### 1.5 Configure Initial Billing

1. **Entry Point**
   - The administrator follows the missing billing configuration action from Home, Finance, or Building Settings.
2. **User Actions and Immediate System Responses**
   1. The system opens Building Settings focused on Billing.
   2. The administrator creates a billing configuration with the required positive amount and a due day from 1 through 28.
   3. The administrator may set the configuration active or inactive and edit or remove configurations where policy permits.
   4. The system validates whether the selected configuration can support the requested finance operation and whether referenced configurations may be changed or removed.
3. **Final Resolution**
   - Configuration-dependent finance actions become available when all other permission and subscription conditions are satisfied. Building activation and join requests are unchanged.
4. **Failure and Recovery**
   - Invalid values remain available for correction with field guidance.
   - Attempts to remove a configuration that must be retained for financial integrity are rejected with an explanation and recovery action.

### 1.6 Request to Join a Building

1. **Entry Point**
   - An authenticated user selects Join Building from Empty State / Welcome or an approved global entry point.
2. **User Actions and Immediate System Responses**
   1. The user enters or scans a valid building join identifier.
   2. The user selects or enters the target unit and chooses owner or tenant.
   3. The system validates the identifier, unit, selected role, and building eligibility. Billing configuration is not a join prerequisite.
   4. On submit, the system creates a pending join request and confirms that administrator approval is required.
3. **Final Resolution**
   - The user sees a pending approval state and can return to accessible Building Suit content.
4. **Failure and Recovery**
   - Invalid join identifier, unavailable unit, or duplicate request is surfaced with a direct correction path.

### 1.7 Review and Resolve Join Requests

1. **Entry Point**
   - A building administrator opens pending approvals from Home.
2. **User Actions and Immediate System Responses**
   1. The system lists pending join requests for the active building.
   2. The administrator reviews requester identity, requested unit, and requested owner or tenant role.
   3. The administrator selects Approve or Reject.
   4. If the requested role is already occupied, the system blocks normal approval and presents an explicit replacement decision.
   5. The administrator may confirm Replace Occupant, cancel, or reject the request.
   6. Rejection requires a reason.
3. **Final Resolution**
   - Approval creates the active membership and occupancy assignment.
   - Explicit replacement ends the prior occupancy while retaining history and activates the requester.
   - Rejection closes the request and notifies the requester.
4. **Failure and Recovery**
   - Concurrent occupancy changes return a conflict and refresh the request before another decision.
   - The system never replaces an owner or tenant implicitly.

### 1.8 Switch the Active Building

1. **Entry Point**
   - Normal authenticated navigation exposes the available building contexts.
   - A protected Building Select destination is used when a building-required destination is opened without an active building, and it may also be entered directly.
2. **User Actions and Immediate System Responses**
   1. Building selection lists accessible active and blocked memberships with building name, location, combined role labels, and active-context indication.
   2. Building Select presents the same building-context choices and also exposes Create New Building and Join Another Building.
   3. The user selects another building from either entry point.
   4. The system closes subscriptions and context-specific cached views for the former building.
   5. The system loads the selected membership, permissions, building data, and scoped realtime subscriptions.
3. **Final Resolution**
   - Home opens in the newly selected building context.
4. **Failure and Recovery**
   - If access was removed, the building is removed from selectable contexts and the system chooses another accessible building or returns to the Empty State / Welcome screen.
   - Building-scoped data from the prior context must not remain visible after switching.
5. **Entry-Point Relationship**
   - Building selection is available through normal authenticated navigation and through Building Select for recovery or direct entry. Both load the chosen building and then open Home.

### 1.9 Manage Members and Occupancy

1. **Entry Point**
   - The administrator opens Home and selects Members or Units.
2. **User Actions and Immediate System Responses**
   1. The administrator searches or filters members and units.
   2. The administrator opens member or unit detail without leaving the Home context.
   3. The administrator may block, unblock, or remove a non-final-administrator membership and must supply a reason when required.
   4. If a member has multiple unit relationships, the administrator selects the affected relationship.
   5. Before removal, the system presents the financial consequence:
      - Any old Occupancy Credit or debt remains tied to the old resident and old occupancy period.
      - The system does not create an automatic settlement expense, refund, or debt transfer.
      - The next resident starts from zero and does not inherit the old balance.
      - If money is later paid back outside the app, the administrator records `Unit Settlement Expense`; if the old resident later pays old debt, the administrator records `Past Resident Payment` / `Late Settlement`.
   6. When registering or replacing an Owner, if old owner-related obligations exist, the system requires a review before completion:
      - Classify each item as `Old Owner Debt`, `Unassigned Owner Responsibility`, or `Pre-First-Owner Unit Obligation`.
      - Show allowed actions by type: Old Owner Debt is informational only; Unassigned Owner Responsibility can be assigned to new Owner, left unassigned, or waived with reason; Pre-First-Owner Unit Obligation defaults to first Owner unless waived with reason.
      - If an obligation is assigned, show the Owner acknowledgment requirement and whether in-app or external acknowledgment is needed before it becomes payable.
      - Disputed assigned items move to `Disputed / Under Review`, do not become payable, do not block Owner registration, and remain visible to Admin for later documented resolution.
   7. The administrator explicitly confirms the action.
3. **Final Resolution**
   - Membership status and occupancy are updated, history remains available, and affected parties receive appropriate feedback.
4. **Failure and Recovery**
   - The final administrator cannot be removed without a replacement.
   - Blocked users retain approved read access but cannot perform writes.
   - Concurrent membership changes produce a conflict and refresh the view.

### 1.10 Review Building and Unit Financial Position

1. **Entry Point**
   - The user opens Finance or an authorized Unit Financial History destination.
2. **User Actions and Immediate System Responses**
   1. The system resolves the user's active building membership and permitted financial visibility.
   2. An administrator sees building wallet balance, manual balance, total balance, collected but not yet available for withdrawal, reserved withdrawal amount, available balance for withdrawal/use, collections, outstanding and late units, bucket-scoped credits, recent transactions, and finance actions.
   3. An owner or tenant sees only permitted unit balances, unit history, collection summary, manual payment instructions, and separated finance sections for `Monthly / Occupancy Dues`, `Owner Obligations / Special Assessments`, and `Disputed / Under Review`.
   4. A multi-unit user can switch among their permitted units.
   5. The user may open the filtered ledger or a permitted unit history.
3. **Final Resolution**
   - The user reaches a current, role-appropriate financial view whose ledger remains the source of truth.
4. **Failure and Recovery**
- Missing billing setup blocks configuration-dependent finance writes and offers configuration to the administrator.
   - Locked or cancelled subscription status makes the building read-only and blocks all building writes, while preserving approved historical reads.
   - Blocked members receive read-only access where supported and no payment or write action.

### 1.11 Record a Manual Payment

1. **Entry Point**
   - The administrator selects Record Payment from Finance or an authorized Unit Financial History view. Manual payment recording remains permanently available after Paymob goes live.
2. **User Actions and Immediate System Responses**
   1. The administrator selects the target unit or resident context.
   2. The administrator selects one due bucket/type, enters a positive amount, selects cash, instapay, wallet, or other, and may add a note.
   3. The system validates the target, amount, method, permissions, subscription state, and billing readiness.
   4. A confirmation step summarizes the selected due bucket, current due in that bucket, applicable credits/discounts, excluded credits from other buckets/scopes, amount being paid, excess amount if any, new credit created by overpayment, remaining due, and final method effect before submission.
   5. If the selected bucket is `Monthly / Occupancy Dues`, excess becomes `Occupancy Credit` for the current occupancy period only. If the selected bucket is `Owner Obligations / Special Assessments`, excess becomes `Owner Obligation Credit` for the Owner/ownership/unit scope. Equalization Credit applies only where entitlement and bucket rules allow, or is settled through payout, never both.
   6. On confirmation, the system records the payment in the ledger and reduces only the selected bucket/scope balance.
   7. If wallet is selected, the system also deducts the amount from the wallet balance.
3. **Final Resolution**
   - The task completes, updated balances and ledger data appear, and concise success feedback confirms completion.
4. **Failure and Recovery**
   - Invalid or stale target data remains editable.
   - A duplicate or uncertain submission is reconciled before permitting another attempt.
   - Regular residents never directly record authoritative manual payments. Platform Operator support for manual-payment operations is available only where privileged support access explicitly permits.

### 1.12 Create a Charge or Generate Recurring Charges

1. **Entry Point**
   - The administrator selects Add Charge or Generate Recurring Charges from Finance.
2. **User Actions and Immediate System Responses**
   1. For a one-off charge, the administrator selects a unit, due bucket/type, positive amount, due date, and description where applicable.
   2. For recurring generation, the administrator selects an approved billing configuration and target eligible active occupancy units. Automatic monthly generation runs at the beginning of each month; manual Admin generation/retry is available for first month, technical failure retry, post-configuration generation, and operational recovery.
   3. The system previews the intended action and warns about duplicate monthly charges.
   4. The administrator confirms.
   5. The system creates eligible ledger charges and skips or rejects duplicates.
   6. For `Special Assessment with Deferred Equalization`, the Admin previews proposed participating/deferred Units, funders, fair shares, Owner responsibility, Deferred Equalization, dates, and documents. Confirmation creates only the draft and linked Money Vote; the screen states zero debt/obligation/ledger/credit/balance effect. Only a separate post-vote API-088 activation confirmation creates financial effects.
3. **Final Resolution**
   - Unit receivables and the ledger reflect the created charges, with a result summary for generated and skipped items.
4. **Failure and Recovery**
   - Invalid amount, inaccessible unit, missing billing setup, subscription lock, or duplicate conflict is explained without creating partial hidden results.

### 1.13 Record an Expense

1. **Entry Point**
   - The administrator selects Record Expense from Finance.
2. **User Actions and Immediate System Responses**
   1. The administrator enters a required title, positive amount, and optional description.
   2. If the amount exceeds the current manual balance, the system warns that the balance will become negative but does not block the approved action.
   3. For an ordinary expense, the administrator selects or confirms the underlying spending purpose/project. The UI suggests/reuses safe recent matches and narrows relevant successful Money Vote authorizations without hiding the final explicit relationship. If authorization is required or chosen, selecting the relevant Vote is mandatory before confirmation and the summary shows winning base amount, tolerance, maximum authorized amount, cumulative consumed amount, remaining authorization, and validity/commitment state.
   4. For a no-vote ordinary expense, the summary shows the Building's effective no-vote spending limit and useful source/provenance plus the cumulative amount already assigned to the purpose. The client never treats a new row as a fresh threshold. Emergency Expense continues through its separate flow.
   5. The administrator confirms the summarized expense; posting and Vote attachment are one server-authoritative operation and there is no post-first/link-later path.
3. **Final Resolution**
   - The ledger records the expense, the manual balance updates, and success feedback appears.
4. **Failure and Recovery**
   - Invalid fields remain editable.
   - Permission, billing, or subscription failures keep the confirmation context available for recovery.

### 1.14 Request a Wallet Withdrawal

1. **Entry Point**
   - The administrator selects Withdraw from Finance.
2. **User Actions and Immediate System Responses**
   1. The administrator enters a positive amount no greater than the available balance after settlement-pending collections and existing withdrawal reservations are excluded.
   2. The administrator enters a new bank-account or e-wallet destination, or selects a destination saved by the device, browser, or Paymob experience only when that capability is supported. Building Suit does not present a building-owned or Admin-owned beneficiary list.
   3. The system validates balance, daily-limit availability, destination type, permission, subscription eligibility, and any threshold-based step-up requirement.
   4. When the amount is at or above the Super-Admin-configured threshold, the system requires a re-login-like confirmation using password or already-enabled supported device biometrics. The administrator does not re-enter a phone number and no OTP is used.
   5. The system presents a confirmation summary with withdrawal amount, final withdrawal fee, total reserved amount, destination type, masked destination data when available, daily-limit impact, reserved-balance impact, and the fact that the request cannot be cancelled after submission. If a final fee cannot be shown before request creation, that payout method is not available in MVP.
   6. On confirmation, the system creates one withdrawal record in `Pending`, reserves building balance and daily-limit capacity for the immutable `withdrawal_limit_day`, and shows submission/progress status.
   7. The system waits for a trusted Paymob callback/webhook or documented reconciliation evidence to move the withdrawal forward. Browser return state and client-side success screens are not authoritative.
3. **Final Resolution**
   - Authorized residents see the withdrawal immediately while it is `Pending`. The compact ledger row shows one primary record; opening it shows a resident-safe status timeline.
   - `Pending` and `Requires Review` are shown as held/reserved money, not completed outflows.
   - A trusted final outcome shows `Confirmed`, `Failed`, or `Reversed`. A documented review with no final external outcome keeps the primary status `Requires Review` and adds a `Still Pending` review-outcome event to the timeline.
4. **Failure and Recovery**
   - No Building Admin cancellation action is available after submission.
   - If Paymob does not provide a final callback within the Super-Admin-configured duration, the item moves to `Requires Review`, remains reserved, and appears in the Super-Admin operational review queue.
   - Platform Operator / Super-Admin review may record `Confirmed`, `Failed`, or `Reversed` as primary status changes only with Paymob reference or documented reconciliation evidence. A `Still Pending` review outcome is allowed only while the primary status remains `Requires Review`; it leaves balance and daily-limit reservations held and posts no final outflow.
   - After `Failed` or `Reversed`, reservations are released and the administrator may create a new independent withdrawal.

### 1.15 Review Ledger and Export Financial History

1. **Entry Point**
   - The user opens Ledger from Finance.
2. **User Actions and Immediate System Responses**
   1. The system displays ledger metrics and transactions permitted for the user's role and unit relationships.
   2. The user filters by transaction type and date range; administrators may additionally filter by unit.
   3. The system updates results and metrics to the applied filter.
   4. The user loads additional results as available.
   5. The user requests an export of filtered or complete permitted results.
3. **Final Resolution**
   - The user reviews or receives the requested permitted financial history.
4. **Failure and Recovery**
   - An export failure leaves filters and results intact and permits retry.
   - Users never receive ledger data outside their approved building and unit visibility.

### 1.16 View Manual Payment Instructions

1. **Entry Point**
   - An owner or tenant selects the payment action for an eligible unit.
2. **User Actions and Immediate System Responses**
   1. The system opens manual payment instructions without implying an online transaction.
   2. The user reviews the building's available instructions and can return to unit history.
3. **Final Resolution**
   - The user understands how to pay through an approved external/manual method; an administrator later records the payment.
4. **Restriction**
   - Paymob collection is not active until merchant onboarding, KYC, contracting, legal/compliance validation, callback verification, reconciliation testing, support procedures, and runbook readiness are complete.
   - The first Paymob release must cover both resident-to-building collection and Building Suit SaaS subscription billing.
   - The portal must not label a browser return or instruction view as payment confirmation.

### 1.17 Create and Resolve an Issue

1. **Entry Point**
   - An unblocked user opens Community, selects Support, and chooses Create Issue.
2. **User Actions and Immediate System Responses**
   1. The user enters required title and category.
   2. The user selects the required location scope (`unit`, `building`, or `common_area`) and may add description, media, camera content, or the MVP anonymous preference.
   3. On submit, an administrator-created issue opens immediately; a resident-created issue enters pending approval.
   4. An administrator reviews pending issues and approves or rejects them.
   5. Participants open issue detail, review retained history, and add comments containing text and/or media while the issue is open.
   6. The issue author or administrator closes the issue.
3. **Final Resolution**
   - The issue reaches open, rejected, closed, or retained archived status as approved, with history and comments preserved.
4. **Failure and Recovery**
   - Blocked users cannot create, comment, approve, reject, or close.
   - A failed comment remains available for retry.
   - The system must not describe retained issue history as destructive deletion.

### 1.18 Publish and Acknowledge an Announcement

1. **Entry Point**
   - An authorized administrator opens Community, selects Support, and chooses Create Announcement.
2. **User Actions and Immediate System Responses**
   1. In Community -> Support, announcements are prioritized before issues. Active and Closed filters are always available; Action Required is available to non-administrators for active RSVP announcements they have not acknowledged. Authorized administrators can create announcements from this context.
   2. The administrator enters required title and message.
   3. The administrator selects normal or urgent priority, a positive duration/end time, and whether RSVP acknowledgement is required.
   4. The system presents a confirmation before publishing.
   5. On publish, the announcement becomes active; urgent announcements are ordered ahead of normal announcements.
   6. Home includes active announcements after task-critical warnings and before general overview information. Urgent announcements are ordered ahead of normal announcements.
   7. Opening an announcement from Home or Community shows Announcement Detail while preserving the originating context and records read state for the current Profile.
   8. If RSVP is required, the user acknowledges it from detail.
   9. The administrator can review read and RSVP metrics and close the announcement.
   10. Announcement-type notifications are prioritized as Important Broadcasts before standard notifications in the complete notification history.
3. **Final Resolution**
   - The announcement closes at its approved end time or through an approved close action, with read and RSVP state retained.
4. **Failure and Recovery**
   - Invalid duration or missing required content remains editable.
   - Destructive announcement deletion is not specified by the approved requirements.

### 1.19 Create, Approve, and Cast a Normal or Money Vote

1. **Entry Point**
   - An unblocked user opens Community, selects Governance, and chooses Create Vote.
2. **User Actions and Immediate System Responses**
   1. The user selects normal or money vote. For Money, the user then selects the explicit typed topic `Spending authorization` or `Change the no-vote spending limit`; the UI submits the server contract value and never infers topic from title, description, labels, amount, or category.
   2. For `spending_authorization`, the user enters one spend proposal or multiple spend alternatives with structured amounts and exactly one explicit no-spend option. Tolerance starts visibly at 0%, calculated maximum exposure is prominent, purpose is explicit, and execution-validity duration is selected within the current Money Vote-constraint policy. For `no_vote_limit_change`, the user enters only one proposed EGP limit: the screen renders server-resolved current limit/provenance, current Building policy version, applicable platform maximum/version, and exactly the read-only semantic choices **Approve proposed limit** and **Keep current limit**. It provides no option-label editor, extra alternative, no-spend row, tolerance, validity, purpose, or exposure control.
   3. The system explains that a resident-created ordinary vote request requires administrator approval, remains visible only to the author and current Building Admin while `pending_approval` or `overdue`, and that the author cannot vote if the request is approved.
   4. An administrator-created normal or money vote opens directly. A resident-created ordinary vote request enters `pending_approval` with the assigned review deadline.
   5. Before Admin decision, the author may edit or withdraw the same request. Withdrawal preserves it for author editing/resubmission, but removes it from current-Admin product views; other residents never see it. Internal audit retention is not an Admin-facing history surface.
   6. The administrator approves or rejects pending or overdue ordinary requests. Rejection requires a reason, creates no Vote, and keeps the rejected request/version visible only to the author and current Admin.
   7. The request becomes `overdue` when the assigned review duration expires; the overdue state never approves or rejects the request automatically.
   8. A rejected or withdrawn request can be edited and resubmitted as the same request, preserving all previous history. Rejected resubmission shows a full new review window calculated from resubmission. A withdrawn request has no resubmission deadline: while the author's same original Building membership remains active and the author currently satisfies submission eligibility, the author may open the withdrawn request, review/edit it, and resubmit it with the normal Submit action at any later time (§8.9). No expiry, countdown, review window, or extra confirmation step is displayed for a withdrawn request.
   9. Eligible participants open vote detail and review activation, participation, eligibility, typed topic, options, and results visibility. A limit-change detail preserves the frozen current/proposed/maximum values, provenance/policy snapshots, fixed choices, status, result, and applied/not-applied state.
   10. The participant selects one option and confirms the vote.
   11. The system applies the selected option to all eligible active units represented by that participant, subject to tenant priority and all other eligibility rules.
3. **Final Resolution**
   - A valid vote reaches closed with plurality results after satisfying the required participation threshold.
   - Normal votes require at least 50% participation. Money votes require at least 70% participation.
   - A valid `approve_proposed_limit` win is applied only by the trusted atomic close and shows the new effective limit, `building_money_vote` provenance, and applied state. `keep_current_limit`, tie, no quorum, expiry, cancellation, or failure shows not applied and leaves value/provenance/protection unchanged. No limit result displays or implies a financial authorization, Expense, payable, reservation, Special Assessment, balance, or ledger effect.
   - An approved ordinary vote can show a Building Admin cancellation action only before the first vote is recorded; cancellation requires a reason and retains the vote/request history. Once the first vote is recorded, no cancellation action is available.
4. **Failure and Recovery**
   - The author, administrator, ineligible owner when an active tenant exists, blocked member, or participant with no eligible unit cannot cast.
   - A participant cannot cast twice for the same eligible unit.
   - Vote duration is resolved as a positive duration from one through seven days. Ten-day behavior is not approved.
   - Mixed topic payloads, client-authored limit choices, a proposed value equal to current or above the snapshotted maximum, or a second open limit-change ballot show canonical field/state errors without changing any existing Vote or policy.
   - Admin review timeout creates `overdue` only; it does not approve, reject, or publish the request.

### 1.20 Admin Replacement Cycle

1. **Entry Point**
   - Any voting-eligible active Owner/resident other than the incumbent opens Governance and selects **Nominate myself for Building Admin** when no replacement cycle is active. No cooldown, current-Admin approval, Platform approval, prior warning, or supporter threshold exists.
2. **User Actions and Immediate System Responses**
   1. The member reviews their own resident-safe candidate profile/reason and confirms self-nomination. Nobody can nominate another person, so no nominee-acceptance step exists.
   2. Confirmation creates exactly one cycle with the current Admin as incumbent and the self-nominating member as the sole challenger. The system blocks another active cycle or challenger.
   3. The normal schedule displays the challenger's safe profile/reason for a fixed 24-hour announcement, then opens a three-day vote without Admin action. The self-nomination form never asks for and never accepts an election title; the cycle heading, label, and summary are generated by the system from the incumbent-versus-challenger identities. Challenger withdrawal during announcement or voting, or trusted challenger-ineligibility termination while the cycle is nonterminal, is an approved exception that ends the schedule with no winner or Admin transfer.
   4. Every eligible Unit voter—including the incumbent and challenger—votes under the same one-vote-per-active-Unit and tenant-priority rules. Candidate status grants no extra vote. A resident who becomes the currently eligible occupant of an existing Unit while the cycle is open sees the ballot and may cast that Unit's vote; a vacant Unit gaining a resident never adds a Unit to the denominator.
   5. The selected choice is final when submitted: the voter can never change or withdraw it. While open, authorized ordinary members see live Unit-based participation/progress only and no exact candidate totals or Unit/person-to-choice mapping. Internal tallies remain exact/immediate, and finalized totals follow existing result rules. The single supersession exception is step 7.
   6. On the normal nonterminated path, the result is finalized by the server automatically at the earlier of the scheduled deadline or the moment every currently eligible Unit already holds an effective vote and no eligible Unit can still cast a first one. Reached quorum alone or an apparent majority alone never closes or decides the ballot early. No screen, menu, or role exposes a `Close election`, `Approve result`, `Finalize`, `Extend`, or `Cancel result` control — not for the Admin, incumbent, challenger, resident, Super Admin, or Platform Operator. Challenger withdrawal or trusted challenger-ineligibility termination may still end the nonterminal cycle earlier, with no winner or Admin transfer. At finalization, 50% normal-governance quorum applies; challenger majority wins, while incumbent majority, tie, or no quorum preserves the incumbent.
   7. If the Unit already holds an effective vote cast by a previous occupant, the newly eligible resident sees the same neutral ballot and may submit. Occupancy change alone changes nothing and the UI never announces a previous vote. On successful atomic supersession, participation remains one effective vote for that Unit and no surface states the previous/new choice, Unit, voter, or per-candidate −1/+1 delta. On failure, the ballot returns a safe error and the previous vote remains effective. DEC-16/ARCH-OPEN-13/SEC-ADR-09 are closed by the participation-only open-ballot projection.
   8. If a repeat self-nomination matches the same still-serving incumbent, the same challenger, and the same Building after a previous terminal cycle, any retry indication shown is derived by the system from prior cycle history. The resident performs no extra step, ticks no checkbox, and enters no label to mark it as a retry.
3. **Final Resolution**
   - A challenger win atomically transfers the role with a complete audit record and no zero-Admin state. Any other completed outcome preserves the incumbent. No outcome creates a cooldown, so a new eligible self-nomination may start immediately after the cycle becomes terminal.
4. **Failure and Recovery**
   - The challenger may withdraw during announcement or voting while the cycle is nonterminal. The UI immediately resolves the cycle as `cancelled_challenger_withdrawn`; recorded votes remain visible only as immutable audit history and cannot produce a winner or Admin transfer. The incumbent cannot block or decide withdrawal, no cooldown applies, and eligible self-nomination reopens after the terminal commit.
   - Withdrawal/open/close races resolve to exactly one terminal result. Lost challenger eligibility likewise produces no winner and preserves the incumbent with no cooldown. Its trusted trigger/timing is a Derived Technical Open Item under ARCH-OPEN-12/DB-OPEN-14/SEC-ADR-08, owned by Engineering and Security rather than the incumbent.
   - No third candidate, second round, automatic periodic election, or resignation completion into a zero-Admin state exists. A later handover/resignation path must preserve exactly one active Admin; its separate successor mechanics are not redefined by election self-nomination.
5. **Required Ballot and Result States**

| State | Trigger | Required presentation |
|---|---|---|
| Loading | Cycle or tally fetch in flight | Skeleton for heading, countdown, options, and aggregate bars. Never render a partial tally as final, and never render a submit control until eligibility resolves. |
| Eligible to cast | Viewer is the Unit's currently eligible voter and the Unit has no effective vote | Ballot with two system-labelled options and a final-submission confirmation. |
| Eligible to replace | Viewer became the Unit's currently eligible voter while an earlier occupant's effective vote exists | Same neutral ballot and the same finality confirmation. No message states or implies that a previous vote exists, was cast, or was invalidated. |
| Already cast by viewer | Viewer holds the Unit's effective vote | Read-only participation confirmation with no change or withdraw affordance and no echo of the chosen option. |
| Not eligible | Viewer is not the Unit's current eligible voter, or holds no eligible Unit | Aggregate view only, with a plain reason and no submit control. |
| Stale cycle state | Client version differs from server, or the cycle advanced since load | Non-destructive refresh prompt; the client re-reads server state and never resubmits or recomputes a result on its own. |
| Supersession failure | Replacement vote rejected or rolled back | Recoverable error, unchanged published participation/progress, ballot still submittable. The failure message never reveals whether an earlier vote exists or what it was. |
| Concurrent finalization | Result committed while the viewer was submitting or waiting | Submission is refused as already-finalized and the surface switches to the terminal result. Exactly one terminal outcome is ever shown; no duplicate or conflicting result appears. |
| Already finalized | Cycle is terminal on load | Read-only outcome with reason (`challenger majority`, `incumbent retained`, `tie`, `no quorum`, `withdrawn`, `challenger ineligible`). No submit, close, approve, reopen, or edit control for any role. |

   - Every state above must render correctly in Arabic with RTL mirroring of layout, countdown, and aggregate bars, using the same system-generated incumbent/challenger labels; numerals, dates, and durations follow the already-approved localization rules.

## 2. Interaction Flows & Information Architecture

### 2.1 Portal Boundary Model

1. Building Suit is a self-contained portal with its own Profile, navigation, building context, permissions, and scoped data.
2. Shop Suit, Business Suit, City Suit, and Super-Admin are separate portal deployments. Their internal interaction flows are not approved in the current requirements and are therefore not specified.
3. Cross-portal links open the target portal and trigger target-portal session, Profile, and permission resolution.
4. No portal embeds or mounts another portal's protected routes.

### 2.1.1 Internal Leadership Reporting Boundary

1. Leadership reporting is not shown in Building Suit resident or Building Administrator navigation.
2. During development, a restricted internal dashboard or recurring export may temporarily support Finance / Revenue Operations and Product Leadership.
3. During pilot, approved Platform Operators use the separately deployed full Super-Admin portal for leadership reporting and related operations.
4. The reporting UX distinguishes registered, configured, active, and paid Buildings; forecasts from realized revenue; and the approved adoption, retention, revenue, and feature-usage metrics.
5. Reporting access is least-privilege and audited; report controls do not mutate Building Suit domain records.

### 2.2 Building Suit Global Navigation

1. **Unauthenticated flow**
   - Portal Entry -> Login
   - Login -> Register (required phone + optional email) -> Verify Phone (WhatsApp OTP) -> Empty State / Welcome or Home
   - Login -> Forgot Password -> Reset Password -> Login
   - Login -> Google OAuth Handoff -> Callback -> One Last Step -> Empty State / Welcome or Home
   - Login -> Fingerprint -> session validation -> Empty State / Welcome or Home, only after fingerprint was enabled following a prior successful login
2. **Authenticated destinations and global capabilities**
   - Primary destinations: Home, Finance, Community, and Profile.
   - Globally available capabilities: identify the current destination, review notifications, choose an accessible building, switch active building, create a building, join a building, change language and appearance preferences, and log out.
   - Building Select remains available as the protected recovery destination described in Section 1.8.
   - Moving between primary destinations preserves the authenticated Account and valid active-building context.
   - A focused task must provide a clear way to return to its originating destination.
3. **Context rules**
   - Home, Finance, and Community operate in the active building context.
   - Profile does not require an active building.
   - Unit Financial History and Ledger require an active building and authorization.
   - Building Settings requires administrator role in the active building.
   - A user without an accessible building sees the Empty State / Welcome experience before building selection and may choose Create Building, Join Building, or Explore the App.
   - Explore the App enters the authenticated product without creating or joining a Building. Building-scoped data and actions remain unavailable, while Profile, Create Building, and Join Building remain accessible.

### 2.3 Authentication Flow

1. Login -> Home when authenticated and a building context is available.
2. Login -> Empty State / Welcome when authenticated with no accessible building.

Email login/recovery is not part of this checkpoint. One Last Step is exclusive to Google authentication.

- **No occupancy history visible:** Show no retained occupancy records.

#### Loading and Processing States

- Initial fetch communicates loading for both metrics and results.
- Filter changes preserve the current ledger context while results refresh.
- Load more communicates append progress without replacing loaded results.
- Export shows progress and prevents repeated export requests.

### 3.7 Support, Issues, and Announcements

#### Ideal State

- Support shows announcement state filters, issue filters, counts, and role-appropriate creation actions.
- Announcements are prioritized before issues.
- Issue detail shows issue state, retained history, comments, attachments, and permitted controls.
- Announcement detail shows priority, message, remaining duration, read/RSVP status, and administrator metrics.

#### Empty States

- **No announcements in selected state:** Show no announcements; authorized administrator receives Create Announcement.
- **No issues in selected filter:** Show no issues; unblocked user receives Create Issue where permitted.
- **No issue comments:** Show no discussion yet while retaining the comment composer only when allowed.
- **No pending issues:** Administrator sees no requests requiring review.

#### Loading and Processing States

- Lists communicate loading without replacing already loaded content.
- Infinite lists show append progress without replacing loaded items.
- Issue and announcement detail communicate loading until authoritative data is available.
- Comment upload and send show progress; failed content remains available for retry.
- Approve, reject, close, RSVP, and publish actions prevent duplicate submission.
- Realtime comments append without forcing the user away from their current scroll position; unseen appended comments show an unread indicator.

### 3.8 Governance

#### Ideal State

- Shows activation status, active/pending/overdue/closed vote filters, eligibility, participation, quorum, options, results, and permitted controls.
- Pending, overdue, and rejected ordinary request detail is visible only to the author and current Building Admin. After pre-decision withdrawal, the author alone retains product-facing request/history access; the current Admin loses the surface and other residents remain denied. Internal audit retention never appears as Admin history.
- Author view exposes Edit, Withdraw, and Resubmit only in the allowed states. Admin view exposes Approve/Reject for `pending_approval` and `overdue`; Admin never sees resident-content edit controls.
- Approved ordinary vote detail exposes Cancel only before the first recorded vote and requires a reason. After the first recorded vote, cancellation is absent or disabled with the explicit state reason.

#### Empty States

- **No votes in selected state:** Show no votes and offer Create Vote only to unblocked eligible users.
- **No pending approvals:** Administrator sees no ordinary vote requests awaiting review.
- **Overdue approvals:** Administrator sees overdue request count, overdue age, and the retained original review deadline without implying automatic decision.
- **No governance activity:** Show no recent governance activity.
- **Building below 60% activation:** Show the activation requirement and disable vote creation/casting where required.

#### Loading and Processing States

- Vote lists and detail communicate loading until authoritative data is available.
- Cast, approve, reject, edit, withdraw, resubmit, close, and cancel actions use blocking action progress within the active task.
- The system must prevent repeat cast attempts while the first cast is unresolved.
- Realtime vote results update the open detail without changing the user's selection state unexpectedly.

### 3.9 Future Services and Provider Scope

#### Ideal State

- No active MVP state exists for provider directory browsing, provider contact, or provider profile management.
- Any future provider experience must be defined in a post-MVP UX revision before implementation.

#### Empty States

- No active MVP empty state exists for provider search or provider profile creation.

#### Loading and Processing States

- No active MVP loading or processing state exists for provider browsing, contact, creation, editing, or moderation.

### 3.10 Profile

#### Ideal State

- Shows Account name/email/phone, Building Suit display name, accessible memberships, administrator shortcuts when applicable, preferences, Security with Fingerprint Sign-In toggle when supported, and logout.

#### Empty States

- **Legacy Account with no phone:** Show Not Set with Add and Verify Phone. A Google callback handles this on One Last Step; non-Google Accounts use the normal profile phone flow.
- **No accessible building memberships:** Show no buildings and preserve access to Explore the App, Profile, Create Building, and Join Building.
- **All visible memberships blocked:** Show each with Restricted state and no write actions.

#### Loading and Processing States

- Initial profile data communicates loading for identity and memberships.
- Profile update, password update, leave building, and logout confirmation actions show progress.
- Preference changes apply immediately and persist.

### 3.11 Notifications

#### Ideal State

- Recent Activity preserves the current context and provides access to the complete notification history.
- The complete history prioritizes Important Broadcasts before standard notifications and groups standard notifications by date.
- Unread state updates from realtime events.

#### Empty States

- **No notifications:** Communicate All Caught Up with no action.

#### Loading and Processing States

- The complete history communicates initial loading until authoritative data is available.
- Cached notifications may remain visible during background refresh.
- Notification items remain display-only; there is no visible per-item or mark-all-read processing state.

### 3.12 Unauthorized and Cross-Portal Access

#### Empty States

- Portal handoff uses a blocking session and Profile resolution state.
- No protected target content is displayed before permission resolution.

## 4. Validation & Interaction Behavior

### 4.1 Validation Execution Standard

1. Required markers and constraints are visible before submission.
2. Format and simple field validation fires on blur after the user has interacted with a field.
3. Cross-field, permission, subscription, uniqueness, balance, occupancy, and conflict validation fires on submit.
4. Submit always revalidates the complete form, regardless of prior client validation.
5. Server validation remains authoritative and maps actionable safe details to the relevant field or form-level message.
6. Invalid fields receive explicit, programmatically associated error feedback; focus moves to the first invalid field after submit.
7. Correcting a field clears its stale field error once it becomes valid.
8. Primary actions remain disabled only when required data is visibly incomplete, an action is processing, or the user is known to be ineligible.
9. This specification defines validation behavior without prescribing a shared form-validation framework.

#### 4.1.1 Field Label Behavior

1. Every input that accepts user-entered text must have a persistent, associated label that communicates the expected value.
2. Authentication-family inputs use the floating label pattern: the visible label starts inside an empty, inactive field, then moves to a persistent top position when the field is focused or filled.
3. The label must never disappear, be replaced by placeholder text, or become the only cue available through motion. Placeholder or example text is supplemental and may appear only when it does not compete with the label.
4. Optional, required, read-only, disabled, error, and helper states remain programmatically and visually associated with the same field label.
5. The behavior must work in English and Arabic, with labels, examples, errors, and optional markers preserving a clear relationship to the field in both LTR and RTL layouts.

### 4.6 Future Provider Validation

Provider validation is not active MVP behavior. If provider scope is approved post-MVP, the future UX/API revision must define profile fields, uniqueness, consent, category/service, moderation, and recovery validation before implementation.

### 4.7 Success States

1. Provide concise success feedback for completed mutations that leave the user in the same context.
2. Complete the active task after a confirmed successful mutation unless the result must be reviewed.
3. Refresh or patch the visible affected data immediately after success.
4. Redirect only when the user's context has materially changed:
   - Authentication success -> Home or Empty State / Welcome.
   - Building creation -> completion/Home in the new building context.
   - Leave active building -> another accessible Building context, or Empty State / Welcome when none remains.
   - Logout or unrecoverable session expiry -> Login.
5. Critical financial success states include the resulting status. A withdrawal command shows `Pending` while the reservation and gateway submission are unresolved, `Requires Review` when the configured Paymob-delay threshold is crossed, and never shows either state as confirmed.
6. Partial batch results explicitly state created, skipped, and failed counts.

### 4.8 Error States and Recovery

1. **Validation error:** Attach safe field details to fields and provide a form-level summary when needed.
2. **Unauthenticated or expired session:** Attempt one transparent refresh. If refresh fails, clear protected state and return to Login with a session-expired message.
3. **Permission denied:** Remove unavailable action, explain the restriction, and return the user to the nearest permitted view.
4. **Unknown item:** Show content unavailable and return to the relevant list.
5. **Conflict:** Explain the changed state, refresh affected data, and require a new explicit decision.
6. **Network failure:** Keep user input, show connection failure, and provide retry. Do not report success.
7. **Timeout:** Show an uncertain-result message for write actions and reconcile before permitting a duplicate submission.
8. **Subscription locked or cancelled:** Explain that the building is read-only, block all building writes, and retain approved read access.
9. **Invalid join identifier or occupied role:** Keep the join/approval context and offer correction or explicit replacement where authorized.
10. **Insufficient wallet balance:** Keep the entered withdrawal/payment context and require a valid lower amount or another method.
11. **Declined or failed payment processing:** Do not update the ledger as confirmed. Show failed/pending status and an approved recovery action only after gateway behavior is resolved.

### 4.9 Confirmation and Destructive Interaction Rules

1. Require confirmation for building creation after nearby conflict, occupant replacement, member removal, leave building, join-code regeneration, billing deletion, finance writes, vote cast, vote close/cancel, issue close, subscription cancellation, and logout.
2. Confirmation summaries state the target, amount or consequence, and irreversible effect.
3. Destructive actions are clearly distinguished from safe actions and provide Cancel.
4. Dismissing a confirmation performs no mutation.
5. Issue and announcement history behavior must use retain/archive language when history remains available; it must not imply destructive deletion.

### 4.10 Language, Directionality, and Realtime Behavior

1. All approved user-facing content is available in English and Arabic.
2. Changing language applies immediately; Arabic uses right-to-left reading and interaction order where direction has semantic meaning.
4. Realtime updates are scoped to the active Portal, Profile, building, and permitted content.
5. Realtime events patch targeted current data and may show transient feedback.
6. Switching buildings closes old building subscriptions before opening new ones.
7. Realtime updates never bypass permission checks or expose data from another portal/building context.
8. The target accessibility standard and supported assistive technologies remain unresolved. No unsupported conformance claim may appear in the product or this specification until approved.

### 4.11 Context Preservation

1. Secondary tasks preserve their originating route, active building, filters, query, selected mode, and list position unless success materially changes that context.
2. Cancelling or leaving a confirmation performs no mutation.
3. While a blocking decision is active, unrelated background actions cannot be invoked accidentally.
4. Returning from a secondary task restores the originating position without an unexpected jump.
5. Long or nested content must have one unambiguous owner for each scroll or pan gesture; competing gesture regions must not make content unreachable.
6. Presentation, transition, and scroll-motion choices are optional and are defined outside this document.

## 5. Edge Cases & Interruptions

### 5.1 Portal Route Without a Required Profile or Permission

1. The target portal first validates the global Account session.
2. The target portal then resolves its own Profile and permission state.
3. If the Account has no Profile for the target portal:
   - Do not render protected portal content.
   - Show the target portal's approved onboarding or access-request state.
   - Provide a safe return to the originating portal or Login.
4. If the target Profile exists but lacks permission:
   - Show a portal-specific unauthorized state.
   - Do not transfer Building Suit roles as substitutes.
5. If a Building Suit user directly enters an administrator-only route:
   - Redirect to the nearest permitted Building Suit view.
   - Show a concise permission message.
   - Revalidate on the server if an action was attempted.

### 5.2 Network Latency or Disconnect During a Multi-Step Wizard

1. Preserve entered data while the wizard remains open.
2. Show a connection or latency state without moving the user backward.
3. Disable duplicate final submission while the result is unresolved.
4. If the request definitely failed before processing, present Retry.
5. If the result is uncertain, reconcile the outcome before allowing another create or join attempt.
6. Do not claim durable draft restoration after app termination because it is not approved or evidenced.
7. Location detection failure leaves manual location entry available.

### 5.3 Network Latency or Disconnect During a Finance or Payment Flow

1. Keep the confirmation context and entered values visible.
2. Prevent repeat submission while the request is unresolved.
3. On a timeout or disconnect after submit, show an uncertain status and refresh/reconcile the ledger before retry.
4. Never infer a successful payment or withdrawal from a browser redirect, closed task surface, or local timeout.
5. A Paymob transaction, if approved later, remains in blocking verification, visible pending status, or visible review status until a trusted callback/webhook or documented reconciliation evidence resolves it.
6. Paymob collection retry UX remains unresolved; withdrawal cancellation after submission is not available to the Building Admin.
7. If the selected payment bucket, due amount, or applicable credit changes while a payment is pending confirmation, stop and refresh the preview before allowing confirmation.

### 5.4 Session Expiry During a Complex Form

1. The client attempts one transparent session refresh.
2. If refresh succeeds, the original action resumes once and the form remains unchanged.
3. If refresh fails:
   - Stop the mutation.
   - Present a blocking session-expired state.
   - Return to Login.
   - Do not claim that unsaved draft data will survive app reload because durable draft persistence is not approved.
4. After reauthentication, permissions and active building context are resolved again before returning to protected content.
5. A user whose permission changed during the expired session cannot resume the restricted action.
6. Fingerprint may satisfy the local reauthentication prompt only when previously enabled and still valid; server session validation and action-specific recent-auth policy remain authoritative.

### 5.5 Building Context Changes During Active Work

1. Switching buildings while an active task contains unsaved building-scoped data requires canceling or explicitly discarding that interaction first.
2. After switch, old building lists, balances, notifications, and realtime subscriptions are cleared or replaced before the new context displays.
3. A deep link referring to another building must verify access and either switch with user awareness or reject the link.
4. If the active membership becomes blocked, left, or removed in realtime, write controls close immediately and the user is routed to an approved read state, another accessible Building, or Empty State / Welcome.

### 5.6 Concurrent Membership and Occupancy Changes

1. If another administrator resolves a join request first, refresh it and show that it is no longer pending.
2. If an owner or tenant position becomes occupied before approval, require a fresh explicit replacement decision.
3. If the final administrator changes before a leave/removal action, revalidate and block any action that would leave no administrator.
4. Historical memberships and occupancy remain visible where authorized.

### 5.7 Membership Removal With Financial Balance

1. Before removal, show the exact known old-resident amount due and Occupancy Credit for the current occupancy period.
2. Warn that the old balance remains historical and tied to the old resident/occupancy period.
3. Confirm that the new resident starts from zero and does not inherit old credit or debt.
4. Explain that no automatic settlement expense, refund, or debt transfer is created.
5. The administrator must explicitly confirm after reviewing this consequence.
6. If the balance changes before confirmation, stop and present the refreshed consequence.

### 5.8 Subscription and Billing State Changes

1. A building in trial or past-due grace remains subject to its assigned zero-charge trial policy and 14-day grace behavior.
2. Locked or cancelled status rejects all building writes even if the relevant screen was already open.
3. Missing billing configuration does not reject join requests and does not change building operational activation. It rejects only finance operations that require a configuration and leaves unrelated finance reads available where approved.
4. A user viewing read-only finance content retains that content where approved.
5. Administrator-facing subscription information uses the approved post-trial formula of EGP 20 per active Unit per billing cycle with an EGP 200 minimum, and shows the active-unit snapshot, remaining trial days, and first billing date.
6. Trial policy, active-unit snapshot, subscription status, or pricing-policy changes refresh the displayed charge basis before a user relies on it.
7. Every affected active Building Suit profile receives an in-app price-change notice and an external notice through the company-configured external delivery channel(s). Admin dashboard/banner and subscription page surfaces may show the new price and effective date, but notification scope is not Admin-only.
8. Cancellation moves the building to read-only for 3 months and can be reactivated during that period without data loss.
9. Cancellation is blocked when wallet balance is positive; the UI must clearly instruct the administrator to withdraw the full wallet balance first.
10. Active-unit counts use one rule across governance, reporting, and post-trial subscription billing: a non-deleted Unit with at least one current approved active owner or tenant counts once. Vacant Units and Units with only blocked, pending, rejected, or ended memberships do not count; either an active owner or active tenant is sufficient. Each billing cycle uses a canonical active-unit snapshot with the EGP 200 minimum.
11. Monthly maintenance generation targets current active occupancy/eligible active resident Units only. Manual Admin generation/retry does not expand the eligible Unit set or transfer historical monthly debt to a new resident.

### 5.9 Governance Eligibility and Snapshot Edge Cases

1. Participation and results use the approved total-unit snapshot captured for the vote where specified.
2. One active unit contributes at most one vote.
3. An active tenant has priority; the owner votes only when no active tenant exists.
4. A participant representing multiple eligible units casts the same selected choice for all eligible units.
5. For ordinary votes, the Administrator and author remain ineligible as specified. For Admin replacement, the incumbent and challenger remain eligible through Units they validly represent. Blocked members and prior-voted Units remain ineligible.
6. Admin-replacement incumbent majority, ties, and no quorum retain the incumbent; no second round or cooldown is created.
7. A replacement choice is final after submission. During the open ballot, authorized ordinary members see live participation/progress only and no exact candidate totals; individual Unit/person choices remain secret and the internal tally remains exact/immediate.
7. Manual close uses the creation snapshot.
8. Manual close, expiry processing, and auto-close use the creation-time activation, active-unit, and total-unit snapshots. Current occupancy changes do not alter an open vote's validity or denominator.
9. Ordinary vote-request `overdue` preserves the author's edit/withdraw context and Admin decision context; it does not open a Vote or show the request to other residents. After withdrawal, the Admin context no longer displays its content/history.
10. Rejected and withdrawn request resubmission must not show a new unrelated request path. Rejected resubmission displays its full new review window. Withdrawn resubmission has no deadline and displays none; edit/resubmit availability is derived from current server-authoritative eligibility and the same active original membership under §8.9, and a successful withdrawn resubmission displays the full new review window assigned from the resubmission timestamp.
11. When Admin changes while requests are `pending_approval` or `overdue`, the new Admin sees inherited workload counts and request details by role authorization; the former Admin loses the Admin-only request view. The request timeline preserves the prior Admin as historical actor where applicable.

### 5.10 Notification and Realtime Edge Cases

1. Realtime events are ignored when they do not match the active Portal/Profile/building scope.
2. A deleted or inaccessible referenced item shows content unavailable rather than a blank protected view.
3. Unknown notification types use neutral fallback content without exposing internal values.
4. Missing translation keys fall back safely and must not break the timeline. All user-facing text — notifications and system success/error messages — arrives as i18n keys plus parameters and is rendered into the active language (English/Arabic) by the client, never as server-rendered sentences (canonical rule: PRD NFR-I18N-05/06; System Architecture §7.8; API Contract §1.6).
5. Notification items do not expose read, mark-all-read, or entity deep-link interactions.

### 5.11 Future Provider Privacy and Contact Edge Cases

Provider privacy, contact, and moderation edge cases are not active MVP behavior because provider scope is removed. A future post-MVP provider decision must define these edge cases before any provider journey is implemented.
## 8. Checkpoint-05 required journeys and states

### 8.1 Special Assessment

The creation surface is explicitly labelled **Draft — no charges created** and shows project data, participating/deferred Units, original-funder/fair-share/Owner-responsibility/Deferred-Equalization preview, dates, and documents. Submission creates a Money Vote proposal, not a charge. Detail distinguishes `draft`, `pending_vote`, `vote_failed`, `vote_expired`, `cancelled`, `approved`, and `posted`; only `posted` shows obligations/ledger effects. Material edit warns that a new Money Vote is required. Activation is a separate confirmation available only after successful vote.

### 8.2 Emergency Expense and review

Admin flow shows current spendable balance beside amount and blocks amount above it. Category is required; `other_emergency` reveals required detail. Evidence upload or an explicit unavailable reason is required. Confirmation states that posting is permanent, uses existing funds, and creates no Unit/Owner debt. After posting, a 24-hour report countdown captures category, immediate-action explanation, amount, paid party, method/date, Building-funded amount, urgent-vote need, and either at least one authorized evidence document or a nonblank evidence-unavailable reason. Missing both blocks report submission; each revision displays and preserves its own evidence/reason. Overdue uses the visible `Emergency Report Overdue` state without implying reversal.

Resident-safe detail shows two independent status groups: `report_status = report_due|report_overdue|reported` and `review_status = not_flagged|awaiting_admin_response|response_submitted|warning_vote_pending|review_closed`. A flag may be submitted before the report, never disables the report form, and overdue may appear simultaneously with active review. The chronological API-107 screen retains report revisions with their evidence/reason, flag/evidence, evidence-backed Admin response revisions, warning-vote request/decision, fixed-option vote/result, and optional warning. ### 8.3 Admin replacement

Any voting-eligible active Owner/resident other than the incumbent sees **Nominate myself for Building Admin** when no cycle is active. ### 8.9 Checkpoint-13 withdrawn-request resubmission journeys and states

This section records the approved resident and Building Admin behavior for an ordinary vote request that its author withdraws before the Building Admin decision (locked decisions Q181–Q195). It reuses the existing request surfaces only, adds no Super Admin or company-dashboard screen, and keeps the resident/Building Admin application as the active product slice. It changes no rule for `pending_approval`, `overdue`, `approved`, or `rejected` requests beyond what is stated here.

1. **Withdrawn status without an artificial deadline.** The author's request detail and personal history present `withdrawn` with a clear explanation that the request is retained, is outside the Building Admin review queue, and can be reviewed, edited, and resubmitted while the author's same original Building membership remains active and current submission eligibility is satisfied. No expiry, countdown, deadline, or configured review window is displayed for the withdrawn state, and none exists to display.
2. **Review/edit first, then the normal Submit.** Opening a reusable withdrawn request leads to its normal review/edit experience with the retained current content. Resubmission is the ordinary final Submit action of that experience. There is no one-tap Resubmit from any list, no separate confirmation modal, checkbox, acknowledgement, typed phrase, preliminary Restore step, or duplicate Resubmit click, and no copied/new request: the same `vote_request_public_id`, lifecycle, and history continue.
3. **Temporary ineligibility is content-read-only and self-recovering.** While the original membership is active but the author temporarily fails current submission eligibility, the withdrawn request stays visible to its author with a safe machine-derived reason (`temporarily_ineligible`); Edit and Submit are not shown, but the applicable Hide or Restore personal-presentation action remains. When server-authoritative eligibility returns for that same still-active membership, edit/resubmit availability returns automatically with no support action, restoration workflow, or record recreation.
4. **Permanent membership end is a terminal content-read-only state.** After the original membership ends permanently, the request remains a historical record in the original author's own account history with reason `membership_ended`; no edit or resubmit action is ever shown or accepted again, but the active authenticated original-author account still receives Hide or Restore according to current personal visibility without needing a current membership. If the person rejoins the same Building under a new membership, the old request stays terminal read-only and is never reactivated, transferred, cloned, or adopted; that membership grants no reuse or other Building authority, while the same original-author account may still organize its old record. A new proposal uses the ordinary new-request flow. It never appears to the current Building Admin in review lists, Building history, search, dashboards, counters, or exports because it was withdrawn before a decision.
5. **Personal history, Hide, and Hidden records.** The original author's personal request history offers Hide only on an own visible record whose current canonical state is exactly `withdrawn`; `Hidden records` (Arabic equivalent) offers Restore only on an own hidden record still exactly `withdrawn`. No `pending_approval`, `overdue`, `approved`, `rejected`, or other non-withdrawn card/detail shows either action. Hide and Restore are presentation/organization actions on the author's own history only: they are visibly distinct from delete, never mutate lifecycle/evidence or grant Building authority, and cannot revive eligibility or reuse. Hidden reusable records open directly for review/edit/Submit; ineligible or terminal records open content-read-only with the applicable Restore action and no prerequisite Restore click.
6. **Successful resubmission automatically unhides.** When the ordinary Submit successfully resubmits a hidden withdrawn request, the hidden presentation state clears atomically and the request appears in active tracking with `pending_approval`, its full new review window, and normal submitted-state actions with no Hide. If resubmission wins a race, a stale Hide receives canonical safe state-changed feedback and the refreshed active request remains visible; if Hide wins first, later successful resubmission clears it. A failed validation or conflict never presents the request as submitted and never changes the hidden state.
7. **Current-rule validation on resubmission.** Submit revalidates everything under current server-authoritative rules; nothing is grandfathered from the original submission. Failures render safe, actionable errors beside the affected fields plus the existing concise summary pattern, the request remains `withdrawn` and editable, and the author corrects the same request rather than creating a new one. Client-side validation only assists; the server decides. Resident content is never silently altered to force validity.
8. **Building Admin review of a resubmitted request.** The Admin review queue positions the request by its latest successful submission time with the standard deterministic ordering; it does not retain the original queue position and receives no special priority or penalty. The Admin detail shows only the current submitted content version plus a neutral lifecycle timeline (submitted, withdrawn, resubmitted, decided — server times under existing display conventions). Prior content versions, edit diffs, withdrawn text, internal audit metadata, device data, and the author's hidden-state preference never appear in ordinary Admin review, and the request is not presented as a new unrelated request.
9. **Ordinary resubmission notification.** The current Building Admin receives the ordinary immediate in-app review notification through the existing outbox conventions with neutral localized wording equivalent to "A voting request was resubmitted for review". It exposes no old content, implies no misconduct, adds no priority badge, and deep-links only to the authorized current review projection, reauthorizing on open.
10. **Committed withdrawal invalidates decision actions.** Once a withdrawal commits, an open Admin review view transitions/refreshes to a clear `Request withdrawn` state through realtime/cache invalidation where available; Approve/Reject controls are disabled or removed, stale in-flight decision work is aborted or ignored, and a late response from a stale decision request can never render an approval/rejection the server rejected. Server-side state/version authorization is the mandatory guarantee; client invalidation only improves responsiveness.
11. **Conflict feedback in both directions.** If a Building Admin decision commits first, the resident's withdrawal or resubmission attempt shows safe state-changed feedback with the authoritative decided state and a refresh path; if withdrawal commits first, the Admin sees the authoritative withdrawn state. Neither side's UI may imply that the losing command partially applied.
12. **Click audit.** The complete reuse journey is open the withdrawn request → review/edit → normal Submit. A hidden request adds only the Hidden records navigation before opening. Restore exists solely for returning a record to the normal list without submitting it. No confirmation, restore-before-submit, or duplicate action is added anywhere in the journey.

Actions the server does not currently allow are never shown as available. Loading, empty, error, offline/stale, idempotent-replay, conflict, and concealed-not-found states follow existing canonical patterns; EN/AR copy is semantically equivalent with RTL layouts keeping status/time/content readable; statuses are never color-only; focus returns predictably after refreshes and state transitions; and read-only, hidden, and conflict states are screen-reader labelled.
