# Building Suit Optional User Interface Specification

**Specification status:** Optional presentation profile
**Behavior source:** `03. BUILDING_SUIT_UX_SPEC.md`
**Motion source:** `03B.BUILDING_SUIT_MOTION_SPEC.md`
**Brand source:** `building-suit-brand-guidelines/`

## 1. How to Use This Document

This document defines one approved visual and component direction for Building Suit. It does not define product rules, permissions, validation, data behavior, or recovery. Those remain authoritative in the UX specification.

Choose one implementation mode before design or generation begins:

1. **UX only:** Load `03. BUILDING_SUIT_UX_SPEC.md`; the implementing AI or design team chooses the complete interface.
2. **UX + optional UI:** Load the UX specification and this document; apply this presentation direction without changing UX behavior.
3. **UX + custom UI + motion:** Load the UX and motion specifications; ignore this document and create a different interface.
4. **UX + optional UI + motion:** Load all three documents; use this visual direction and the independent motion system.

If the interface direction conflicts with UX behavior, the UX specification wins. If this document specifies movement differently from the motion specification, the motion specification wins.

## 2. Interface Foundations

1. The 390 × 844 mobile viewport is the base composition reference. Larger and smaller viewports preserve hierarchy and safe-area behavior rather than scaling pixel values mechanically.
2. Use the Building Suit brand system for color, typography, iconography, spacing, imagery, light mode, and dark mode. Do not introduce a second visual identity inside product surfaces.
3. Building Navy (`#16293B`) is the canonical primary action color in light mode. Premium Gold (`#D89B42`) is the canonical primary action color in dark mode.
4. Semantic colors communicate state only. Amber Alert (`#E1841F`) and other status colors must not become decorative section accents.
5. Rounded planes, restrained elevation, topological imagery, and clear foreground/background layering form the core visual language.
6. English and Arabic compositions mirror directional placement where meaning requires it. Content order, touch targets, safe areas, and text expansion must remain usable in both directions.

## 3. Application Shell

1. The primary mobile navigation is a persistent bottom bar with Home, Finance, Community, Services, and Profile.
2. Standard destinations use a header containing the menu trigger, contextual title, and notification trigger.
3. Focused subpages hide the standard header and bottom navigation and provide explicit back navigation.
4. The side menu contains:
   - Active building identity and accessible building list
   - Create Building and Join Building
   - Language and appearance
   - Logout
5. The menu panel occupies approximately 67.5% of the mobile viewport. The current page remains visibly related to it and becomes non-interactive while the menu is open.
6. Menu direction mirrors for Arabic. Keyboard focus enters the menu while open, returns to the trigger on close, and cannot reach obscured background actions.
7. On standard shell pages, the notification trigger opens Recent Activity. Services and Profile may link directly to the complete Notifications history.
8. Recent Activity is approximately 340 px wide with a maximum height of 420 px in the base viewport. It is anchored below and end-aligned to its trigger, uses a light dismissing backdrop and directional arrow, and retains the current page behind it.

## 4. Authentication

1. Login, Register, and Forgot Password use a shared full-page composition.
2. In the base viewport, a dark 200 px identity region has 40 px curved lower corners. A foreground form plane overlaps it by approximately 40 px.
3. The form plane uses a narrow reading width and approximately 30 px corners. Secondary navigation sits outside the primary action group.
4. A theme control sits at the safe-area end edge.
5. Login ordering is identifier, password, Forgot Password, Login and eligible Fingerprint action, a labeled divider, Google, then Register.
6. Register uses one continuous scrollable form: full name, required phone, optional email, password, confirmation, terms, Create Account, divider, and Google.
7. Forgot Password retains the shared frame but contains explanatory copy, one recovery identifier, and Send Reset Link.
8. Verification surfaces clearly identify channel, destination, cooldown, current step, and remaining steps.
9. Authentication text inputs use floating labels instead of static above-field labels. The label rests inside the empty field, floats to the top edge of the field on focus or once a value exists, and remains visible during filled, disabled, read-only, error, and processing states. Placeholder examples are supplemental and appear only after the label has floated.

## 5. Building Onboarding and Administration

1. Create Building uses a four-phase accordion workspace. Only the active phase is fully expanded.
2. Completed phases collapse into compact summaries with Edit actions so users retain context without keeping every form open.
3. Create Building is a focused task and does not show the primary bottom navigation.
4. Join Building uses a scanner-inspired composition:
   - A dimmed building image occupies the upper region.
   - Premium Gold scanning corners and a pulsing scan line communicate the code-entry theme.
   - This scanner is decorative; it never requests camera access or claims to read QR codes.
   - Code entry begins in a rounded lower plane that can expand to reveal unit and owner/tenant controls.
5. Pending approvals, member actions, replacement decisions, and billing edits use contextual secondary surfaces that retain the building-management view behind them.
6. Building Select uses large selectable building summaries plus Create New Building and Join Another Building.

## 6. Home

1. Home begins with a contextual topological or image-based building region below the shell header.
2. The expanded identity region includes building name, city, role and unit, restricted state when applicable, and governance activation.
3. A rounded foreground content plane includes a centered affordance indicating that more content is available.
4. Content priority is:
   - Quick actions: Pay Fee, New Issue, Vote
   - Administrator setup and approval warnings
   - Notice Board with urgent announcements first
   - Building balance summary
   - Issue and vote summaries
   - Units and Members controls, search, filters, and results
5. Contextual tasks opened from Home retain its building, selected mode, filters, and scroll position.
6. The expanded-to-compact scroll composition uses the generic contextual-collapse recipe in the motion specification. Visual stop values may use the optional adapter in Section 13.

## 7. Finance

1. Finance begins with a topological balance region above a rounded dashboard plane.
2. The total building balance receives the strongest emphasis. Collected but not yet available for withdrawal, reserved/held withdrawal amount, available balance for withdrawal/use, completed withdrawals, failed/reversed withdrawals, and wallet/manual balances remain distinguishable as supporting values without fixing the final layout in this document.
3. Administrator content includes building balances, collections, late and outstanding units, recent transactions, subscription or billing restrictions, and permitted finance actions.
4. Owner and tenant content emphasizes permitted units, separated finance sections, balances, history, collection summary, and manual payment instructions.
5. Unit finance visually separates `Monthly / Occupancy Dues`, `Owner Obligations / Special Assessments`, and `Disputed / Under Review`. Use section headings, filter chips, or grouped rows rather than a single mixed balance.
6. Payment and Expense share a transaction surface only when the selected mode remains unambiguous. Withdrawal, Charge Unit, Batch Fee, Special Assessment, Equalization Payout, owner-obligation review, and transaction detail may use separate contextual surfaces.
7. Every ledger mutation uses a confirmation surface that presents target, selected bucket/scope, amount, method, consequence, and final action. Payment surfaces should visually separate current due, applicable credits, excluded credits, Paymob fee, total charged, excess, and the resulting `Occupancy Credit`, `Owner Obligation Credit`, or `Equalization Credit` where applicable. Withdrawal surfaces should visually separate withdrawal amount, final fee, and total reserved amount.
8. Special Assessment surfaces show project cost, total Units, active funding Units, original funder group, fair share, deferred pending obligations, and equalization status as separate scan-friendly fields.
9. Ledger and Unit Financial History are focused, independently scrollable pages with restorable filters and scroll position.
10. Finance uses the generic contextual-collapse recipe in the motion specification. Visual stop values may use the optional adapter in Section 13.

## 8. Community and Governance

1. Community uses a two-option Support/Governance switch.
2. Support orders announcements before issues.
3. Announcement controls expose Active and Closed; Action Required appears only when behavior rules require it.
4. Announcements may use a horizontally snapping collection. Issue filters and results follow in a rounded foreground plane.
5. Authorized Create Announcement remains adjacent to the announcement context. Create Issue remains easily reachable above primary navigation for unblocked users.
6. Issue, announcement, and vote creation/detail use contextual secondary surfaces so the selected Community mode, filters, and position remain visible or restorable.
7. Governance includes activation summary, Active/Pending/Closed filters, eligible subfilters, activity, Create Vote, and Vote Detail.
8. Support and Governance use the navy/gold section identity. They do not introduce section tint colors.

## 9. Services

1. A two-option control switches between Browse Directory and My Provider without losing either mode's working state.
2. Browse Directory orders search, horizontally scrollable category choices, result count and Clear Filters, then provider results.
3. Provider summaries include category identity, avatar or initial, location, description, primary service, and Phone/WhatsApp actions.
4. Selecting the summary body opens Provider Detail. Selecting Phone or WhatsApp invokes the external action without first opening detail.
5. My Provider replaces the browse results with either Become Provider or the provider dashboard.
6. Provider detail, creation, Add Service, and Edit Service use contextual secondary surfaces and return to the relevant retained state.

## 10. Profile

1. Profile begins with a fixed topological identity region containing avatar or initials, Account name, and email.
2. A rounded account plane rises over the identity region and contains Account information, Building Suit Profile, horizontally scrollable memberships, administrator shortcuts, preferences, Security, and Logout.
3. Edit Profile, Security, and Leave Building use contextual secondary surfaces. Logout uses a clear confirmation alert.
4. The identity region uses the generic contextual-collapse recipe in the motion specification. Visual stop values may use the optional adapter in Section 13.

## 11. Notifications

1. Recent Activity shows type icon, title, message, relative time, and unread indication in a bounded scroll region.
2. Read items remain visible with lower emphasis. The empty state is **All Caught Up** with no action.
3. The complete history places Important Broadcasts before standard activity and groups standard activity by date.
4. Notification items remain display-only. They do not expose read, mark-all-read, or entity deep-link actions.
5. Selecting See All closes Recent Activity before opening the complete history. Dismissing Recent Activity leaves the current route unchanged.

## 12. Component and State Conventions

1. Use inline, associated field errors and a form-level summary when multiple errors need orientation.
2. Use associated floating labels for text-entry inputs when this UI profile is selected. Do not use placeholder-only labeling; optional and required markers remain attached to the label.
3. Required, optional, read-only, disabled, pending, blocked, destructive, and successful states must be distinguishable without relying on color alone.
4. Use skeleton placeholders for initial structured content such as summaries, result collections, identity, and metrics.
5. Use action-level progress for mutations. Loaded content remains stable during background refresh or append operations.
6. Use concise transient feedback for completed mutations that leave the user in context.
7. Destructive confirmations visually separate the destructive action from Cancel and state the consequence before commitment.
8. Contextual secondary surfaces block interaction with obscured content, preserve underlying position, and restore focus on close.
9. Empty states explain the current condition and expose an action only when the user is permitted and an approved recovery exists.
10. Unknown or inaccessible content uses a neutral unavailable state without exposing internal identifiers.

## 13. Optional Layout Adapters for the Motion System

These values reproduce the original Building Suit composition. They are optional UI adapters, not universal motion rules.

### 13.1 Menu adapter

- Open content transform target: translate 60% away from opening edge, scale to 85%, 40 px corners, lateral shadow, and at most 0.5 px softening.
- Menu resting width: approximately 67.5% of viewport.
- Apply the menu recipe, directionality, interruption, focus, and Reduced Motion requirements from the motion specification.

### 13.2 Home adapter

- Contextual collapse distance: 150 px.
- Foreground stop: approximately 160 px from viewport top; available height is `viewport - 160 px`.
- Supporting identity fades by the halfway point.
- Building name moves approximately 65 px and changes from 30 px to 22 px.
- Unit and activation summaries may travel approximately 109 px and 140 px respectively.

### 13.3 Finance adapter

- Contextual collapse distance: 56 px.
- Balance emphasis scales toward 60% and settles into the compact identity region.
- Foreground stop: approximately 140 px from viewport top.

### 13.4 Profile adapter

- Expanded identity height: approximately 310 px.
- Compact identity height: approximately 130 px.
- Identity content fades over the first 150 px, translates at approximately 40% of scroll distance, and scales toward a 70% floor.

## Checkpoint-05 UI additions

- Status chips are grouped, never flattened: Special Assessment states; Emergency report `Report due|Emergency Report Overdue|Reported`; independent review `Not flagged|Awaiting Admin response|Response submitted|Warning vote pending|Review closed`; replacement nomination/cycle; ordinary request `Pending approval|Overdue|Approved|Rejected|Withdrawn`. Overdue and active review may display together.
- Finance forms use a visible spendable-balance meter and blocking inline error for an over-balance Emergency Expense. Category selection, conditional `other_emergency` detail, evidence/evidence-unavailable control, permanent-expense confirmation, and report countdown are required components. Every report revision requires either one-or-more authorized evidence documents or a nonblank unavailable reason and displays the preserved choice in history.
- API-107 resident-safe detail uses a chronological expense/report revisions with evidence-or-reason/flag/evidence/Admin-response revisions/warning-request decision/fixed-option vote/result/optional-warning timeline. Flag-before-report leaves report controls enabled. A pending or rejected resident warning request displays `Response submitted` review state and no Vote row/link; only direct Admin creation or API-105 approval displays `Warning vote pending`. Styling must not imply refund, reversal, freeze, suspension, permission change, or Platform adjudication.
- Admin replacement uses the incumbent plus one eligible self-nominated challenger. Its normal nonterminated schedule is a fixed 24-hour announcement followed by a three-day ballot; reached quorum or an apparent majority does not close, decide, or transfer Admin early. Challenger withdrawal during announcement or voting, or trusted challenger-ineligibility termination while nonterminal, may end that schedule early. Cancellation/ineligibility presentation shows no winner, no Admin transfer, the incumbent preserved, recorded votes retained only as immutable audit history, no cooldown, and immediate eligible self-nomination after terminal commit. The entry action is **Nominate myself for Building Admin**; there is no nominee-acceptance or current-Admin/Platform decision control. Both participants may vote through eligible Units. While open, the ballot surface shows Unit-based participation/progress only and never exact candidate totals or a Unit/person choice; internal tally stays exact/immediate and finalized totals follow existing result rules.
- Ordinary resident vote request detail gives Admin Approve/Reject actions for `Pending approval` and `Overdue`; rejecting opens a required-reason modal. Author view gives Edit/Withdraw/Resubmit only where permitted. Creator view retains rejected and withdrawn cards for same-request editing/resubmission; rejected resubmission displays a full new review window, and withdrawn resubmission has no deadline and displays none (behavior in UX §8.9 and the Checkpoint-13 additions below). After withdrawal, Admin and other-resident product views show no request content/history; immutable internal audit is not an Admin surface. Approved ordinary vote detail shows cancellation only before the first recorded vote and requires a reason.

## Checkpoint-08 UI additions

- The replacement cycle header, list card, notification title, and result summary are composed by the system from the incumbent and challenger identities. No screen contains an election-title input, and no surface renders a resident-authored election name. Presentation must not fall back to a free-text field when an identity is missing; it renders the approved system-generated pattern instead.
- No surface, menu, overflow action, admin tool, or operator console exposes `Close election`, `Approve result`, `Finalize now`, `Extend voting`, or `Cancel result` for a replacement cycle. Result presentation is produced by server state only. The countdown is informational: when the server finalizes early on confirmed complete eligible-Unit participation, the surface switches to the terminal result even though the countdown had time remaining, without asking anyone to confirm.
- Participation presentation is Unit-based. Labels read as Units, never as residents, members, or users, and the denominator is the Building's fixed Unit count. A vacant Unit gaining a resident during voting must not visibly change the denominator.
- A resident who becomes an existing Unit's currently eligible voter mid-cycle sees the standard neutral ballot. The UI never displays that the Unit already voted, who voted, what was chosen, or that a previous vote will be or was invalidated. Occupancy change alone triggers no toast, banner, badge, or notification about vote status.
- After a successful replacement vote, the participation/progress projection refreshes so the Unit contributes exactly one effective vote. No open-ballot surface renders candidate totals or a −1/+1 option delta, and no animation or annotation signals supersession. The client re-reads the server projection; internal authoritative tallies remain exact/immediate. This closes DEC-16/ARCH-OPEN-13/SEC-ADR-09 without changing final-result publication.
- Money Vote creation starts with the explicit typed topic. `Spending authorization` presents single-proposal/multi-alternative modes, structured amounts, exactly one no-spend choice, visible 0% default tolerance, maximum exposure, purpose, and validity. `Change the no-vote spending limit` presents one proposed EGP field beside server-resolved current value/provenance and maximum/policy snapshots, with exactly read-only Approve proposed/Keep current choices and no spending-specific controls. Detail/result renders the topic and applied/not-applied state. Expense forms retain explicit purpose/Vote linkage and authorization consumption fields.
- Super-Admin controls render two separate cards/routes and data models: no-vote-limit default/maximum/version/new-Building-only applicability/explicit exceptional propagation/eligibility/protection/provenance/audit; and Money Vote tolerance/validity constraint versions prospectively applicable to new Votes in existing and new Buildings, with no propagation control. Checkpoint 10 supplies the propagation scheduling and notice contract below.
- Replacement-vote failure is a recoverable inline error on the ballot with unchanged totals and no disclosure that a prior vote exists. Concurrent finalization during submission renders the already-finalized terminal state, never a duplicate or conflicting result.
- Terminal replacement results are strictly read-only for every role, including the incumbent, challenger, Building Admin, company Super Admin, and Platform Operator.

Never show an editable recipient list or trust client eligibility.
- Active schedule cards/detail show Building, current and proposed values, `Building Suit` source, planned effective time, actual application time where applicable, version, and accessible status treatment for `scheduled`, `suspended_open_vote`, `applied`, `superseded_by_local_vote`, `cancelled_by_super_admin`, and safe terminal no-op. Status uses text/icon plus color and remains readable on compact layouts.

- Cancellation preview states the scheduled value/time, that the current value remains, and that Building Suit cancelled it. When a relevant Vote is open, both Super-Admin preview and member notice prominently state that the Vote remains active, independent, and binding with the approved success/non-success consequences.
- Building policy and notification surfaces expose only resident-safe scheduled/suspended/applied/cancelled/superseded information. ## Checkpoint-12 UI behavioral additions

- No Super Admin screen, navigation entry, dashboard information architecture, prototype component, or implementation priority is created here. These are future-consumer behaviors for protected contracts; resident/Building Admin application work remains the next active UI priority.
- A future grant form preselects temporary and requires either the explicit configured-default-expiry mode or an explicit valid future expiry. Permanent is a separately selected mode completed by ordinary form submission with mandatory internal reason; no additional confirmation control or step exists, and blank/null expiry never changes the selection to permanent.
- Extend and both conversion directions retain one stable grant identity/history. Extension retains its explicit confirmation; either dedicated conversion action uses its protected internal reason and ordinary submission without another confirmation. Manual revoke keeps explicit confirmation, and emergency revoke-all keeps its high-salience warning/confirmation. No second-approver, grace, auto-renew, auto-permanent, restored-revocation, or revoke-and-recreate presentation exists.
- Employee notices and self-safe status components cover only configured pre-expiry, conversion, manual-revoke and emergency-revoke facts and allow only type, effective time, expiry when applicable, and access-ended/conversion facts. Account disablement/employment termination creates no employee-notice component or outbox expectation in this checkpoint. Internal reasons, incident detail, cancellation content, manager identity, recipient lists, and Building data are forbidden component inputs. Building-member components receive no grant data.
- An open protected audit surface reacts to a grant-version/access-loss signal by aborting requests, purging memory/query/persistent/offline/browser state and reusable links, ignoring late responses, and rendering an accessible localized `Access ended` replacement. Protected content never has an offline/stale-content fallback. Copy states honestly that a file already downloaded externally cannot be recalled.
- Export/job/download components recheck current authority and render safe `queued|cancelled_access_ended|artifact_expired|unavailable` outcomes without exposing filenames, filters, internal reasons, or content after access loss. Loading, empty, retry, stale-session, RTL, focus, keyboard, screen-reader and non-color status treatment follow the existing system.

## Checkpoint-13 UI additions

- Withdrawn request cards and detail show the `Withdrawn` chip with a retained-and-reusable explanation and no expiry, countdown, deadline, or review-window element; the reuse path is the normal review/edit screen ending in the ordinary Submit button, with no extra confirmation modal, checkbox, typed phrase, Restore-first step, duplicate Resubmit click, or one-tap list resubmission.
- Content-read-only presentations reuse the existing disabled/read-only field treatment: temporarily ineligible withdrawn requests show a safe reason banner and no enabled Edit/Submit control, returning to editable automatically when eligibility returns; permanent original-membership end keeps those reuse controls absent forever, including after rejoining. In both cases the active authenticated original author still sees Hide on an own visible withdrawn record or Restore on an own hidden withdrawn record; this account-presentation action needs no current membership and grants no Building authority.
- Personal history adds Hide only on an own visible record whose canonical current state is exactly `withdrawn`, and `Hidden records` (Arabic equivalent) adds Restore only on an own hidden record still exactly `withdrawn`; no non-withdrawn card/detail renders either action. Both use presentation-action styling distinct from delete, and hidden reusable records open directly without a prerequisite Restore click. Resubmission-first makes a stale Hide render canonical safe refreshed active state; Hide-first is cleared atomically by successful resubmission, which returns the request to active tracking with `Pending approval`, its full new review window, and no Hide action.
- Resubmission validation failures use the existing field-level error placement plus the concise summary pattern, leave the card in `Withdrawn`, and never present the request as submitted; conflict responses use the canonical safe state-changed presentation with a refresh action.
- Admin review queue cards order by the latest successful submission time with ordinary priority and no resubmission badge implying urgency; Admin detail renders only the current submitted content version plus a neutral lifecycle timeline row set (submitted, withdrawn, resubmitted, decided with canonical localized timestamps), and never prior content versions, diffs, withdrawn text, internal audit metadata, or the author's hidden preference. On a committed withdrawal, an open Admin review view swaps to a `Request withdrawn` state, disables/removes Approve/Reject, and ignores late stale decision responses.
- The resubmission review notification reuses the standard in-app notification presentation with neutral wording equivalent to "A voting request was resubmitted for review" and the standard deep link. Every state above applies equally in Arabic with RTL mirroring; loading, empty, error, stale, and conflict states, keyboard/focus discipline, screen-reader labels, and non-color status treatment follow the existing system.
