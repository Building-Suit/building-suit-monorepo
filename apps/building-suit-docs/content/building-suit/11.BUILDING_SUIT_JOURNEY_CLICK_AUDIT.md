# Building Suit Journey Click/Action Audit

**Source basis:** `03. BUILDING_SUIT_UX_SPEC.md` Section 1 (Core User Journeys 1.1–1.25)
**Purpose:** Quantify the discrete user-initiated effort required by each approved active MVP journey on its minimum (happy) path, so compression opportunities can be identified without silently altering source requirements.
**Status:** Updated through Business Strengthening Checkpoint 13, including structured Money Vote/authorization, purpose-based Expense enforcement, author-only withdrawn requests with deadline-free same-request resubmission and hide/restore (§4.6), and participation-only open replacement publication.

## 1. Methodology

"Action" is defined narrowly so counts are comparable across journeys and reproducible by anyone re-auditing the spec:

| Counted as one action | Not counted as a separate action |
|---|---|
| A tap on a primary or secondary CTA (Submit, Continue, Confirm, Approve, Publish, etc.) | Reading or scrolling content |
| A tap-based decision that determines which path the journey takes (role choice, payment method, normal/urgent, candidate, option select) | Typing individual characters into a field |
| Completing the text-entry fields on one screen, counted once regardless of field count (the "compose" effort) | A second occurrence of the same kind of action already counted (e.g., a field that is part of the same compose step) |
| Entering a delivered code (OTP/reset code), counted once regardless of digit count | System-driven waits (location resolution, gateway callbacks, debounce) |

A screen that has both fields to complete **and** a CTA to submit them therefore counts as **2 actions** (compose + submit). A screen with a branching decision **and** a separate compose step **and** a CTA counts as **3 actions**. Counts reflect the **minimum path**: the fewest required taps to reach Final Resolution, skipping every optional field and optional filter. A **Typical/Max** column is given where a common (not just minimal) path materially differs — e.g., an administrator who lives in the building they create.

Counts are an effort proxy, not a literal tap log of any specific UI build — they are derived from the journey text in `03. BUILDING_SUIT_UX_SPEC.md` §1, not from implementation. Where the spec leaves a UI detail unresolved (e.g., whether OTP auto-submits), the count assumes the more conservative reading (an explicit submit/verify tap) so this audit never understates effort. Checkpoint-07 synchronizes the changed election flow only; a complete journey-by-journey recount and reduction pass is intentionally deferred until the business-improvement interview is finished, so this document does not prematurely discard approved controls.

## 3. Top Compression Opportunities

Ordered by a combination of action count, journey frequency, and first-impression importance (a one-time 9-action journey that every paying administrator must complete is weighted higher than a 5-action journey most users never touch).

### 3.1 Create a Building (§1.4) — 5–7 actions after approved compression

This is the first substantial task a new administrator performs, so its cost is disproportionately visible.

- **Approved behavior:** Location selection/confirmation is first and mandatory. The user must select or confirm the real location before naming/completing the building.
- **Do not compress away:** The nearby-building discovery step (location → discovery list → path choice) exists specifically to prevent duplicate buildings and to surface the "Request to Join" and "Request Building Suit to Set It Up" paths introduced for first-activation support (PRD §3.6, UX §1.4A). Removing or skipping it would undermine the anti-duplication and onboarding-routing goals the feature was built for. This is treated as **intentional friction**, not a defect.
- **Approved compression:** After location/discovery, the user chooses join existing building, request company-assisted onboarding, or continue self-service creation. Previous rigid phase-based presentation is superseded; phases may be merged/compressed to reduce friction.
- **Approved autofill:** Address is auto-filled from selected location and editable; the user may add an optional landmark note. The initial building name is generated from the location-derived address and remains editable.

### 3.2 Register and Verify a New Account (§1.2) — 3–4 actions, with phone OTP wait time

The raw action count is moderate, but phone OTP delivery latency and resend cooldown are still part of the perceived friction.

- **Approved behavior:** Registration requires phone verification only. Email is optional, can be added later from Profile / Account Settings, and is verified only before email-based notifications/messages are sent.
- **Compression retained:** Treat phone OTP entry as auto-submitting on the 6th digit where technically reliable; otherwise count one explicit verify action.

### 3.3 Publish and Acknowledge an Announcement (§1.18) — 5 actions

- **Compress:** Default priority to "normal" and RSVP-required to "off," presenting both as a collapsed "Advanced options" disclosure rather than two always-visible decisions. For the common case (a normal, non-RSVP announcement), this reduces the creation path from 5 actions to 3. **Spec-compliant** — the spec requires the administrator to be able to set these, not that they must be presented as undismissable top-level choices every time.

### 3.4 Create, Approve, and Cast a Vote (§1.19) — 4 actions to create

- **Compress:** Default vote type to "normal" (the more common case per the approval/participation rules) rather than presenting normal/money as a forced first decision. Saves 1 action for the majority of vote creators. **Spec-compliant** — type remains user-changeable, only the default changes.
- **Do not compress:** Pending/overdue/rejected visibility, author-only withdrawn history, rejection/cancellation reasons, same-request history, rejected full-window reset, and cancellation-before-first-vote are governance controls. Admin/other-resident withdrawn views must not exist; withdrawn resubmission has no deadline and adds no confirmation click (§4.6).

### 3.5 Record a Manual Payment (§1.11) — 5 actions, high frequency

This journey's count is unremarkable, but its frequency (run by every administrator, every month, per paying resident) means even a 1-action reduction compounds significantly across the portfolio.

- **Compress:** Pre-select the building's most-used payment method as the default in the method selector rather than requiring an explicit choice every time, while keeping the other methods reachable in one tap. Saves 1 action for the common case. **Spec-compliant** — the spec specifies the available methods, not that one must always be explicitly chosen with no default.
- **Do not compress:** The selected due bucket and payment-preview step are required because generic mixed payments are not allowed. Collapsing them would risk applying money or credits to the wrong occupancy, ownership, or dispute scope.
- **Do not compress:** The confirmation-modal step is explicitly justified in §2.6 ("Finance operations use confirmation modals because they create ledger effects") and should not be collapsed into a single inline-confirm tap. This is **intentional friction** protecting financial integrity, consistent with the same pattern in Create Charge (§1.12), Record Expense (§1.13), and Request Withdrawal (§1.14).

## 4. Patterns Worth Replicating

Four journeys already achieve the spec's floor of 1 action: View Manual Payment Instructions (§1.16), Move Between Isolated Portals (§1.25), Review Building/Unit Financial Position (§1.10, viewing only), and Review Notifications via the popover (§1.24). Each succeeds the same way: the destination is reachable from a single, always-visible entry point with no intermediate decision or compose step. Where a journey already has an obvious single-purpose entry point (e.g., Switch the Active Building, §1.8), the same pattern — single tap to the surface, single tap to the outcome — is the template to apply when implementing the compressions above.

## 4.1 Checkpoint-05/06/07 intentional friction

- Special Assessment needs separate draft preview, Money Vote, and post-vote activation; the confirmation cannot be compressed into immediate posting.
- Emergency Expense confirmation must show available balance/permanence; the mandatory report may be completed immediately but its evidence/reason fields cannot be skipped. Flagging requires a reason and explicitly states that it does not refund or freeze anything.
- Replacement uses one confirmed self-nomination with no nominee-acceptance action and no title step: the resident types no election name, so the compose cost of starting a cycle is a single confirmation. The fixed 24-hour announcement and the scheduled three-day ballot deadline are intentional waits on the normal nonterminated journey; reached quorum or an apparent majority never shortens them. Confirmed complete eligible-Unit participation does end the wait, but it is a system-evaluated condition rather than a user action, so it removes waiting time without adding or removing a click. Challenger withdrawal during announcement or voting, or trusted challenger-ineligibility termination while nonterminal, may end that journey early, but these are terminal governance transitions—not click-reduction shortcuts—and produce no winner or Admin transfer, preserve the incumbent and audit-only recorded votes, create no cooldown, and permit immediate eligible self-nomination after terminal commit. The final-vote confirmation communicates that the voter cannot change or withdraw their own choice; the waits and confirmation remain approved governance safeguards, subject to the later dedicated click-reduction audit.

- Ordinary resident votes require an Admin decision. Rejection reason is mandatory and the historical result remains reachable; replacement must never be routed through this decision screen.
- Ordinary request edit/withdraw/resubmit histories, overdue reminders, and cancellation before the first recorded vote are intentional safeguards. They add retained state visibility plus documented rejection/cancellation reason capture; withdraw has no reason input and adds no extra action to the common Admin-created vote path.

## 4.2 Checkpoint-08 journey effects

- **No manual completion step exists.** The normal replacement result is finalized by the system, so no journey contains a `Close election`, `Approve result`, `Finalize`, `Extend`, or `Cancel result` action for any role. Zero clicks are spent on completing an election, and none may be added.
- **Reduced operational dependence on the Admin.** The incumbent has no action anywhere on the normal-result path — they cannot start, approve, delay, close, or cancel the cycle against them. The election proceeds and completes with no Admin involvement at all, which removes the Admin as a bottleneck and as a conflict-of-interest surface.
- **Retry costs no clicks.** A repeat self-nomination by the same challenger against the same still-serving incumbent is recognized automatically from prior cycle history. The resident performs the identical single self-nomination journey; there is no retry checkbox, no reference to the previous cycle, and no extra confirmation.
- **Occupancy-driven voting adds no steps.** A resident who becomes an existing Unit's eligible occupant mid-cycle uses the same single-cast ballot journey as any other voter. Occupancy change alone triggers no user action, no acknowledgement, and no notification about vote status.
- **New complexity is behind the interface, not in front of it.** Automatic supersession and early full-participation completion introduce real concurrency, audit, and reconciliation complexity for engineering and operations: serialized per-Unit casting, exactly-once terminal transitions across five racing paths, append-only vote history with supersession metadata, and reconciliation that must not leak ballot secrecy. None of that cost is passed to the resident as an additional click, but it is a genuine implementation and operational risk recorded here and in the business analysis.

## 4.3 Checkpoint-09 journey effects

- **Money Vote stays one flow.** Single versus multiple alternatives is an in-form choice; amounts, required no-spend, visible 0% tolerance default, maximum exposure, and validity do not create separate screens. Voter detail is read-only and adds no confirmation beyond the existing cast confirmation.
- **Expense integrity adds at most one explicit selection.** The interface prioritizes relevant successful authorizations and reuses/suggests recent purposes, but the Admin confirms the purpose and required Vote before the existing confirmation. No post-first/link-later shortcut exists.
- **No-vote grouping remains low-click.** Purpose/project is reused or suggested from context; the server decides aggregation and threshold. Emergency Expense remains separate.
- **Replacement publication removes data, not actions.** Open members see participation/progress only; exact candidate totals appear only with the finalized result under existing rules. No delay, refresh action, or supersession acknowledgement is added.
- **Super-Admin propagation is one explicit schedule flow plus confirmation/audit.** Eligibility/protection, recipient summary, current value, and conflicts are server-calculated. The flow includes future time and initial-notice preview; later cancellation is a separate explicit confirmation, while inline value/time editing is absent. Checkpoint-11's two cancellation text inputs are intentional governance actions: the internal record and resident-safe explanation cannot be merged, skipped or derived.

## 4.4 Checkpoint-11 journey effects

- **Safe correction is one focused action plus confirmation.** The operator supplies the internal rationale and new safe explanation on one surface, reviews the resident notification preview, and confirms. Recipient resolution is server-owned, so no recipient-selection clicks are added; no resident acknowledgement is required.
- **Internal correction is one focused append-only action.** Corrected reason plus rationale and confirmation are necessary evidence. There is no second-person approval, resident preview or notification step.
- **Protected audit reads add no confirmation click.** View/search/export records access invisibly and fails closed if evidence cannot persist. Dedicated permission controls visibility without burdening an authorized reader with an acknowledgement.
- **Resident history remains read-only.** Latest explanation and the complete safe chronology appear in the existing detail surface; residents need no correction acknowledgement and see no reactivation/reschedule action.

## 4.5 Checkpoint-12 journey effects

- **Future management journeys are behavioral evidence, not screens.** This audit records the protected contract interactions without adding Super Admin prototype routes, components or navigation. Resident and Building Admin improvements remain the next active product/design slice.
- **Temporary default removes an unsafe choice, not a safeguard.** Temporary is preselected, but the manager must deliberately choose configured-default expiry or an explicit future expiry, provide the protected internal reason and submit. Permanent requires explicit type selection, protected reason and the same normal submission—no second confirmation dialog, checkbox, acknowledgement or click; an empty expiry never becomes a shortcut.
- **Extension and conversion each remain one focused command.** Extension retains its approved confirmation. For either dedicated conversion, the manager supplies the new expiry where applicable and mandatory internal reason, then uses the normal command submission against the current lifecycle version without another confirmation. The same grant/history continues; no revoke/recreate, second approver or automatic renewal adds clicks.
- **Manual and emergency revocation preserve deliberate destructive friction.** One-grant revoke requires reason plus explicit confirmation. Emergency revoke-all requires one incident reason plus a high-salience all-grants confirmation, then system reconciliation; recipient selection and per-grant confirmations are absent because the server resolves/atomically revokes the full active set.
- **Employee notice and access-ended journeys are low-action.** Upcoming-expiry, conversion, manual-revoke and emergency-revoke notices are informational and expose no internal reason. Account disablement/employment termination still ends access immediately but creates no employee-notice journey in this checkpoint. Access loss replaces the protected view and purges cached state; the employee may navigate away or seek authorized support, but cannot renew, restore, continue offline or reuse an old download link from that state.
- **Risk reduction justifies the protected friction.** Exact expiry, live request/job/download reauthorization, emergency denial and short artifact retention add implementation/operations cost while preventing indefinite, stale-session and leaked-artifact access. No numeric duration or later-checkpoint behavior is counted or implied.

## 4.6 Checkpoint-13 journey effects

- **Reuse costs the minimum possible actions.** The complete withdrawn-request reuse journey is: open the request → review/edit → normal Submit. A hidden request adds only the Hidden records navigation before opening; no Restore-before-submit step, confirmation modal, acknowledgement, duplicate Resubmit click, or one-tap list shortcut exists anywhere. Restore exists solely to return a record to the normal personal list without submitting it. Residents preserve their work instead of recreating requests, with no artificial resubmission deadline while the same membership remains active and eligible.
- **Deliberate absences are safeguards, not friction.** No one-tap resubmission from the list exists because Q182 requires review/edit before ordinary Submit, where current-rule errors land. Content-read-only states (temporary ineligibility, ended membership) expose no Edit/Submit, but still expose Hide on an own visible exact-withdrawn record or Restore on its hidden form; this account-presentation action needs no current membership and grants no Building authority. Every non-withdrawn state exposes neither.
- **Admin workload stays clear at zero added actions.** Resubmitted requests take ordinary latest-submission queue placement with current-content-only review plus a neutral submitted/withdrawn/resubmitted timeline; the neutral lifecycle context preserves trust without biasing the reviewer with old text, and the ordinary immediate notification adds no new Admin action. A committed withdrawal removes decision actions from an open review rather than letting a wasted decision click fail late.
- **Hide/restore reduces clutter without weakening auditability**: exact-withdrawn-only presentation actions on the immutable original author's own history, never deletion or Admin-visible, and still available after membership end. Resubmission-first rejects stale Hide and keeps the active request visible; Hide-first is atomically cleared by successful resubmission. Permanent membership boundaries still prevent content reuse or Building authority after rejoining. The active product priority remains the resident/Building Admin application, not the company Super Admin Dashboard; the distinct Checkpoint-14 financial dispute journey is counted separately below.

## 4.7 Checkpoint-14 journey effects

- **Creating a dispute is one compact form.** Open exact payment/receipt → Dispute → choose structured reason, explain, optionally attach evidence → Submit. There is no confirmation, support redirect, attachment requirement, duplicate case-type screen, or free-floating entry. The original finance detail remains the anchor and gains only the neutral active indicator.
- **Information exchange stays inside one chronology.** An Admin request focuses the resident on one Reply action with optional evidence; it never forces withdrawal/recreation. The Admin reviews the same case after reply. Append-only history creates implementation cost, not extra user steps.
- **Admin review has exactly three actions.** Accept, Reject, or Request information; each collects its required reason/question in the selected action. While `DB-OPEN-20` is unresolved, Accept adds no correction fields or financial/non-financial selector and fails safely when classification/schema is unavailable, without adding a click. Only after future closed-schema approval may server-classified financial acceptance add its necessary fields and separate-entry preview inside that action—not a source-edit screen, resident confirmation, Vote, company escalation, or second approval. Correction-free acceptance creates no accepted-correction notification.
- **Withdrawal and reconsideration add only selected agency.** While undecided, Withdraw is one retained-state action with no delete confirmation. After rejection, Reconsider appears once and requires genuinely new material in the same case; no deadline, priority, or support handoff is added.
- **Continuity adds no administrative reassignment.** Membership end exposes only the author's own open-case read/reply continuation, and Admin replacement transfers review visibility automatically. Former Admin cache purge, version conflict refresh, first-commit-wins locking, notification dedupe, and correction reconciliation are system work, not user clicks.
- **Intentional friction is limited to evidence-quality controls.** Required structured reason/explanation and mandatory Admin reason/question protect review quality; correction details protect ledger integrity. Optional evidence, one Submit, server-derived actions, accessible EN/AR errors, and direct deep links keep the workflow compact without weakening authorization or immutability.

## 4.8 Checkpoint-15 journey effects

- **Creating community content is one compact form.** Open community create → pick `Discussion` or `Issue` → fill the canonical fields → pick named or anonymous (with inline copy that the Admin still sees identity) → one Submit. No confirmation modal, second approval, company path, or duplicate type screen exists; the pending state is a neutral chip, not an extra step.
- **Rejection turns into productive rework, not re-entry.** The author opens the rejected item, reads the mandatory safe reason, and uses one Revise & resubmit action seeded with the latest revision, choosing presentation afresh for the new revision only. Unlimited genuine-change attempts remove deadline anxiety; the genuine-change guard costs the user nothing when they actually changed something.
- **Admin review is two decisive actions.** Approve commits without extra input; Reject collects its mandatory reason inside the action. The real identity plus the author-selected-anonymous badge sits in the same detail view, so anonymity handling adds zero navigation. Issue progress is the single applicable next-step action (`Start progress`, then `Resolve` with an optional summary field that never blocks).
- **Reopening adds only selected agency.** One Request reopening action with its mandatory reason appears on an own resolved Issue while unused; the Admin decides with Accept or Reject, each collecting its mandatory reason, and the explained outcome reaches the author without any support handoff, escalation, or extra confirmation.
- **Commenting is immediate.** Active members compose and submit in place with a per-comment named/anonymous toggle; no per-comment approval wait exists. The Admin's Hide is one overflow action with an optional reason; residents simply see a neutral unavailable placeholder, costing readers nothing.
- **Intentional friction is limited to review-quality controls.** Mandatory reasons (rejection, reopen request, reopen decision) and the genuine-change resubmission guard protect moderation quality; immutable revisions, presentation immutability, concealment of pending content, first-commit-wins locking, and former-Admin cache purge are system work, not user clicks. Discussion closure, reactions, threading, and notification tuning are deliberately absent pending Q226+, not missing steps.

## 5. Out of Scope for This Audit

Journeys whose cost is dominated by asynchronous system behavior rather than user action — Request a Wallet Withdrawal (§1.14, Paymob callback/webhook or reconciliation review), Create a Building's location resolution (§1.4 Step 1) — are not compressible by removing user actions, since the wait is not a user action. Improving perceived latency there is a performance/UX-feedback question, not a click-count question, and is not addressed by this document.
