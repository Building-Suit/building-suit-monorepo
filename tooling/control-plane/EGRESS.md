# Compact Dot egress contract

Normal operation uses `runner/dot-health-inputs.sql`: one server-side current-state scan, explicit columns and indexed latest rows. Tasks awaiting admission are paginated separately. Descriptions, plans, metadata, complete execution/verification histories and logs are excluded from the ordinary contract. Admission includes only dependency/decision identities and publication path authority needed to preserve exact gates.

BS-31 classifies this scan using the existing process receipts and health classifier before loading supervisor evidence. Healthy workers, future timers, exact human gates and live incident leases do not load evidence. Due receipt reconciliation, STUCK, unknown failure, publication handoff, completion credit and next-task acquisition retain their existing guarded recovery paths. A cycle cache loads a task snapshot once; an observed post-reconciliation state transition can invalidate it. Full supervisor evidence remains available for an actual recovery, and every existing verification/budget/lease/credit authority remains enforced.

The health server serves `/api/status` entirely from one local cache, including local telemetry. It has one serialized PostgreSQL session through the existing configured session pooler, a 30-second query deadline and 30-minute connection rotation. BS-31 publishes its classified observations locally; the server also refreshes compact state every two minutes. No browser GET of status performs SQL. The browser refreshes every 60 seconds. History and queued tasks load only when opened, 25 records per page; task, verification and incident details each fetch one explicitly selected identity. Cached timestamps and a three-minute stale warning remain visible if SQL fails.

The observer relay retains its five-second **small persisted outbox watermark query**, which covers missed notifications through the pooler. The separate health five-second heartbeat/listener is removed. Fifteen-second event batching, identifier watermarks, the existing watchdog lock and persisted per-subject event/generation outcomes coalesce duplicate work. If the scheduled scan has already consumed an event batch, the relay drops its pending duplicate wake. `094_compact_dot_cycle.sql` acknowledges only the scan's captured watermark, retaining events arriving during evaluation; it reconciles recovery completion/review evidence internally and grants cycle writes only to the runtime executor. The existing two-minute n8n fallback is retained unchanged.

Local telemetry lives under the configured repository's `.local/control-egress`, with owner-only files and three-day retention. Only numeric query/returned-byte/client-session/cache/cycle/evidence counters are stored. Last-hour and last-24-hour totals use local files, consume zero LLM and call no billing API. Event/fallback counters classify evaluations by whether the compact scan saw pending outbox events; they are not n8n trigger-node counts. Returned-byte counters measure query response bodies, not PostgreSQL wire framing or provider billable egress. Client session counts do not claim physical pooler backend connections.

## Validation and rollout

Run `node --test tooling/control-plane/tests/*.test.mjs`, with explicit disposable PostgreSQL prerequisites for the three existing integration tests. `dot-egress.test.mjs` requires `CP_EGRESS_TEST_DATABASE=cp_egress_<name>` for its actual PostgreSQL payload test; it inserts huge synthetic descriptions/metadata and 100 verification histories inside a rollback transaction. Also run `tests/compact-dot-cycle-smoke.sql` in a disposable database to verify late-event preservation and observer denial. Ordinary health rows have a 15 KB regression budget, watchdog rows 25 KB, and a representative overview 100 KB. Pooling/error/reconnect tests and real relay batching tests cover transport behavior.

Use the existing exact environment-bound migration transaction and immutable prepare/activate mechanism, with installed-pointer compare-and-swap, schema attestation, complete regression receipts, readiness and rollback. Apply this control-only forward migration; do not apply product migrations. Preserve the source release's entire dependency closure and add the new modules. Restart health and event services only; n8n already dispatches the installed bootstrap and needs no workflow change. Observe at least ten minutes after activation before claiming success. A new deployment must not overwrite a concurrent installed release.
